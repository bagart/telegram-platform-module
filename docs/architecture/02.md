
02 — Domain Model и базовые контракты

1. Назначение

Этот документ определяет доменную модель TelegramModuleEngine, структуру декларативных DTO/definition объектов и границы основных сущностей.

Цель — сначала зафиксировать понятия и отношения между ними, а уже потом проектировать Laravel-интеграцию, БД, bootstrap, Menu и Management.

Главная цель контрактов: module package → typed immutable definition → Engine → registries / runtime / admin / menu.

Не должно быть ситуации, когда половина информации о module находится в: ServiceProvider, config/, routes/, migrations, seeders, controllers, React, database.

Главное правило:

Domain Model не должна зависеть от Laravel, Eloquent, Telegram API, HTTP, Redis или конкретного UI.

2. Базовые понятия

В Engine необходимо различать следующие сущности:

ModuleId

TelegramModuleDefinitionProvider (entry point)
TelegramModuleCompatibility
TelegramModuleConfig (PlatformModuleConfig)
TelegramModulePlatformConfig
BotModuleBinding
ChatModuleOverride
EffectiveModuleConfig
ResolvedModule

CapabilityDependency

Их нельзя объединять в один универсальный Module class и нельзя называть одним словом Config.

3. Общий принцип: Definition vs Implementation

Module состоит из двух слоёв: Definition (что module собой представляет) и Implementation (как module работает).

Definition должен быть максимально декларативным и не должен содержать business logic.

Definition не должен выполнять: DB queries, HTTP requests, Telegram calls, filesystem operations, cache operations.

Это общий принцип всех DTO: DTO describes → Engine resolves → runtime executes.

В частности:

- dependencies описывают requirement, но не выполняют resolution — requirement решает Engine resolver;
- resources содержат permission ID, но не выполняют authorization — allowed/denied решает Authorization service;
- visibility policy — это metadata, не исполняемая внутри DTO.

Ни один DTO не должен выполнять runtime side effects или скрытые mutations при чтении.

Также: modules never talk to each other directly — взаимодействие только через capability/contribution контракты, которые разрешает Engine.

4. ModuleId

Идентификатор модуля — отдельный Value Object.

Требования: immutable; canonical string; case-sensitive или case-normalized по одному глобальному правилу; запрещены пробелы; запрещены неоднозначные значения; пригоден для database key, config key, cache key, URL/API.

Рекомендуемый формат: lowercase-kebab-case.

Стабильность ID (правила):

- ID — внешний ключ, используемый БД (tg_bot_modules.module_id), menu contributions, permissions, frontend manifests, cache и diagnostics;
- никогда не class name, display name или Composer package name;
- ограниченный charset, например [a-z0-9][a-z0-9._-]*, ASCII, lowercase;
- переименование ID — это migration-level operation, требующая явного module identity migration;
- тихая смена `cinema` на `movies` осиротит существующие bindings.

Примеры: menu, management, mafia, cinema-radar, proxy-operations, summarizer.

Не использовать PHP class name как module ID. Например, BAGArt\TelegramBotMafia\TelegramBotMafiaServiceProvider не является идентификатором модуля.

5. ModuleDefinition

ModuleDefinition — декларативное описание модуля, предоставляемое самим package.

Он отвечает на вопрос: что представляет собой данный модуль и какие возможности он предоставляет/требует?

Definition приходит только от module package; Configuration приходит от platform owner; Bot configuration приходит из BotModuleBinding; Effective configuration вычисляется resolver.

Пример:

ModuleDefinition(
    id: ModuleId('mafia'),
    name: 'Mafia',
    description: 'Telegram Mafia game',
    version: ...,
    dependencies: [...],
    capabilities: [...],
    contributions: [...]
)

Definition должен быть immutable.

6. Definition entry point и четыре ответственности

Не называть источник definition "ServiceProvider" — предпочитать TelegramModuleDefinitionProvider / EntryPoint.

Его свойства: stateless; не требует DB, HTTP, текущего bot или текущего user.

Четыре ответственности, которые никогда не смешиваются в одном классе:

- Definition = WHAT (что module поставляет);
- Provider = HOW (как Laravel integration регистрируется);
- Domain/Application = business logic;
- Runtime Resolver = WHETHER (активен ли module для данного bot).

Laravel ServiceProvider — это infrastructure registration, отдельная сущность.

7. Совместимость и версии

Compatibility metadata: отдельный TelegramModuleCompatibility DTO может описывать engineVersion constraint, phpVersion и (опционально) framework version.

Composer остаётся первичным механизмом dependency enforcement; compatibility в Definition — дополнительная runtime диагностика, дающая MODULE_ENGINE_VERSION_UNSUPPORTED вместо запуска module частично и ловли случайных runtime errors.

Module может объявить minimum/maximum Engine version, но Engine никогда не позволяет module centrally override compatibility checks.

Тройное разделение версий — три независимые версии, которые нельзя схлопывать в одну:

- package version — Composer, source of truth;
- module contract version — Definition, публичный контракт module;
- configuration schema version — configuration DTO/schema.

Definition не должен дублировать Composer package version; Engine читает её из Composer metadata.

8. Что входит в Definition

Минимально: id, name, description, dependencies, capabilities, contributions.

В дальнейшем могут появиться: version (contract version, см. раздел 7), vendor, icon, category, documentationUrl, supportUrl, tags.

Но Definition не должен превращаться в универсальную свалку metadata: каждое поле должно иметь конкретного потребителя.

Рекомендуемая внутренняя иерархия (composition, а не один гигантский DTO):

TelegramModuleDefinition
ModuleIdentity
ModulePresentation
ModuleDependencies
ModuleCapabilities
ModulePermissions
ModuleResources
ModuleConfiguration
ModuleLifecycle
ModuleInfrastructure

Не делать один огромный TelegramModuleConfig на 150 properties.

9. Что НЕ входит в Definition

Definition не должен содержать:

- enabled;
- bot ID, tenant ID, user ID, group/chat ID;
- database state, runtime state, Laravel application state;
- mutable configuration, secrets, Telegram bot token;
- admin settings конкретного бота;
- Eloquent models (нельзя TelegramModuleConfig(model: BotModule::...));
- Request objects;
- Container.

Definition описывает package/module, а не его текущее состояние.

10. Naming conventions для DTO

Имена должны быть последовательными:

- *Definition — package metadata (TelegramModuleDefinition, ModuleDependencyDefinition, ModuleCapabilityDefinition, ModulePermissionDefinition, ModuleResourceDefinition);
- *Context — runtime context;
- *State — state representation;
- *Snapshot — immutable resolved snapshot;
- *Resolution — результат разрешения;
- *Settings — persistent settings (если это действительно settings);
- *Binding — bot/module connection (BotModuleBinding);
- *Override — scoped configuration overrides (ChatModuleOverride);
- *Manager — state-changing operations;
- *Resolver — resolution;
- *Registry — indexed metadata;
- *Runner — execution.

Не использовать одно слово Config для всех этих сущностей.

TelegramModuleConfig не должен означать одновременно: package manifest, platform config, bot config, effective config.

Это одна из наиболее важных правок исходной концепции.

11. TelegramModuleConfig (PlatformModuleConfig)

TelegramModuleConfig — configuration конкретной установки платформы (platform-level; в терминах naming convention — PlatformModuleConfig).

Это не Definition.

Концептуально:

TelegramModuleConfig(
    platformPolicy: ...,
    platformConfig: ...,
    presentation overrides: ...,
    admin exposure: ...
)

Он отвечает: разрешён ли этот module на данной установке и как он интегрирован с этой установкой?

Его задача — platform-level overrides. А package definition — TelegramModuleDefinition. Это два разных объекта.

12. Слои конфигурации: default / configured / effective

Нельзя смешивать default, configured и effective.

Полная модель слоёв (каждый уровень — отдельный type):

ModuleDefinition
↓
PlatformModuleConfig
↓
BotModuleBinding
↓
ChatModuleOverride
↓
EffectiveModuleConfig

- Module defaults описываются Definition.
- Platform overrides описываются config/tg_modules.php.
- Bot overrides хранятся в persistent state (BotModuleBinding, database).
- Chat overrides, если поддерживаются, хранятся отдельно (ChatModuleOverride).
- EffectiveModuleConfig — только вычисленный immutable resolved snapshot; он не хранится как authoritative state и не является source of truth.

Главный инвариант контрактов: ModuleDefinition описывает то, что поставляет package; PlatformModuleConfig описывает решение владельца платформы; BotModuleBinding описывает подключение skill к конкретному bot; ChatModuleOverride — локальные overrides; EffectiveModuleConfig — только вычисленный immutable результат. Ни один из этих объектов не должен подменять другой, ни один DTO не должен выполнять runtime side effects, и ни один слой не должен напрямую подменять lifecycle, runtime context, authorization или implementation другого слоя.

13. tg_modules.php — composition root

tg_modules.php должен быть declarative composition root.

Например концептуально:

return [
    'cinema' => new TelegramModuleConfig(...),
    'mafia' => new TelegramModuleConfig(...),
];

Он содержит только: module ID, platform policy, platform config.

Он не содержит: bot state, chat state, runtime mutable state, произвольные ServiceProvider class-ы.

Configuration не должна создавать module. Configuration может только: override, disable, restrict, configure.

Нельзя добавить неизвестный module через config и ожидать его регистрации. Unknown module config → configuration error. Это предотвращает typo вроде 'cinemma'.

Identity: array key должен совпадать с config->moduleId, а Engine проверяет configured key == discovered definition ID. Несовпадение (key = cinema, config.moduleId = mafia) — fatal configuration error. Один источник identity. Duplicate configuration keys невозможны.

14. ServiceProvider: кому принадлежит

ServiceProvider::class — не domain concept, это Laravel-specific integration. В чистом Domain Model не должно быть serviceProvider: SomeLaravelServiceProvider::class в ModuleDefinition.

Рекомендация: provider должен принадлежать module package definition (TelegramModuleDefinition / Provider), а не platform config.

Почему: platform owner не должен подменять runtime implementation. Иначе configuration file становится executable composition API с риском accidental override, wrong provider, incompatible provider. Пользовательский config не должен указывать arbitrary ServiceProvider class.

Если provider всё же сохранён в TelegramModuleConfig (совместимость с исходной архитектурой), Engine должен проверять configured provider == discovered provider. Но лучше убрать его из user-facing config.

Итоговое разделение: Domain — ModuleDefinition / Provider; Laravel Integration — tg_modules.php с только platform policy/config.

Это важное исправление первоначального замысла.

15. Семантика enabled

Слово enabled в platform config должно означать только platform-level allowed/default policy, а не bot enabled.

Не использовать одно слово enabled без scope semantics. Иначе через полгода будет "module enabled?" — но непонятно: package? platform? bot? chat?

Рекомендуются явные термины: installed, registered, platformAllowed, botEnabled, chatEnabled, effective.

Например вместо enabled: true — policy: ModulePlatformPolicy::enabled() или availability: ...

TelegramModuleConfig может содержать: platformPolicy, platformConfig, presentation overrides, admin exposure.

Но botEnabled там быть не должно. Bot state — только database (PostgreSQL).

16. Разделение Definition и Config (пример)

Package сообщает:

Definition:
id = mafia
requires = telegram.navigation
provides = mafia.game
contributions = [...]

Администратор платформы задаёт:

Config:
platformAllowed = true
platformConfig = MafiaPlatformConfig(...)

Для другой установки: Config: platformAllowed = false.

Package при этом остаётся тем же.

17. TelegramModulePlatformConfig

TelegramModulePlatformConfig — immutable DTO с platform-level configuration.

Базовый DTO должен быть небольшим. Предварительная концепция:

TelegramModulePlatformConfig(
    menu: ...,
    migrations: ...,
    seeders: ...,
    userUrl: ...,
    adminUrl: ...
)

Но это пока не финальный контракт.

Особое внимание необходимо уделить тому, какие поля действительно являются configuration, а какие на самом деле являются module descriptors.

18. URL configuration и resource identity

Нужно различать:

- userUrl — URL entry point для bot owner/user (пользовательского интерфейса модуля), например /cinema;
- adminUrl — platform/admin configuration UI (административного интерфейса), например /admin/modules/cinema.

Но URL не должен быть произвольной строкой без contract.

Лучше: ModuleRouteDefinition — stable resource identity вида resource/action, например cinema.settings, вместо "/admin/cinema".

Почему: URL может измениться. Stable identity — module, resource, action. Router сам строит URL. Тогда cinema.settings может сегодня быть /admin/modules/cinema, а завтра /settings/skills/cinema — и module contract не ломается.

Поэтому userUrl/adminUrl лучше рассматривать как compatibility convenience, а не core identity.

Ограничения:

- абсолютный URL не должен быть обязательным;
- предпочтительно хранить route/path descriptor, а не готовый абсолютный URL;
- если URL зависит от bot context, он не должен храниться как простой static string.

Если пользователь хочет явно задать URL, должна существовать UrlOverride. Но default URL определяется module resource.

Это необходимо отдельно проработать в документе Menu/Management Integration.

19. Admin/Menu resource registries

Admin не должен знать module-specific URLs. Он получает AdminResourceRegistry и строит navigation по: module, section, resource, action.

То же для Menu: MenuResourceRegistry. Module definition может объявлять menu resources.

20. Resource visibility policy

Resource должен иметь visibility policy, например: always, authenticated, permission, module active, feature available.

Но permission evaluation не выполняется внутри DTO: DTO содержит permission ID; Authorization service решает allowed/denied.

21. CapabilityId

Capability — отдельный Value Object.

Формат: namespace.name.

Примеры: telegram.navigation, telegram.bot-api, telegram.media, telegram.payments, telegram.storage.

Module capabilities должны иметь stable IDs, например: cinema.search, cinema.catalog, cinema.rating.

Capability ID не должен зависеть от PHP interface name. Implementation может быть interface CinemaSearch: capability ID — публичный контракт, PHP interface — implementation contract.

Это позволяет module A зависеть от capability B без жёсткой зависимости на package B — особенно полезно для optional integrations.

Module menu может предоставлять telegram.navigation; другой implementation в будущем тоже может предоставлять эту capability.

22. ModuleCapability

ModuleCapability описывает capability, предоставляемую module.

Концептуально:

ModuleCapability(
    id: CapabilityId,
    metadata: ...
)

Важно: Capability означает наличие архитектурного контракта, а не просто наличие какого-либо класса.

23. Provider Module vs Consumer Module

Модуль может: consume capability; provide capability; одновременно consume и provide.

Например: Menu provides telegram.navigation; Mafia requires telegram.navigation.

Это позволяет избежать жёсткой зависимости Mafia → Menu.

24. Capability vs Permission vs Resource

Не смешивать три concept:

- Capability — что система умеет (stable ID, не PHP interface name);
- Permission — кому разрешено (stable ID, например cinema.search, cinema.admin, cinema.configure);
- Module resource — где это доступно.

Эти три concepts должны оставаться отдельными.

Permission definitions объявляются декларативно, но permission system — отдельный module: Engine хостит только PermissionContribution контракты, не саму authorization.

25. ModuleDependency

Зависимость должна быть отдельной сущностью. Типы: ModuleDependency, CapabilityDependency.

Пример module dependency: requires module menu. Пример capability dependency: requires capability telegram.navigation.

Концептуально:

ModuleDependency(
    moduleId: ModuleId,
    constraint: VersionConstraint|null,
    required: true
)

Позволяет описывать requires: menu >= 2.0.

Но версия module должна использоваться только если реально требуется version compatibility. Не стоит вводить version constraints только ради сложности.

26. CapabilityDependency

Концептуально:

CapabilityDependency(
    capability: CapabilityId,
    required: true
)

Пример: telegram.navigation или telegram.bot.commands.

27. Circular Dependencies

Engine должен уметь обнаруживать A → B → A, а также A → B → C → A.

Cycle должен считаться configuration error.

Нельзя пытаться автоматически "разруливать" цикл порядком регистрации.

28. ModuleContribution

Contribution — декларативное описание того, что module добавляет в платформу.

Примеры: MenuContribution, AdminContribution, PermissionContribution, RouteContribution, FrontendContribution.

Не следует создавать один giant ModuleContribution(type: ..., payload: mixed). Предпочтительно typed contributions.

Contribution contracts должны иметь stable contribution IDs, например mafia.menu.main, mafia.admin.settings. Они нужны для deduplication, override, diagnostics, caching и testing.

Ordering/priority допустим, но вторичен по отношению к semantic grouping.

Visibility policy — metadata only; permission evaluation и dependency resolution никогда не исполняются внутри DTO — DTO describes, Engine resolves, runtime executes.

Engine хостит только contribution контракты; сами системы (permission system, audit, settings rendering) — отдельные модули, не часть Engine.

29. MenuContribution

Пример концептуально:

MenuContribution(
    id: 'cinema',
    label: ...,
    icon: ...,
    target: ...,
    order: ...
)

Но Menu-specific semantics не должны проникать в core domain слишком глубоко. Лучше определить generic contribution contract и Menu-specific adapter.

30. AdminContribution

Module может объявить:

AdminContribution(
    section: ...,
    label: ...,
    route: ...,
    permission: ...
)

Management получает их через Engine. Таким образом Management не знает конкретные модули.

31. PermissionContribution

Модуль объявляет:

PermissionContribution(
    id: ...,
    description: ...,
    scope: ...
)

Например: mafia.game.play, mafia.game.manage.

Но Engine не решает, может ли пользователь Artur выполнить это действие — это делает Authorization layer (отдельный permission module).

32. Module commands как metadata

Module commands также должны быть metadata. Например:

command:
id = cinema.search
telegramCommand = /cinema
action = search

Telegram command может быть optional. Web route может быть optional. Mini App action может быть optional.

Поэтому module может существовать вообще без Telegram command. Это важно для infrastructure modules, background modules, Admin-only modules.

Следовательно: module ≠ Telegram command; module ≠ Menu item; module ≠ Admin page.

Module является composition unit, который может предоставлять любое количество ресурсов. Module может иметь 0 commands, 0 menu items, 0 admin pages, 0 permissions, 0 capabilities — и всё равно быть валидным.

Это позволит infrastructure modules: Management может быть admin-only, Engine может не иметь user-facing resources.

Command definition — metadata; command implementation регистрируется отдельно. Menu definition — metadata.

33. ResolvedModule

ResolvedModule — результат объединения ModuleDefinition + TelegramModuleConfig + installation state.

Он является read model. Например:

ResolvedModule(
    definition: ...,
    configuration: ...,
    platformEnabled: true,
    installed: true
)

Он нужен, чтобы consumers не собирали состояние самостоятельно.

34. Installed State

Нужно отличать "ModuleDefinition exists" от "module package actually installed".

Однако Engine не должен самостоятельно анализировать Composer filesystem. Лучше иметь infrastructure adapter ModuleInstallationDetector, который предоставляет installed(ModuleId): bool.

Таким образом Composer остаётся инфраструктурой.

35. BotModuleBinding

BotModuleBinding — persistent состояние подключения module к конкретному bot (bot overrides).

Хранится в database (PostgreSQL), не в config. Содержит botEnabled state и bot-specific settings references.

Configuration changes должны иметь revision, например: bot module binding revision = 12.

36. BotModuleActivation

BotModuleActivation — состояние конкретного module для конкретного Telegram bot. Это уже tenant-level сущность.

Концептуально:

BotModuleActivation(
    botId: ...,
    moduleId: ...,
    status: ...,
    revision: ...,
    createdAt: ...,
    updatedAt: ...
)

37. Activation Status

Не использовать boolean.

Минимальная state machine: DISABLED, ENABLING, ENABLED, DISABLING, FAILED.

Возможно также BLOCKED. Но BLOCKED лучше рассматривать как effective availability, а не как persisted activation status.

Поэтому предпочтительно:

- persisted status: DISABLED, ENABLING, ENABLED, DISABLING, FAILED;
- effective state: AVAILABLE, BLOCKED, UNAVAILABLE.

38. Почему BLOCKED не должен быть обычным статусом

Например: Mafia = ENABLED, но Menu = disabled и Mafia требует navigation. Mafia фактически не может работать.

Однако это не означает, что администратор отключил Mafia.

Поэтому: activation.status = ENABLED, но availability = BLOCKED. Причина: dependency menu unavailable.

Это позволяет не терять исходное намерение администратора.

39. ModuleAvailability

ModuleAvailability — вычисляемый объект.

Он отвечает: может ли модуль быть использован/включён в данном контексте?

Например:

ModuleAvailability(
    state: BLOCKED,
    canEnable: false,
    reasons: [...]
)

Возможные состояния: AVAILABLE, BLOCKED, UNAVAILABLE, DISABLED.

Точные значения будут утверждены в отдельном документе lifecycle/dependency.

40. Blocking Reason

Причины блокировки должны быть структурированными Value Objects. Например:

ModuleBlockingReason(
    code: 'dependency-unavailable',
    moduleId: ...,
    capability: ...,
    messageKey: ...
)

Не следует хранить только строку "Menu is disabled", потому что UI, API и диагностика должны иметь машинно-читаемый код.

41. BotModuleSnapshot

BotModuleSnapshot — центральная read model runtime. Он строится для конкретного bot.

Концептуально:

BotModuleSnapshot(
    botId: ...,
    revision: ...,
    modules: ...,
    capabilities: ...,
    contributions: ...,
    configurationRevision: ...,
    generatedAt: ...
)

Snapshot immutable.

42. Snapshot должен быть полным

Consumer не должен делать modules(), activations(), dependencies(), capabilities() и самостоятельно собирать effective state.

Он должен получить snapshot(bot) и работать с уже разрешённым состоянием.

Это особенно важно для: workers, Telegram update processing, Menu, Management, caching.

43. Snapshot не является Source of Truth

Snapshot — read model.

Source of truth:

- config (tg_modules.php)
- package metadata (Composer + Definition)
- PostgreSQL (database activation/binding state)

Snapshot можно пересоздать, удалить, инвалидировать, закешировать.

Нельзя делать snapshot единственным хранилищем activation state.

44. Snapshot Revision

Snapshot должен иметь revision. Например: botId = 42, revision = 18. После изменения module activation: revision = 19.

Consumers могут проверять актуальность.

45. Effective Module State

Snapshot должен предоставлять состояние module: installed, platformEnabled (platformAllowed), botStatus (botEnabled), available, usable, blockingReasons.

Не заставлять каждый consumer повторять dependency resolution.

46. Effective Capability Set

Snapshot содержит capabilities — только реально доступные capabilities.

Например: Menu disabled → telegram.navigation отсутствует в effective capabilities, даже если package Menu физически установлен.

47. Effective Contributions

Contribution должен попадать в snapshot только если соответствующий module реально доступен для данного bot/context.

Например: Mafia menu item не должен появляться в Menu, если Mafia = disabled или Mafia = blocked.

48. Контекст: ModuleResolutionContext

Очень важный момент: snapshot только на уровне Bot недостаточен для будущих scopes.

Нужно заложить abstraction ModuleResolutionContext.

Минимально: platform, bot. В будущем: group (chat), user, role.

Например:

ModuleResolutionContext(
    botId: ...,
    chatId: null,
    userId: null
)

Первую реализацию можно ограничить Bot context, но API не должен архитектурно закрывать остальные уровни.

49. Почему это важно

В дальнейшем может существовать: Bot: Mafia ON; Chat A: Mafia ON; Chat B: Mafia OFF. Или: User X имеет permission mafia.play, User Y — нет.

Engine должен позволять добавлять эти уровни без переписывания всей модели.

50. Tenant Boundary

BotId должен быть обязательным при разрешении bot-specific state.

Нельзя иметь API snapshot(), который случайно возвращает глобальное состояние. Предпочтительно: snapshot(BotId $botId).

51. Platform vs Bot vs Chat Configuration

Нужно чётко разделять:

- Platform config — config/tg_modules.php. Например: default URLs, provider policy, module-wide configuration, external service configuration, feature availability.
- Bot configuration — Database (PostgreSQL), BotModuleBinding. Например: enabled (botEnabled), module-specific settings, credentials, limits, bot-specific options.
- Chat configuration — Database, ChatModuleOverride (если поддерживаются). Например: feature enabled, chat-specific settings.

52. Configuration Override

Допустимая цепочка:

Platform defaults
↓
Bot overrides
↓
Chat overrides
↓
User overrides

Но это не означает, что каждый параметр обязан поддерживать override. Каждый configuration field должен явно определять допустимый scope.

53. Secret Configuration

Secrets не должны находиться в tg_modules.php, если есть возможность использовать стандартный Laravel secret/environment configuration.

Например: API keys, tokens, passwords должны храниться через application secret/config mechanisms.

TelegramModuleConfig должен описывать структуру configuration, а не становиться хранилищем секретов.

54. Configuration Schema

Configuration schema должна быть частью module definition.

Но schema не должна храниться только в Admin React code — иначе CLI/Web/Admin получат разные schemas.

Engine должен иметь canonical configuration metadata.

Configuration field может описывать: key, type, required, default, label, description, secret, validation constraints, visibility.

Field должен иметь scope: PLATFORM, BOT, CHAT (опционально). Может иметь: READ_ONLY, SECRET.

Validation logic не обязательно должна быть в DTO. Для сложной validation — validator class. Однако validator является implementation, а schema остаётся metadata.

Admin UI может автоматически построить form из schema — это позволит dynamic module settings UI, особенно для bot-specific settings.

Settings rendering — отдельный module: Engine предоставляет только canonical schema.

55. Secret fields в Admin UI

Admin UI не получает secret value. Вместо этого: configured = true.

При изменении: replace secret (explicit operation). Это должно быть стандартом Engine.

56. DTO: transport independence и serialization

Configuration DTO должны быть: typed, immutable, serializable, predictable, transport-independent.

Их можно использовать из: config file, DB hydration, CLI, HTTP, queue, tests.

Snapshot и diagnostics могут сериализоваться для Redis, cache, API, frontend. Но serialization format не должен определять Domain Model — должен существовать отдельный mapper/serializer.

Serialization должна быть deterministic. DTO должен корректно сравниваться по значениям (value-based equality, не object identity).

Это помогает: config diff, cache invalidation, tests, auditing.

57. JSON

Если snapshot будет храниться в JSON:

- schema должна быть versioned;
- enums должны иметь стабильные string values;
- internal PHP class names не должны попадать в persisted JSON;
- сериализация не должна использовать serialize() как публичный формат.

58. Cache Key

Cache key также не является частью Domain Model.

Но Engine должен использовать стабильную схему: tg-module-engine:{bot}:{revision}.

Runtime cache может использовать: module ID, bot ID, revision (snapshot и configuration revision). Это безопаснее, чем TTL-only cache.

Точный cache contract будет определён отдельно.

59. Immutable DTO

Все configuration/definition DTO должны быть immutable.

Предпочтительно: readonly properties; constructor initialization; отсутствие setters; отсутствие public mutable arrays; отсутствие dynamic properties.

Коллекции должны быть immutable или защищены от внешней модификации.

PHP constructor должен объявлять: types, defaults, invariants.

Config DTO нельзя изменять во время runtime. В config/tg_modules.php можно использовать object DTO, поскольку это PHP configuration — но DTO должны быть immutable.

60. Constructor-first Design

Требование проекта: в constructor должно быть объявлено всё необходимое для создания валидного DTO.

То есть new TelegramModuleConfig(...) не должен создавать объект в частично валидном состоянии.

По возможности:

- обязательные параметры обязательны;
- defaults задаются явно;
- null используется только если null действительно является допустимым состоянием.

61. Не злоупотреблять mixed

Плохо: public mixed $config или array<string, mixed> для всего module metadata.

array<string,mixed> не является основным public module contract. Arrays допустимы только для действительно динамических данных.

Но:

- module ID должен быть string;
- provider — class-string<ServiceProvider>;
- URLs — собственный typed representation (ModuleRouteDefinition) или строго определённый string contract;
- class references — class-string<T>, не arbitrary object instance в persistent config.

Предпочтительно: TelegramModulePlatformConfig, MenuContribution, AdminContribution, PermissionContribution, CapabilityDependency.

Это повышает: IDE support, static analysis, refactoring safety, runtime predictability.

62. Collections

Нужны typed collections: ModuleCollection, DependencyCollection, CapabilityCollection, ContributionCollection, BlockingReasonCollection.

Не возвращать наружу произвольные arrays там, где существует domain concept.

63. Validation

DTO validation должна происходить в трёх точках: application boot, configuration save, runtime resolution.

- Boot validation проверяет static configuration.
- Save validation проверяет user input.
- Runtime resolution защищает от stale/inconsistent state.

Никогда нельзя считать, что admin saved config → runtime automatically valid forever.

Runtime validation не заменяет save validation; save validation не отменяет runtime safety.

Definition evolution может сделать старую config invalid.

64. Configuration Schema Versioning и Migration

Configuration schema должна иметь version. Configuration version отделена от package version (см. раздел 7).

Module contract должен быть backward-aware. Например: ModuleDefinition v4 может читать config v3 — через migration.

Но migration не должна быть скрыта в getter — иначе reading configuration начинает менять state, а это плохая архитектура.

Лучше: explicit migration command/process. Configuration read не имеет скрытых mutations.

65. ModuleDiagnostics

ModuleDiagnostics — структурированный результат проверки.

Может содержать: moduleId, installed, platformEnabled, botStatus, availability, dependencies, capabilities, configurationProblems, lifecycleProblems, warnings, compatibility (engine/php version support).

Это read model.

66. Diagnostics != Logging != Audit

- Diagnostics отвечает: каково текущее состояние?
- Logging отвечает: что происходило?
- Audit отвечает: кто что изменил?

Эти три механизма нельзя объединять. Audit — отдельный module; Engine хостит только соответствующие contribution контракты.

67. Domain Events

Domain/application events должны описывать значимые изменения. Например: BotModuleEnabled, BotModuleDisabled, BotModuleActivationFailed.

Но Domain Event не должен зависеть от Laravel Event classes. Laravel adapter может bridge domain events в Laravel events.

68. Commands

Application-level commands: EnableBotModule, DisableBotModule. В будущем: ConfigureBotModule.

Command содержит только необходимые identifiers/options. Не должен содержать Eloquent models.

69. Queries

Application queries: GetModules, GetModule, GetBotModuleSnapshot, GetModuleAvailability, GetModuleDiagnostics.

Это позволит Management, Menu и runtime использовать единый API.

70. Repository Contracts

Domain/Application layer должен зависеть от contracts. Например: BotModuleActivationRepository, BotModuleBindingRepository, ModuleInstallationRepository, ModuleConfigurationRepository.

Но конкретный Laravel/Eloquent код находится Infrastructure.

71. Persistence Model

PostgreSQL — единственный source of truth для persistent state (activation, bindings, settings, overrides).

Предварительно необходима таблица tg_bot_modules с концептуальными полями:

bot_id
module_id
status
revision
created_at
updated_at

Дополнительные поля будут определены в документе Persistence.

Не следует сейчас преждевременно добавлять десятки module-specific columns.

72. Module Settings

Module-specific configuration нельзя помещать в tg_bot_modules, если она не является общей для всех modules.

Предпочтительная модель: tg_bot_modules — activation state; module-specific settings — separate storage.

Это позволит каждому module выбирать собственную структуру данных.

73. Generic Settings

Если понадобится универсальное хранилище bot_module_settings, оно должно быть дополнительным механизмом, а не заменой нормальной модели module.

Для сложных settings module должен иметь собственные tables.

74. Главные инварианты

Engine должен гарантировать:

Invariant 1 — Module ID уникален и стабилен (см. раздел 4).

Invariant 2 — Один bot не имеет двух activation records одного module.

Invariant 3 — Disabled platform module не может стать effective enabled для bot.

Invariant 4 — Module с неудовлетворённой обязательной dependency не является usable.

Invariant 5 — Disabled module не предоставляет effective capabilities.

Invariant 6 — Disabled/blocked module не предоставляет active contributions.

Invariant 7 — Bot activation не изменяет platform configuration.

Invariant 8 — Platform configuration не должна менять activation другого bot напрямую.

Invariant 9 — Snapshot и EffectiveModuleConfig являются производным состоянием (derived), не source of truth.

Invariant 10 — Consumer не должен самостоятельно повторять dependency resolution.

Invariant 11 — Definition отделена от implementation; Definition декларативна, immutable и не выполняет side effects (DB, HTTP, Telegram API, filesystem, cache).

Invariant 12 — ModuleDefinition ≠ PlatformModuleConfig ≠ BotModuleBinding ≠ ChatModuleOverride ≠ EffectiveModuleConfig; ни один слой не подменяет lifecycle, runtime context, authorization или implementation другого.

Invariant 13 — tg_modules.php содержит только platform-level configuration; unknown module configuration — error; configuration key проверяется против module identity.

Invariant 14 — enabled не используется без scope semantics; platform policy отделена от bot enabled state; bot enabled state хранится в database.

Invariant 15 — Capability, permission и module resource — раздельные concepts со stable IDs; permission evaluation не выполняется внутри DTO.

Invariant 16 — Module может иметь 0 commands, 0 menu items, 0 admin pages, 0 permissions, 0 capabilities — и оставаться валидным.

Invariant 17 — Configuration schema канонична (не только во frontend), versioned, с explicit migration; configuration read не имеет скрытых mutations.

Invariant 18 — Configuration DTO transport-independent, без Eloquent models/Request/Container; serialization deterministic; equality — value-based.

76. Главное исправление первоначальной идеи

Первоначально предполагалась структура примерно:

config/tg_modules.php

[
    'module' => new TelegramModuleConfig(
        enabled: true,
        serviceProvider: ...,
        tgPlatformConfig: ...
    )
]

Это сохраняем как внешний API configuration.

Но внутри Engine не следует считать этот объект всей сущностью Module.

Нужно:

ModuleDefinition
+ TelegramModuleConfig
+ Installation State
↓
ResolvedModule

А затем:

ResolvedModule
+ BotModuleBinding/Activation
+ Context
↓
Effective Module State
↓
BotModuleSnapshot

Это значительно чище.

Он должен определить точный контракт plugin/module package:

- как module объявляет себя;

Особенно важно на этом этапе решить один спорный вопрос:

Нужен ли вообще TelegramModuleConfig(... serviceProvider: ...) как ручная запись каждого модуля в config/tg_modules.php, или package должен сам декларативно регистрировать свой immutable manifest, а tg_modules.php должен содержать только platform overrides/enabled state?

Этот вопрос лучше решить до написания кода, потому что от него зависит вся дальнейшая архитектура.
