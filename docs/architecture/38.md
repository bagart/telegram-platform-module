38 — Tenancy & Runtime Context: Scope Model, Bot Module Bindings, Effective State & Runtime Resolution

Единый документ по tenancy и runtime context TelegramModuleEngine.
Объединяет и заменяет прежние документы: 38 (Bot Module Bindings, Multi-Tenancy & Per-Bot Skill Composition), 39 (Module Context, Runtime Resolution & Isolation), 51 (Bot / Tenant / Chat Scope Model).

Зафиксированные решения, обязательные для всего документа:

permission-system internals (grant trees, RBAC evaluation) — внешние: их владеет отдельный access module, который потребляет scope levels; Engine хранит и передаёт только opaque actor/chat IDs и не моделирует внутренности permission system.
никакой reconciliation machinery (K8s-style) — не существует и не проектируется.
никакого Telegram transport внутри Engine — transport внешний и bot-scoped.
PostgreSQL — единственный source of truth; события/кэши — производные.
модули никогда не общаются друг с другом напрямую; любая интеграция — только через platform-provided contracts.

Часть I. Scope model: Platform → Tenant → Bot → Chat → User

1. Назначение части — зафиксировать окончательную модель областей действия (scope) модулей и ресурсов и не допустить смешивания platform configuration, tenant configuration, bot configuration, chat configuration и user state.

2. Базовая иерархия:

Platform
↓
Tenant / Workspace
↓
Bot
↓
Chat
↓
User

USER не является обязательным child scope для всех ресурсов. Один физический Telegram Bot Token принадлежит конкретному bot binding; один пользователь может иметь доступ к нескольким bots/workspaces с разными правами.

3. Scope — это не просто поле (tenant_id, bot_id, chat_id). Scope определяет:

где существует объект
кто им владеет
кто может его изменять
где действует configuration
где действует permission
где действует lifecycle
где действует runtime state.

4. Platform scope используется для: installed modules, module definitions, global capabilities, global resource registry, platform policies, deployment configuration, system-wide infrastructure. Platform scope не содержит конкретного bot configuration, chat state, user preferences.

5. Tenant — изолированное рабочее пространство. Tenant может содержать: bots, users/members, tenant configuration, tenant permissions, tenant module policy, tenant-owned resources.

6. Bot — отдельная operational entity. Bot содержит: Telegram bot token reference, bot configuration, connected modules, bot-specific permissions, bot menu, bot runtime state.

7. Chat — sub-tenant/resource context, не tenant. Tenant в данной архитектуре — bot workspace; нельзя считать Telegram group = module tenant.

8. User может быть: platform user, tenant member, Telegram user — не смешивать. Application user идентифицируется внутри platform; Telegram user — через telegram_user_id. Membership связывает User ↔ Tenant; chat membership связывает Telegram user ↔ Chat. Нельзя считать Telegram user = application user. Один Telegram user может быть связан с несколькими platform users, если архитектура это допускает, но default identity policy должна быть определена явно.

9. Installation ≠ activation: module installed не означает module enabled for every bot; module enabled for Bot A не означает enabled for Bot B. Поэтому ModuleDefinition — platform-level, а BotModuleBinding — bot-level.

10. Tenant module policy (ModulePolicy): tenant может дополнительно иметь policy "allowed modules". Например: Platform: Summarizer installed; Tenant A: Summarizer allowed; Tenant B: Summarizer prohibited → Bot B не может подключить module, даже если module installed.

11. Policy hierarchy: Platform policy → Tenant policy → Bot policy. Принцип restrictive inheritance: нижний scope не может расширить запрет верхнего scope. Platform DENY нельзя override Tenant ALLOW; Platform ALLOW + Tenant DENY → Bot не может enable; Platform DENY нельзя override обычным tenant admin; Tenant DENY нельзя override bot admin. Исключение — explicit platform override, но только как privileged administrative action; arbitrary override flags не используются.

12. Chat-level policy: Chat не имеет собственной копии BotModuleBinding. Обычно module enabled for Bot, а Chat определяет, используется ли module здесь (AntiSpam enabled for Bot, но disabled for Chat A). Для этого нужен ChatModulePolicy / ChatModuleOverride, но он не создаётся для каждого module автоматически — только если module объявляет chat-scoped configuration/policy.

13. Module может заявить supportedScopes, причём по частям, а не одним "scope = BOT". Например:

CONFIG: BOT
POLICY: CHAT
STATE: CHAT

Разные части module могут иметь разные scopes: AntiSpam configuration — BOT, AntiSpam rules — CHAT, strike state — USER + CHAT. Поэтому scope должен быть свойством resource/data model, а не только module.

14. Module-owned data следует owner scope. Module объявляет data scopes, например: bot_settings — BOT, chat_settings — CHAT, user_state — CHAT_USER. CHAT_USER означает конкретный Telegram user внутри конкретного chat конкретного bot. Нельзя использовать global user state, если semantics требуют chat-specific state (Mafia role — GAME/ROOM scoped, а не global Telegram user scoped). Module сам определяет semantic scope; Engine проверяет, допустим ли этот scope.

15. ModuleDataOwnership contract: module обязан объявить owned data classes/categories, например:

BOT_CONFIG
BOT_STATE
CHAT_CONFIG
CHAT_STATE
USER_STATE
AUDIT_DATA

Это позволяет Engine понять, что можно purge. Нельзя доверять arbitrary DELETE queries из admin UI; purge проходит через DataOwnershipRegistry. Это особенно важно для plugins.

16. Data lifecycle следует scope:

при disconnect bot-scoped data может сохраниться;
при purge module-owned bot data удаляется;
при tenant deletion tenant-owned data удаляется/архивируется по retention policy;
при bot deletion bot-owned data обрабатывается отдельно (soft vs hard с purge);
chat deletion не должна удалить bot configuration;
user removal не должна удалить global Telegram identity.

17. Resource Registry также имеет scope. Например: AdminPage — PLATFORM_ADMIN, BotAdminPage — BOT_ADMIN, ChatSettings — CHAT_ADMIN. Учитываются system/internal resources: не всё является user-visible; internal module resource может быть PLATFORM_INTERNAL (например internal health probe), но даже internal должен иметь ownership — это помогает diagnostics, auditing, cleanup.

18. Scope ≠ permission. BOT scope не означает, что все пользователи bot могут изменять. Scope отвечает: "о каком объекте речь?". Permission отвечает: "может ли actor выполнить action?". Это принципиально и не смешивается.

19. Database-enforced isolation там, где возможно:

tenant-owned tables имеют tenant_id;
bot-owned tables обычно имеют tenant_id + bot_id;
chat-owned tables имеют tenant_id + bot_id + chat_id.

Нельзя полагаться только на application logic bot_id → tenant_id. Composite foreign keys / database constraints следует использовать там, где practically возможно: (tenant_id, bot_id) должны однозначно определять bot. Это снижает риск accidental cross-tenant reference.

20. Scope inheritance для configuration может поддерживаться: Platform default → Tenant override → Bot override → Chat override. Но inheritance должен быть explicit per setting, не magic fallback. Configuration schema объявляет inheritance strategy: INHERITABLE, BOT_ONLY, TENANT_ONLY, NOT_INHERITABLE. Например: timezone — Tenant default + Bot override; Telegram bot token — только Bot scope.

21. Secret никогда не должен inherit downward, если это нарушает security boundary: tenant API key не должен автоматически показываться bot admins. Visibility и inheritance — отдельные concepts: значение может inherit, но быть not visible нижнему admin. Это важное различие.

22. Scope resolution должен быть deterministic и возвращать: effective value, source scope, visibility. Например: timezone = Europe/Berlin, source = TENANT, overridden = false → Admin UI может показать "inherited from workspace". Bot admin может видеть effective value, но не обязательно secret source. resolve(module, bot) учитывает: platform policy, tenant policy, bot policy, binding, dependencies, configuration.

Часть II. Bot Module Bindings & Activation Policies

23. Ключевая архитектурная особенность платформы:

один Laravel application
↓
много Telegram bots
↓
каждый bot имеет собственный набор skills/modules
↓
каждый bot имеет собственные groups/chats
↓
каждый bot имеет собственное permission tree
↓
один установленный module package
↓
используется одновременно многими bots.

Композиция "один установленный plugin/module → множество bots → у каждого bot свой набор подключённых skills" при глобальной физической регистрации PHP-кода, с разрешением enable/disable, configuration, availability, permissions и runtime context на уровне конкретного bot — фундаментальный multi-tenant инвариант TelegramModuleEngine.

24. Поэтому module нельзя моделировать как installed = enabled. Lifecycle levels:

platform availability
bot binding
chat activation.

Chat-level activation в первой версии может быть optional, но архитектура обязана его предусматривать — иначе позже появится необходимость переписывать весь permission/binding layer.

25. Три уровня, которые строго разделяются: Platform, Bot, Chat / Tenant Context.

Platform level определяет: какие modules физически установлены, какие ModuleDefinitions существуют, какие capabilities существуют, какие resources зарегистрированы, какие modules глобально доступны.

Bot level определяет: какие skills подключены к конкретному bot, configuration конкретного bot, menu availability, commands, bot-level permissions, module preferences.

Chat level определяет: какие features разрешены в конкретной группе, chat-specific permissions, chat-specific settings, module-specific state.

26. Нельзя хранить module.enabled как глобальный boolean, если речь идёт о skill. ModuleDefinition описывает установленный module; BotModuleBinding описывает подключение module к bot.

27. BotModuleBinding концептуально содержит: bot_id, module_id, enabled, configuration, version, timestamps. Но configuration лучше не смешивать с lifecycle state, поэтому предпочтительнее BotModuleBinding + BotModuleConfiguration.

28. Разделение ответственности:

Binding отвечает: подключён ли module к bot?
Configuration отвечает: как module работает у этого bot?

Это позволяет валидные сочетания: module enabled + configuration invalid; module disabled + configuration valid.

29. Configuration не исчезает при disable. Например: Bot #1: Cinema enabled, language = ru, quality = compact. После disable: Cinema disabled, configuration preserved. После повторного enable: Cinema enabled, прежняя configuration restored. Это стандартное поведение.

30. Bot identity отделена от Telegram chat identity. Не использовать chat_id как bot tenant ID. Один bot обслуживает множество chats:

Bot
├── Chat A
├── Chat B
└── Chat C

Bot module binding привязан к Bot. Chat module state привязан к Bot + Chat + Module при необходимости. Например: Bot A: Mafia enabled; Chat 1: Mafia enabled; Chat 2: Mafia disabled — один skill подключён к bot, но не активен в конкретной группе.

31. BotModuleBinding не копирует ModuleDefinition:

Definition — static metadata: module ID, name, description, version, dependencies, capabilities, resources, permissions schema, configuration schema.
Binding — dynamic state: bot ID, module ID, desired enabled state, timestamps, configuration reference/version.

32. Не хранить в DB: PHP class names, ServiceProvider names, migration classes, seeder classes — это metadata application code, а не tenant data. DB хранит stable module_id (например mafia), а не BAGArt\TelegramBotMafia\TelegramBotMafiaServiceProvider. Это обеспечивает package refactoring, namespace changes, implementation replacement.

33. Module ID должен быть immutable. Если package переименован, module ID желательно сохранить. Если это невозможно, нужна explicit module identity migration.

34. BotModuleBinding имеет unique constraint: bot_id + module_id. Нельзя иметь два active bindings одного module для одного bot. Если module поддерживает profiles — это должна быть отдельная концепция; не создавать module_id + bot_id + random instance без архитектурной необходимости. Один bot имеет один logical module instance; внутри него может быть multiple resources, multiple commands, multiple menu entries, multiple chat configurations.

35. Module configuration может иметь уровни: platform defaults, bot overrides, chat overrides. Рекомендуемая модель:

ModuleDefinition defaults
↓
Platform configuration
↓
(Tenant configuration)
↓
Bot configuration
↓
Chat configuration.

Нельзя смешивать user configuration, secrets и module metadata. Например: ModuleDefinition: default language = ru; Bot: language = en → Effective configuration: en.

36. Configuration resolver должен быть централизованным. Не config(), DB query, env() в каждом module handler. Module получает ModuleRuntimeContext с resolved configuration.

37. Runtime Context может содержать: platform, bot, chat, actor, module, effective configuration, permissions, capabilities. Это не должен быть огромный mutable object; предпочтителен immutable context (детали — Часть IV).

38. Bot module state доступен через ModuleAvailabilityResolver. Не Bot::modules()->where(...) в каждом controller, не config('modules'), не class_exists(...), не if ($bot->id === ...). Все такие проверки уходят в Engine.

39. Bot Admin работает через BotModuleManager и показывает: Installed, Available, Connected, Blocked, Disabled, Deprecated. Особенно важно различать Installed и Connected:

Mafia: Installed: yes, Connected: no.
Другой bot: Mafia: Installed: yes, Connected: yes.
Третий: Mafia: Installed: yes, Connected: yes, Effective: BLOCKED — причина: required dependency disabled.

Таким образом Admin UI может дать [Подключить], [Отключить] или [Исправить зависимости].

40. Module catalog глобальный; bot-specific catalog является filtered view. Например: Global: Cinema, Mafia, Summarizer, Proxy, Menu; Bot A: Cinema, Menu; Bot B: Cinema, Mafia, Menu. Это не две разные системы — это same ModuleRegistry + different BotModuleBindings. Admin UI не поддерживает отдельный hardcoded список modules.

41. Подключение module к bot не должно физически загружать PHP package заново. Laravel application загружает package один раз; Engine загружает definition один раз; runtime выбирает effective modules для конкретного bot. Это позволяет 100 bots × 50 skills без 5000 ServiceProvider registrations.

42. Service Provider — module-level, не bot-level. Например MafiaServiceProvider регистрируется один раз. Но Mafia может быть active: Bot A, Bot C, Bot F; и inactive: Bot B, Bot D. Provider не должен пытаться определить bot configuration при application boot. Bot context появляется позже: webhook, polling, command, queue job, Mini App request, admin request. Поэтому boot-time ≠ bot runtime — это необходимо явно закрепить.

43. Activation policy per module (platform): OWNER_SELECTABLE, PLATFORM_ONLY, REQUIRED (cannot be disabled), FORBIDDEN, ADMIN_ONLY. UI различает три разных UX состояния с разными причинами:

Disabled — admin выбрал это сам;
Unavailable — не может быть connected;
Blocked — enabled, но prerequisites missing.

44. Module Engine не должен становиться Authorization Engine. Он только предоставляет permission definitions, module ownership, availability: Engine умеет сказать "module requires permission X"; authorization subsystem решает "actor has X?". Таким образом: Module Engine — WHAT exists и WHAT is available; Authorization — WHO may use it. Permission system — отдельный subsystem (access module); его internals (grant trees, RBAC evaluation) внешние и здесь не моделируются; Engine data несёт только opaque actor/chat IDs и передаёт scope levels в access module.

45. Permission resolution не должна происходить раньше bot resolution, потому что permission tree bot-specific. Например: Bot A: admin → mafia.manage; Bot B: admin → cinema.manage. Один module package может объявить permission schema, но конкретные grants хранятся per bot, per role, per chat, per actor — в зависимости от модели authorization (в access module).

46. Optimistic concurrency: BotModuleBinding поддерживает optimistic concurrency, например version = 17. Admin A: enable module; Admin B: disable module. Последовательность: A reads version 17; B changes → 18; A writes expecting 17 → typed conflict (MODULE_BINDING_CONFLICT / CONCURRENT_CONFIGURATION_MODIFICATION), не silent lost update. Это предотвращает lost updates и особенно важно для Bot Admin, Platform Admin, API, Telegram Mini App. Для multi-step topology mutations используется bot-level topology lock (bot:{id}:module-topology); module lifecycle mutation происходит внутри него.

47. Binding operations idempotent: enable Mafia дважды не создаёт две записи; disable дважды также безопасно. Enable operation: validate → persist (не persist → validate). Результаты typed, никогда не bare false: blocked / dependency_missing / forbidden / config_invalid / unavailable.

48. Effective state может стать BLOCKED после последующего изменения dependency — это нормально. Restoring dependency может вернуть binding в ACTIVE; BLOCKED binding не удаляется автоматически.

49. Dependency impact явный: disabling dependency предупреждает "Disabling B will disable A" и требует confirmation; cascade disable — explicit option, default off. Enabling module с disabled dependency не делает silent auto-enable (результат DEPENDENCY_DISABLED); disabling module с enabled dependents падает с MODULE_HAS_ENABLED_DEPENDENTS, если не подтверждено явно.

50. Bot binding не удаляется автоматически, если module package временно недоступен. Например: package removed → binding остаётся orphaned; Engine показывает MODULE_NOT_INSTALLED. Это полезно для восстановления. Orphaned binding не исполняется, но его configuration сохраняется. Если package снова устанавливается, binding может восстановиться автоматически: uninstall package → reinstall package → restore previous bot composition. Если module ID изменился — нужна migration.

51. Module replacement поддерживается: old-module replaced by new-module. Engine может предоставить replacement migration metadata, но автоматическая migration не является default. Bot composition — пользовательское состояние; изменение package не должно неожиданно менять его. Поэтому Package lifecycle и Bot composition lifecycle независимы — это один из главных архитектурных инвариантов всей платформы.

52. Installation не auto-enable: установка package ничего не меняет для существующих bots. New-bot provisioning использует explicit platform profiles (basic / standard / media), применяемые как one-time provisioning snapshot; после этого обычные bindings — source of truth; изменения profiles никогда не меняют существующие bots retroactively. Bot clone, bot deletion (soft vs hard с purge) и module replacement — explicit operations со своими политиками; secrets никогда не копируются и не раскрываются через binding data.

53. Transaction и side-effect ordering: binding mutation + audit + version increment — в одном DB transaction; cache invalidation и events — после commit (transactional outbox optional). Внешние эффекты (включая любые внешние API) не являются transactional resources: сначала commit, затем event/job (например menu update) с retry; неудачный menu refresh никогда не откатывает committed binding.

54. Binding mutations генерируют typed lifecycle events. Event не является source of truth: DB binding (PostgreSQL) является source of truth для desired bot state; effective availability является computed state.

55. Audit: lifecycle operations (connected, enabled, disabled, configured, uninstalled, purged) аудируются: actor, bot, module, operation, old/new state, revision, timestamp, source/reason, correlation ID. Audit хранится отдельно от binding (binding не является audit log) и никогда не содержит secret values (configuration audit фиксирует "api_key changed", а не значения).

56. Единая точка изменения bindings — Engine (BotModuleManager application service). Admin controllers, CLI, Telegram Mini App, API не изменяют binding напрямую — все используют BotModuleManager/Engine application service.

57. Menu module использует Engine для получения active modules bot и не хранит собственный список подключённых skills. Management module использует Engine для platform module catalog и bot module catalog. Basic module не требует специальных hardcoded integration points в platform. Skills не модифицируют core bot routing для каждого bot отдельно; skills регистрируются глобально и фильтруются runtime по bot context.

Часть III. Effective State, Snapshot & Caching

58. Desired vs effective state. Binding хранит desired intent (desired_enabled), никогда — authoritative effective state. Effective state вычисляется Engine resolver:

Installed AND PlatformEnabled AND BotEnabled AND DependenciesSatisfied AND ConfigurationValid
(+ tenant/bot policy из Части I).

Bot-level states: NOT_INSTALLED, AVAILABLE, DISABLED, PROVISIONING, READY, BLOCKED (with reason), ERROR, UNAVAILABLE (policy), ORPHANED (binding exists, definition missing). Только READY участвует в runtime. Platform disable имеет precedence и не разрушает bot bindings; re-enable может их восстановить. Missing package → ORPHANED, никогда auto-delete (rollback/reinstall friendliness).

59. Central distinction — discovery registry vs per-bot active runtime registry:

ModuleRegistry держит все discovered modules, включая disabled — admin diagnostics должны их видеть.
BotModuleRuntimeRegistry держит только effective modules одного bot; регистрация handlers/commands/menu происходит по возможности только для effective modules.

Это уменьшает branching, attack surface, overhead и убирает сотни проверок if (enabled) из runtime.

60. Immutable, versioned BotModuleSnapshot per bot (topology only, не все settings/permissions). Один incoming update работает против одного консистентного snapshot. Binding changes увеличивают monotonic topology version, инвалидируют кэши после DB commit и публикуют domain event (v1: единственное событие BotModuleTopologyChanged с botId/moduleId/operation/version). Long-running workers детектируют stale snapshot по version и перезагружают topology без перезапуска платформы.

61. Cache keys всегда включают bot identity: bot-modules:{botId}:{version}; per-binding tg:module-binding:{bot}:{module}:{version}.

62. Canonical scope key builder предоставляется Engine (например RuntimeScopeKey); нельзя позволять каждому module самостоятельно придумывать cache key. Примеры:

module config: module:{module}:bot:{bot}:config
chat cache: module:{module}:bot:{bot}:chat:{chat}:...
permission cache: bot scope, либо bot + chat + actor.

Нельзя module:mafia:permission:admin, если permission зависит от bot — это приведёт к cross-tenant leakage.

63. Snapshot invalidation triggers: binding change, bot state change, platform module config change, registry version change — но не каждый permission grant (permission snapshots — отдельный слой, принадлежащий access module).

64. Общая формула: effective state = policy (platform/tenant/bot) + binding + dependency + configuration; scope resolution deterministic.

Часть IV. Runtime Context, Resolution & Isolation

65. Главный принцип части:

installed module
≠
enabled module
≠
available module
≠
authorized module
≠
executed module.

66. Каждая операция module выполняется в явном context. Context layering: PlatformContext → BotContext → ModuleContext → OperationContext. BotContext = bot identity / tenant / workspace; ModuleContext = BotContext + definition + binding + effective configuration; OperationContext добавляет chat/user/request. Минимально: platform, bot, module; при необходимости: chat, actor, request, operation. Contexts typed, immutable, никогда не service locator.

67. Runtime Context может содержать: platform, bot, chat, actor, module, effective configuration, permissions, capabilities — но это не огромный mutable object; используется immutable context.

68. Bot context однозначно идентифицирует: конкретный Telegram bot, его tenant/workspace, его runtime configuration. Не использовать global currentBot. Особенно запрещено: static $currentBot, singleton mutable currentBot, глобальная переменная bot context. Это критично для queue workers, Octane, long-running daemons, async runtime, concurrent requests.

69. Chat context: если operation относится к Telegram chat, bot + chat рассматриваются как единый security/runtime context. Нельзя принимать chat_id без проверки принадлежности bot. Telegram update сначала привязывается к Bot, только после этого — к Chat. Это предотвращает cross-bot confusion.

70. Actor context определён отдельно. Например: Telegram user, Telegram bot owner, platform administrator, system worker. Actor не является module; actor не является tenant.

71. Authorization (внешний access module) использует: actor, bot, chat, permission — через explicit AuthorizationContext (actor, tenant, bot, chat, module, resource, action); Engine передаёт opaque IDs и scope levels. Module Engine использует: bot, module, dependency state. Не смешивать эти responsibilities. Один и тот же actor может manage Bot A, но не manage Bot B; может configure Summarizer для Bot A, но только use для Bot B.

72. Runtime Resolution Pipeline (рекомендуемый, централизованный):

incoming operation
↓
resolve bot
↓
create bot context
↓
authorize actor's bot access (against IDOR)
↓
resolve module
↓
resolve effective module state
↓
resolve capabilities
↓
resolve configuration
↓
delegate permission check to the access subsystem
↓
execute operation.

Authorization ordering против IDOR: resolve bot → authorize actor's bot access → resolve module → check binding → delegate permission check → execute. A module settings page никогда не доверяет произвольный bot_id из request.

73. Если module не указан явно, его может определить: command, route, menu item, webhook action, job, resource. Но после определения module ID должен быть explicit. Не передавать PHP class как runtime identity: runtime identity — stable module ID.

74. Module lookup идёт через Registry. Не new SomeModule() из controller, не class_exists() для определения module availability, не config('tg_modules.foo.enabled') в handler. Engine предоставляет ModuleResolver.

75. Availability вычисляется один раз на operation context — например ModuleAvailabilitySnapshot. Snapshot содержит: desired state, platform state, dependency state, capability state, configuration state, effective state. После создания snapshot в рамках одной operation не меняется самопроизвольно; это особенно важно при concurrent admin changes и async operations. Long-running job создаёт новый snapshot перед execution и не использует snapshot, созданный несколько часов назад.

76. Queue payload содержит: bot ID, module ID (если job module-specific); при необходимости chat ID, actor ID, binding revision. Не передавать serialized runtime context как основной способ восстановления. Queue job восстанавливает context из authoritative state. Например: Job: bot_id=7, module_id=mafia, binding_revision=19 → Worker: resolve bot 7, resolve mafia, validate revision/state, execute. Если binding изменился: job может быть rejected или revalidated — это policy, но централизованная. Queue jobs не полагаются на глобальный "current bot".

77. Runtime isolation: каждый bot имеет логически изолированные configuration, permissions, module state, menu state, cache namespace, queue context, secrets. Особенно Bot A vs Bot B: никакие module-specific values не должны случайно shared. Один PHP process может последовательно обслуживать разные bots; runtime state одного bot не протекает в другой bot. Все bot-scoped repositories требуют explicit BotContext (forBot($bot)->find($id), никогда find($id)); bot-scoped data tables несут bot_id; все bot-specific caches/settings/permissions/queues bot-scoped; нет static "current bot" globals, singletons или process-global state; shared workers multi-bot safe и re-resolve context между tasks.

78. Effective configuration precedence (deterministic):

module defaults
↓
platform config
↓
tenant config (если есть)
↓
bot override
↓
chat override.

Если chat override не существует — bot value; если bot override не существует — platform (tenant) value; если и его нет — module default. Configuration resolution не выполняется через произвольные config() calls; resolver централизован.

79. Secrets не имеют обычного inheritance semantics без explicit policy. Например API key лучше иметь как platform secret / bot secret; не копировать автоматически secret из platform в bot database. Configuration resolver различает public config, private config, secret config. Admin UI не получает secret через обычный module configuration DTO. DTO для runtime configuration может содержать resolved values, но secret access explicit. Module Context не содержит все secrets автоматически — principle of least privilege: module-specific service получает только необходимые credentials (LLM client получает API credential, menu renderer — нет). Secrets никогда не попадают в logs.

80. Модули никогда не общаются друг с другом напрямую. Module A не читает configuration module B и не читает его данные: Cinema не читает config('mafia.*'); Mafia не читает DB tables Cinema. Нет module-to-module вызовов, импортов internal services, repositories, Eloquent models других модулей. Любая интеграция проходит только через platform, которая предоставляет public contracts / capabilities / service interfaces. Public module contract: commands, capabilities, resources, events, service interfaces. Module API минимальна; internal services, internal repositories, internal Eloquent models не экспортируются и не являются public integration API.

81. Runtime Context не превращается в Service Locator. Не делать $context->get('anything'); лучше typed properties, typed context objects, explicit services. Context может содержать BotContext, ChatContext, ModuleContext, ActorContext — отдельные typed types; ModuleRuntimeContext может их агрегировать, но не предоставляет arbitrary container access. Запрещено $context->container()->make(...). Service resolution остаётся ответственностью DI container; context только описывает operation.

82. Module invocation имеет explicit API: moduleRunner->execute(bot, module, operation), а не module->handleEverything($context). Skill modules не знают весь platform runtime; они получают необходимые dependencies, context, validated configuration.

83. Transport (внешний по отношению к Engine): Telegram integration должна быть scoped. Bot API client использует bot identity / token context. Нельзя, чтобы module handler получал global Telegram client, потенциально указывающий на другой bot. Особенно опасен singleton TelegramBotClient с mutable token — запрещён. Лучше bot-scoped client factory:

TelegramClientFactory
↓
BotContext
↓
client

либо immutable bot-specific client. Engine сам transport не реализует — он потребляет bot-scoped client у внешнего transport layer.

84. Один request может потенциально работать с несколькими bots (например platform admin operation, сравнивающая bot A и bot B). Поэтому assumption "one request = one bot" не встраивается в global state. Но Telegram update обычно имеет один bot context — это operational optimization, не architectural requirement.

85. Menu должно получать BotContext, затем available modules через Engine. Menu item ссылается на module ID + action ID, а не controller class, не hardcoded route, не hardcoded Telegram command. Например: module: cinema, action: search → Menu Engine resolve cinema.search через module resource/action registry. Это позволит: module disabled → menu item disappears. Но deep link не должен обходить availability: если пользователь вручную вызвал cinema.search при disabled module, Engine должен отказать. Hidden UI не является security. То же для Telegram command, Web route, Mini App URL, callback query: все entry points проходят ModuleAvailabilityGuard.

86. Guard должен быть центральным (например EnsureModuleAvailable). Не реализовывать if (!$moduleEnabled) в каждом handler. Guard проверяет: module exists, bot binding, platform state, dependencies, configuration. Authorization может быть следующим guard: ModuleAvailable → Authorized → Handler. Skill handlers не дублируют module availability checks без необходимости.

87. Error taxonomy едина и семантически различна — никогда не сворачивать всё в 403:

MODULE_NOT_ENABLED_FOR_BOT
MODULE_UNAVAILABLE_FOR_BOT
PERMISSION_DENIED
+ отдельные категории dependency failure и configuration failure.

Если actor не authorized — FORBIDDEN; если module unavailable — MODULE_UNAVAILABLE. Не смешивать эти errors. Это важно для Admin UI, Telegram responses, API, logging, metrics.

88. Runtime Context должен быть traceable. Каждая operation может иметь: operation ID, bot ID, module ID, chat ID, actor ID. Но secrets никогда не логируются. Module logs автоматически имеют module_id, bot_id, а при chat operation — chat_id. Реализация — scoped logger context, но logger context должен быть request/job scoped, не process-global. Для long-running worker context обязательно очищается, иначе Bot A log context может попасть в Bot B. Runtime context не протекает между bots.

89. Metrics должны иметь module и bot только если cardinality приемлема; не обязательно every user ID в metric labels — иначе metrics explosion. Recommended labels: module_id, operation, result, maybe bot class/tenant. Высококардинальные данные — в logs/traces. Runtime module resolution должен быть observable, например: module_resolution_total, module_blocked_total, module_execution_total, module_execution_duration. Но observability не должна менять correctness.

90. Runtime module resolution не выполняет side effects. Resolver: reads, computes, returns. Не enable, не disable, не migrate, не seed, не send messages. Это позволяет безопасно использовать его из HTTP, Telegram, CLI, Queue, tests.

91. Runtime Context может быть создан synchronously, asynchronously, from CLI. Поэтому Engine не зависит от HTTP Request; module resolution работает без Laravel HTTP layer. Console command использует те же правила, что Telegram webhook; Admin UI использует same Engine. Таким образом Telegram, Web, Mini App, CLI, Queue используют одну Module Availability model — это один из главных архитектурных invariants.

92. Multi-bot equivalence: один installed module может одновременно работать у разных bots; Bot A может иметь module enabled, Bot B — disabled; разные configuration, разные permissions, разные chats; Chat A и Chat B одного bot могут иметь разные module state. Runtime context resolution не создаёт скрытой зависимости между bots.

93. Package/runtime разделение: module package загружается один раз на application; module runtime state не является package-global state; module singleton не хранит mutable bot-specific state; module services должны быть bot-safe — если service state зависит от bot, он должен быть scoped/factory-created; long-running worker не переиспользует bot-specific mutable service state без корректного scope. Async execution сохраняет explicit bot/module context. Concurrent execution не смешивает module configuration, Telegram tokens, permissions.

Главные инварианты (итог):

Multi-tenancy: архитектура обеспечивает композицию "один установленный plugin/module → множество bots → у каждого bot свой набор подключённых skills" при глобальной физической регистрации PHP-кода; enable/disable, configuration, availability, permissions и runtime context разрешаются на уровне конкретного bot. Это фундаментальный multi-tenant инвариант TelegramModuleEngine.

Scope: scope отвечает исключительно за область существования и действия ресурса, а permission — за право actor выполнить действие. Platform, Tenant, Bot, Chat и User не являются взаимозаменяемыми идентификаторами; каждый scoped resource обязан явно объявлять ownership/scope, а все runtime, queue, admin и Telegram operations должны передавать scope context явно и никогда не полагаться на глобальный current bot/tenant.

Isolation: runtime архитектура гарантирует полную изоляцию Bot A и Bot B при одном установленном наборе PHP-модулей: Engine единожды знает, что существует, а для каждой конкретной операции отдельно и детерминированно разрешает bot → module → capability → configuration → permission, не используя глобальный mutable context и не позволяя одному bot случайно исполнить skill, конфигурацию, permission или transport operation другого bot.

Authorization: ни один module не должен предполагать, что tenant_id, bot_id, chat_id или telegram_user_id сами по себе являются достаточной авторизацией; scope определяет объект действия, authorization (внешний access module) определяет право действия, а Engine связывает эти два измерения через единый AuthorizationContext, передавая access module только opaque actor/chat IDs и scope levels.
