41 — Module Discovery, Registration & Manifest
1. Назначение

Этот документ определяет, как TelegramModuleEngine узнаёт о существовании модулей, как модуль описывает себя, как registry строится и как исключить из платформы все остаточные foreach, ручные списки и hardcoded ServiceProvider registration.

Главный принцип:

module package
↓
module manifest / definition
↓
TelegramModuleEngine
↓
ModuleRegistry
↓
platform / bot / chat runtime.
2. Discovery ≠ Enablement

Discovery отвечает:

какие modules существуют в установленном application.

Enablement отвечает:

какие modules подключены к конкретному bot.

Это принципиально разные операции.

3. Composer

Composer отвечает только за:

физическую установку PHP package.

Он не должен знать:

какие bots используют module
какие chats используют module
какие permissions выданы.
4. Module package

должен предоставлять machine-readable описание:

ModuleManifest.
5. Manifest

является bridge между package и Engine.

6. Manifest должен содержать минимум:
   module_id
   module version
   module name
   description
   provider
   configuration definition
   dependencies
   capabilities
   resources
   lifecycle policy.
7. Но Manifest

не должен содержать runtime state.

Например нельзя:

enabled = true.
8. enabled

относится к:

BotModuleBinding.
9. Manifest

должен быть immutable.

10. Module package

предоставляет definition,

а Engine

регистрирует её.

11. Registration

должна происходить централизованно.

12. Не:
    foreach modules

13. Не:
    config('telegram.modules').
14. Не:
    hardcoded array

15. Не:

67. Ошибки должны обнаруживаться:

83. Manifest

## Merged from earlier revisions (05, 18, 23, 54)

- ModuleDescriptor: after discovery each module becomes an immutable ModuleDescriptor combining packageName, packageVersion, definitionProvider and definition. Descriptor is package-owned runtime metadata; descriptor ≠ configuration (config is application-owned; they are joined only at resolution). Discovery must not require a runtime module object, so disabled or broken modules remain visible in the admin catalog. Basic discovery must work without instantiating runtime implementations.
- Discovery lifecycle phases: DISCOVERY → CONFIGURATION → REGISTRATION → BOOT → RUNTIME. Module ServiceProviders are registered by the Engine only for platform-enabled modules, in a valid Laravel bootstrap phase — never `foreach (config('tg_modules')) { app()->register(...) }`. Standard Laravel package auto-discovery must not bypass Engine control of provider activation.
- Manifest parsing safety: the manifest parser must be minimal and safe — no `include` of arbitrary manifest PHP just to read metadata; prefer JSON/YAML with a safe parser or composer extra; no eval, callback strings or executable PHP in the manifest (reduces supply-chain risk; metadata may be consumed before activation). All manifest paths (migrations, translations, views, assets, config schemas) must be package-relative, validated and canonicalized; resource loaders must reject `../` path traversal and keep asset paths package-root bounded. Signature/integrity/publisher fields may be reserved for a future trusted-plugin registry, but cryptographic signing is not MVP.
- Failure policy: a manifest/definition failure must never partially register a module. Module metadata carries a failure policy: OPTIONAL vs REQUIRED_PLATFORM. A broken optional module becomes INVALID — diagnosable, other modules continue, boot survives. A required platform component may fail boot. Only allowlisted/core packages may declare REQUIRED_PLATFORM; otherwise a malicious or broken plugin could block the entire platform.
- MISSING_CODE and reconciliation: removing a package from Composer must not purge database data. Persisted bindings/configuration enter a MISSING_CODE diagnostic state ("module code unavailable, bindings/configuration exist"); reinstall/restore is possible, and only explicit purge deletes data. An InstallationReconciler compares discovered package state against persisted installation state (installed_version), surfacing pending upgrades instead of silently trusting either Composer or DB as truth. Module removal detection never triggers automatic uninstall semantics.
- Typed resource descriptors: migrations, seeders, routes, commands, views, translations and frontend assets are declared as typed descriptors (MigrationResource, SeederResource, RouteResource, FrontendResource, ...), not arbitrary arrays. Registering a seeder ≠ executing it: seed execution happens through the module installation/provisioning lifecycle (`tg:modules:seed --module=...`, `tg:bot:module:provision`), never during provider boot.
- Install ≠ enable security boundary: a Composer-installed but unconfigured module is DISCOVERED / NOT ENABLED by default (autoEnable = false in production). Installing a third-party package must not silently grant routes, commands, handlers, permissions, menu entries or background workers; an administrator enables it explicitly. Definition and provider loading must not require the DI container (no `app()->make()` during discovery) to avoid circular bootstrap.
- Module ID format and identity checks: strict machine-readable format (e.g. `^[a-z][a-z0-9-]*$`), no namespace notation, no display names. manifest.id === definition.id is validated; mismatch is a fatal discovery error. Two packages sharing one Definition class is also diagnosed. Renaming a module ID is a migration-level operation.
- Module surfaces (optional descriptor metadata): TELEGRAM / WEB / ADMIN / MINI_APP / CLI / WORKER / MENU. Surfaces help Admin UI and diagnostics, but a surface is never a permission. The Engine must not assume every module is a Telegram handler.
- Registry cache/fingerprint: cache is derived data keyed by a fingerprint of installed module IDs, versions and manifest versions; source of truth stays installed packages + manifests. Compiled registry may be exposed via `tg:modules:cache` / `tg:modules:clear`; CLI, web and queue share the same registry — no separate CLI discovery mechanism.
