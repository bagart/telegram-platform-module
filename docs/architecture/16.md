16 — Module Capabilities, Contracts, Dependencies & Extension Points
1. Назначение

Этот документ фиксирует, что именно module может подключить к Telegram Bot Platform, через какие контракты это происходит и как устроена система зависимостей между modules и внешними capabilities. Необходимо различать: module dependency, capability dependency, provider, implementation, optional dependency, version constraint, runtime availability, policy availability.

Главная цель — не превратить TelegramModuleEngine в ещё один огромный framework. Engine должен предоставлять маленький стабильный набор контрактов, а конкретные modules должны расширять платформу через них. Цель системы зависимостей — чтобы module зависел не от конкретной реализации без необходимости, а от формального capability contract.

2. Основная модель

Module — это не просто ServiceProvider. Module представляет собой пакет: Module Definition + Resources + Capabilities + Configuration + Runtime handlers + optional UI contributions.

3. Module должен быть composable

Например, Mafia может использовать: Telegram events, Menu, permissions, bot settings, group context, admin UI. А Proxy может использовать: HTTP services, admin UI, scheduled jobs — и вообще не использовать Telegram Bot API.

4. Поэтому Engine не должен считать, что: module = Telegram handler.

5. Module Capability

Capability отвечает: что module умеет предоставлять платформе?

Например:

telegram.handler
menu.contribution
admin.page
bot.settings
group.settings
scheduled.task
command
webhook
event.listener

6. Capability ≠ Resource

Resource — что нужно зарегистрировать. Capability — какую возможность предоставляет module.

Например, Mafia может иметь:

Resource: MafiaServiceProvider.
Capabilities: bot.settings, menu, admin, telegram.commands, telegram.handlers.

7. Capability ID и typed descriptors

Для внутренних API лучше typed descriptors. Но module ID и capability ID должны быть стабильными строками. Например: mafia, mafia.menu, mafia.admin, mafia.bot-settings; llm.text-generation, storage.object, telegram.bot-api, search.fulltext, proxy.http-client.

8. Capability Registry

Engine должен иметь ModuleCapabilityRegistry. Registry позволяет: find capability, list capabilities, check availability, resolve owner module. Но Registry не должен выполнять capability.

9. Capability executor — ответственность конкретной subsystem. Например: Menu → MenuCapabilityHandler.

10. Поэтому: Engine = registry, а не Engine = universal executor.

11. Core capability types

Для первой версии достаточно: BotHandler, BotSettings, MenuContribution, AdminResource, Permission, Command, EventSubscriber, ScheduledTask, FrontendResource.

Можно добавить Webhook, API endpoint, Widget, Notification provider — но не нужно делать их частью обязательного v1 contract.

12. Bot Handler

Module может предоставить handler для Telegram updates. Handler должен быть bot-aware: он получает BotContext. Handler не должен получать arbitrary HTTP request, если это Telegram update.

13. Context

Должен содержать минимально: bot, tenant, update, module snapshot. Но не делать giant Context.

14. Module handler проверяет module effective state. Лучше: runtime dispatcher сам фильтрует disabled modules. Тогда handler может предполагать module active. Но defense-in-depth: критичные operations могут дополнительно проверить state.

15. Bot settings capability

Module объявляет BotSettingsDefinition. Definition содержит: DTO type, schema, defaults, version. Engine хранит metadata. Actual settings хранятся через BotModuleRepository.

16. Menu capability

Module объявляет MenuContributionDefinition. Menu module получает только contributions. Не позволять module напрямую изменять Menu DB.

17. Admin capability

Module объявляет AdminResourceDefinition. Management получает metadata. Module может предоставить: settings page, dashboard, diagnostics, bot configuration, platform configuration.

18. Scope: каждый admin resource имеет PLATFORM или BOT. В будущем: GROUP.

19. Permission capability

Module объявляет permission definitions. Например: mafia.play, mafia.admin, mafia.settings.view, mafia.settings.edit. Engine регистрирует definitions. Authorization subsystem хранит grants. Не делать Engine permission manager — разрешение permission остаётся во внешней подсистеме authorization.

20. Command capability

Module может объявить Telegram command, например /play.

Command descriptor должен включать: command, moduleId, handler, scope, priority.

21. Collision

Если два modules объявили /play, Engine должен обнаружить конфликт. Возможны aliases (например /game, /mafia), но aliases тоже должны проходить conflict validation.

22. Command priority: можно разрешить explicit priority, но не использовать priority как способ скрытого overwrite. Если collision — по умолчанию ERROR.

23. Event capability

Module может подписаться на: BotCreated, TelegramUpdateReceived, BotModuleEnabled, GroupCreated и т.д. Event subscriptions декларируются module.

24. Не использовать dynamic Event::listen('*') без explicit declaration. Почему: wildcard listeners плохо диагностируются, сложно оптимизируются, опасны для third-party modules.

25. Scheduled task

Module может объявить schedule. Task descriptor, например: id, schedule, handler, timezone policy, overlap policy. Но Scheduler остаётся Laravel/application subsystem. Engine только предоставляет metadata.

26. Frontend capability

Module может предоставлять: React page, components, assets. Frontend resource должен иметь: moduleId, entrypoint, chunk, version. Не передавать PHP class name во frontend.

27. Backend/frontend contract

Module может публиковать: route name, API contract, permissions, UI schema. Но frontend не должен знать DB.

28. API capability

Если module предоставляет API, API resource должен иметь: scope, permission, route, handler. Engine не должен становиться API gateway. Management/API subsystem регистрирует endpoint.

29. Webhook capability

Можно предусмотреть ModuleWebhookDefinition. Например, внешняя система вызывает /api/modules/foo/webhook. Authentication должна быть отдельным contract. Module не должен самостоятельно читать Authorization header, если platform gateway уже обработал его.

30. Module lifecycle hooks

Нужны hooks: onPlatformEnable, onPlatformDisable, onBotEnable, onBotDisable, onBotDelete. Но не делать их обязательными: например, простому module не нужен onBotEnable.

31. Hook должен быть explicit contract: BotModuleLifecycleHandler. Это лучше, чем if (method_exists($module, ...)).

32. Hook execution — через lifecycle manager. Не выполнять hooks внутри Resolver; Resolver должен быть read-only. Это важный принцип: Resolver — READ, Manager — WRITE, Lifecycle — SIDE EFFECTS.

33. Capability discovery

При startup Engine строит Capability Registry из Module Definitions. Registry immutable после bootstrap. Это даёт deterministic application.

34. Runtime modules не могут зарегистрировать новые capabilities на лету. Почему: иначе cache, workers, frontend, admin начнут видеть разные module topology. Plugin installation изменяет topology только через deployment, restart/rebootstrap. Dynamic bot activation не изменяет topology.

35. Это ключевой distinction: module topology = application lifecycle; bot activation = runtime/tenant lifecycle.

36. Capability availability

Например: Menu capability exists, но Mafia menu contribution disabled for Bot A. Поэтому capability registry не отвечает "can this user use it?" — это Resolver + Authorization.

37. Capability resolution

Получаем: Capability exists → Module platform-enabled → Bot module enabled → permission → capability available. Но capability itself не хранит bot state. Capability descriptor immutable.

38. Module API

Рекомендуется дать module один основной composition point: TelegramModuleDefinition.

Conceptual structure:

TelegramModuleDefinition(
id,
name,
version,
dependencies,
resources,
capabilities,
configuration,
)

Но Definition не должен превращаться в 100-parameter constructor. Для этого resources и capabilities могут быть typed collections. Configuration — отдельный descriptor.

39. Example conceptual structure

Definition
├── Identity
├── Dependencies
├── Resources
├── Capabilities
└── Configuration

40. Identity

Содержит: id, name, version. id — строгий immutable identifier; не менять ID после публикации module. Name может меняться. Version — module-defined compatibility version. Description — UI metadata.

41. Dependencies, Capabilities, Resources — typed descriptors. Configuration — schema + defaults.

42. Service Provider

Не обязательно часть public Definition API. Он может быть Resource: ServiceProviderResource. Это делает модель единообразной.

43. Но есть нюанс: Laravel package discovery обычно работает через Composer. Engine не должен заставлять каждый package вручную прописывать config/app.php. Поэтому module package должен иметь composer extra metadata или Engine-specific discovery mechanism. Однако не дублировать Definition в JSON и PHP.

44. Рекомендация: Composer metadata только указывает DefinitionProvider class. Например conceptually:

bagart/telegram-bot-module-mafia
↓
TelegramModuleDefinitionProvider
↓
Definition

45. Provider возвращает immutable Definition. Provider не делает: DB, HTTP, filesystem mutation, migrations, registration side effects. Только declaration. Это позволяет Engine: discover, validate, cache.

46. Definition cache

В production можно кешировать compiled registry, например bootstrap/cache/tg_modules.php. Но generated cache не должен становиться source of truth. Source: Composer + package definitions + tg_modules.php. Cache — compiled artifact.

47. Cache invalidation — после: composer install/update, config change, module package change. Artisan: tg:modules:cache, tg:modules:clear. Application boot может автоматически использовать compiled registry. Development может discovery без cache; production — лучше compiled.

48. Module contract version

Engine API будет развиваться. Definition должна указывать engineApiVersion или compatibility range, например engine >= 1.0 < 2.0. Это отдельно от module version.

49. Если module incompatible — Engine должен fail: MODULE_ENGINE_VERSION_UNSUPPORTED. Не пытаться запустить module partial.

50. Capability versioning

Не все capability changes backward-compatible. Например: menu.v1, menu.v2. Но не плодить версии без необходимости. Лучше capability contract version: capabilityVersion. Engine validates compatibility.

51. Capability Contract

Определяет: interface, version, required operations, compatibility.

52. Три типа зависимостей

Dependency contract имеет три вида, и они никогда не смешиваются: module dependency, capability dependency, infrastructure requirement.

53. Главный принцип

Зависимость должна описываться как «потребителю нужна capability X», а не обязательно «потребителю нужен module Y».

Например, Cinema module может требовать TextGeneration. Он не обязан знать OpenAI, Ollama, local LLM или другой provider. Provider Resolver выбирает конкретную реализацию.

54. Module dependency используется только когда конкретный module действительно необходим. Например, mafia-ui может зависеть от mafia-engine.

55. Capability dependency предпочтительнее для services, providers, integrations, infrastructure.

56. Infrastructure requirement

Третий вид edge — требование к окружению: Redis, queue, filesystem, LLM runtime. Это отдельный contract (InfrastructureRequirement). Module dependency, capability dependency и infrastructure requirement — три типа зависимостей, которые не смешиваются. Предпочитать capability dependency там, где есть абстракция: llm.text-generation вместо Ollama; distributed lock вместо Redis.

57. Provider

Объявляет provides capability X. Например: OllamaProvider provides llm.text-generation; другой — OpenAIProvider provides llm.text-generation.

Consumer видит TextGenerationInterface. Consumer не получает OpenAI SDK object, если это не требуется contract.

58. Capability vs module dependency

Поддерживаются оба: requiresModule и requiresCapability — это заложено в архитектуру сразу. Capability graph не заменяет module dependency graph: module dependency точнее для конкретной implementation dependency; capability dependency абстрактнее.

59. Например, две разные menu implementations. Плохо: requires: telegram-platform-menu. Лучше концептуально: requires capability telegram.menu. Но если нужен конкретный implementation — hard module dependency. Это позволяет альтернативные implementations.

60. Capability provider: Engine может определить, who provides telegram.menu.

61. Conflict: если два modules одновременно предоставляют exclusive capability — ERROR, если нет explicit selection.

62. Capability conflicts: module может объявить conflictsCapability, если несовместим. Например, две реализации одного exclusive scheduler.

63. PROVIDES / CONSUMES

Capability types можно разделить на PROVIDES и CONSUMES. Например Mafia: CONSUMES telegram.menu, CONSUMES authorization, PROVIDES mafia.game. Это формирует dependency graph.

64. Management UI может показать: Provides: telegram.menu; Requires: authorization; Optional: admin.ui. Это сильно улучшит диагностическую часть админки.

65. Dependency Graph

Должен быть explicit. Узлы: modules, capabilities, providers. Рёбра: requires, optionally_requires, provides, conflicts, enhances.

Например: Module A requires Capability X, provided by Provider B.

66. Graph должен быть directed. Cycle detection обязателен. Например A → B → C → A — такой graph INVALID.

67. Но provider relationships не должны создавать искусственный цикл. Dependency graph должен различать dependency edge и provider selection edge. Иначе capability provider может ошибочно создавать dependency cycle.

68. Static vs effective graph

StaticDependencyGraph строится из manifests/contracts в момент discovery — immutable, global, ровно один экземпляр. EffectiveDependencyGraph — scoped view per tenant/bot, вычисляется поверх static graph с учётом policy, configuration, health и provider selection; может меняться в runtime без пересборки static graph.

Три вопроса остаются отдельными ответственностями: graph отвечает "can the requirement be satisfied?"; resolver — "by whom (which provider)?"; selector — "which implementation?".

69. Static graph errors — cycle, duplicate exclusive capability, invalid declaration — boot/configuration errors. Per-bot unsatisfied requirements дают только blocked/degraded effective state с сохранением desired binding.

70. Effective graph

Module enabled не значит all optional dependencies active. Effective graph строится из: desired state, policy, configuration, scope, provider availability.

71. Module dependency имеет: module ID, version constraint, required/optional, activation requirement.

72. Version constraint должен быть explicit. Например >=2.1 <3.0. Не latest. Для production floating latest нежелателен.

73. Capability version также имеет compatibility contract. Provider может поддерживать capability v2; consumer требует ^2.0; resolver проверяет compatibility.

74. Если provider не подходит — dependency blocked. Не runtime fatal error при первом вызове.

75. Dependency resolution должна происходить до activation. Исключение — explicitly lazy optional dependency.

76. Optional dependency

Не должна блокировать основной module. Например, analytics provider optional: provider unavailable → module remains ACTIVE, но capability unavailable. Это должно быть observable.

77. Required capability: если отсутствует — module BLOCKED.

78. Capability scoping

Каждый capability definition и capability requirement несёт typed scope: PLATFORM / BOT / CHAT|GROUP / USER. Global existence of a capability недостаточна — Engine проверяет, что provider активен для требуемого scope. Например, Mafia requires telegram.menu с scope=BOT — должно быть satisfied для конкретного bot.

79. Effective capability

Effective capability = module available AND bot binding enabled AND scope binding enabled AND authorized.

Эти проверки остаются раздельными, чтобы error codes были точными: MODULE_NOT_AVAILABLE vs PERMISSION_DENIED. PERMISSION_DENIED — результат authorization, а не capability state: capability остаётся AVAILABLE, если не проходит только permission. Это предотвращает путаницу в Admin UI между "unavailable" и "not allowed".

80. Scope leakage

Provider должен объявлять supported scopes. Нельзя inject bot-scoped provider в platform-scoped singleton — это предотвращает scope leakage.

81. Dependency Injection должен учитывать dependency scope. Например, platform singleton не может зависеть напрямую от chat-scoped service. Это должно обнаруживаться на validation time. Иначе — hidden state leak.

82. Provider selection

Должен учитывать: priority, health, compatibility, policy, configuration, scope, cost/limits, availability.

83. Priority не должен обходить policy. Например: Provider A priority 100, Provider B priority 10; policy: A forbidden; resolver: B. Если B отсутствует — capability unavailable. Не silently use forbidden A.

84. Provider selection может быть STATIC, DYNAMIC, HYBRID. STATIC: explicit provider. DYNAMIC: resolver selects provider. HYBRID: preferred provider + fallback providers.

85. Fallback должен быть explicit. Не "try every provider".

86. Provider binding scoped (PLATFORM/TENANT/BOT) и deterministic. Collision нескольких providers для одного exclusive capability/scope — explicit error. Silent first-provider-wins запрещён.

87. Provider selection должен быть deterministic при одинаковом configuration, health, policy, candidates.

88. Если используется weighted selection — seed/strategy должны быть explicit.

89. Provider lifecycle

Также определяется. Например: STATIC, LAZY, PER_REQUEST, PER_OPERATION, LONG_RUNNING. Provider не должен автоматически create long-running process, если contract этого не требует. Provider initialization может быть lazy, но capability availability может проверяться preflight.

90. Provider health

Health отдельна от provider registration. Registered provider может быть unhealthy. Resolver не должен выбирать unhealthy provider, если healthy alternative существует.

91. Health policy должна быть explicit. Например: REQUIRED_HEALTHY, ALLOW_DEGRADED, IGNORE_HEALTH.

92. Provider errors

Должны классифицироваться: transient, permanent, quota, auth, policy, timeout.

93. Resolver может применять fallback только для eligible error classes. Например, provider timeout может trigger fallback, но invalid user input — не должен.

94. Policy denied не должен превращаться в automatic fallback, если fallback тоже запрещён.

95. Authentication failure может быть provider unavailable, но требует diagnostic.

96. Quota exceeded может temporarily block provider.

97. Circuit breaker

Resolver может использовать circuit breaker. Circuit breaker должен быть scoped, например provider + tenant. Не один global breaker для всех tenants — иначе one tenant outage ломает остальных.

98. Provider cache

Должен учитывать: scope, policy, configuration revision, provider health revision. Нельзя cache provider choice forever. Provider choice должен invalidation при: config change, policy change, provider health change, provider registration change.

99. Capability resolution может быть cached. Но cache не является source of truth.

100. Dependency state

SATISFIED, OPTIONAL_MISSING, BLOCKED, INCOMPATIBLE, UNAVAILABLE, DEGRADED.

Эти состояния должны быть различимы. Missing module и missing provider — не одно и то же. Missing capability и provider unhealthy — тоже разные.

101. Dependency diagnostics

Должны показывать: consumer, dependency, provider, required version, actual version, reason.

Например:

module: summarizer
capability: llm.text-generation
required: >=2
provider: local-ollama
actual: 1
status: INCOMPATIBLE

Это намного лучше, чем "dependency failed".

102. Admin explanation duty

Admin UI обязан объяснять причины блокировки в терминах capability model: "Manage Games — blocked because Play is disabled"; "Summarizer — blocked, no provider for llm.text-generation@2". Diagnostics — machine-readable reason codes (DEPENDENCY_MISSING, DEPENDENCY_DISABLED, INCOMPATIBLE_VERSION, POLICY_DENIED, CONFLICT, ...), доставляемые через единый Engine availability/diagnostic report. UI никогда не пересчитывает dependency graphs сама и показывает только зависимости, релевантные данному scope (Composer-level package dependencies — не Bot Admin noise).

103. Topological ordering

Dependency graph должен поддерживать topological ordering. Например: Core → Storage → Search → Module. Activation: Core, Storage, Search, Module. Deactivation — reverse order. Это должно быть deterministic.

104. Если graph имеет независимые nodes — можно parallelize. Но parallelism не должен нарушать dependency ordering.

105. Activation planner

Создаёт dependency execution plan. Plan содержит: nodes, dependencies, parallel groups, blockers.

106. DependencyResolver делает resolution. Planner активации получает resolved plan. Это сохраняет separation of concerns: DependencyResolver не реализует activation сам — не запускает module resources напрямую, не изменяет desired state, не bypass authorization и policy.

107. Capability injection

Должна быть explicit. Например: TextGenerator $generator. Не Container::make('openai').

108. Module не должен знать provider implementation name, если dependency capability-based.

109. Для optional capability: CapabilityResolver::optional(...). Result: provider instance или null/Unavailable.

110. Лучше использовать CapabilityHandle. Handle может предоставить: availability, provider ID, execute. Но provider ID не должен быть единственным API.

111. Capability contract должен быть typed interface. Например TextGenerationProvider. Provider adapter реализует TextGenerationProvider. Module работает только через interface.

112. External SDK остаётся adapter implementation detail. Это позволяет менять OpenAI → Ollama без изменения module logic.

113. Multiple providers

Capability может иметь multiple providers. Provider может предоставлять multiple capabilities. Но capability contracts должны оставаться независимыми.

114. Один provider не должен объявлять "если используете A, автоматически получите B", если B реально не предоставляется.

115. Composite Provider может объединять A + B. Это должно быть explicit provider composition.

116. Conflicts

Также должны поддерживаться. Например: Module A conflicts with Module B; или Provider X conflicts with Provider Y. Причина может быть: exclusive port, exclusive webhook, incompatible runtime. Conflict должен обнаруживаться до activation. Не runtime collision.

117. Dependency constraints

Могут иметь requires, recommends, conflicts. requires — hard dependency. recommends — optional enhancement. conflicts — incompatible combination.

118. Не путать optional dependency и recommendation. Optional dependency может использоваться, если доступна. Recommendation может влиять на diagnostics/provider selection, но не является dependency.

119. Resolution result

Dependency resolution должна быть deterministic, reproducible, observable. Resolver должен выдавать ResolutionResult.

120. ResolutionResult: satisfied dependencies, selected providers, blocked dependencies, conflicts, warnings, execution order.

121. ResolutionResult может иметь revision. Например dependency_revision = 27.

122. Runtime snapshot может фиксировать dependency revision. Это помогает reproduce incidents.

123. Provider selection также фиксирует provider revision. Например: llm = ollama, provider_revision = 91.

124. Operation логирует: dependency_revision, configuration_revision, policy_revision, provider revision. Это даёт deterministic diagnostics.

125. Security

Dependency system не должен позволять module register arbitrary provider для privileged capability. Например: authentication, secret storage, authorization.

126. Для privileged capabilities нужен capability grant.

127. Module manifest может объявить requires capability. Но Engine policy решает: allowed or denied.

128. Provider может быть trusted, untrusted, experimental. Untrusted provider не должен автоматически получать privileged capability.

129. Provider isolation

Может требовать отдельный process/container. Особенно: external CLI, binary, network-facing service. Это согласуется с общей architecture: PHP module и isolated external worker/service.

130. Capability Adapter может общаться: HTTP, Unix socket, CLI wrapper, queue. Но module видит только typed capability contract.

131. Failure внешнего provider не должен crash Module Engine.

132. Provider adapter переводит transport failure в platform error taxonomy.

133. Capability Resolver решает: fallback / block / retry. Это предотвращает provider-specific exception leakage.

134. Diagnostics access

Dependency graph должен быть доступен Admin diagnostics. UI показывает: module, dependencies, providers, versions, state, blockers.

135. Можно визуализировать dependency graph. Но граф не является source of truth. Source: persisted definitions, provider registrations, effective policy/configuration.

136. Module graph visualization

В будущем Management может показать: Mafia → Menu → Telegram WebApp; и Mafia → Authorization. Но граф должен быть machine-generated из Definition. Не поддерживать отдельную документацию вручную.

137. Module health

Каждый module может иметь diagnostics provider. Например MafiaDiagnostics возвращает: database OK, scheduler OK, configuration OK. Engine contract: ModuleDiagnosticsProvider.

138. Но diagnostics не должны влиять на effective state автоматически. Например warning не означает disabled. Только declared critical checks могут block readiness.

139. Health vs readiness: разделять Health, Readiness, Activation. Это важно для production.

140. Module observability

Engine может автоматически добавлять module, bot, capability к telemetry context. Например metric telegram.module.handler.duration с labels module=mafia, bot=123.

141. Но осторожно с bot IDs: не допускать high-cardinality metrics без policy. Лучше module + operation, а bot ID — logs/traces.

142. Error attribution

Любая ошибка module должна иметь moduleId. Engine может предоставлять ModuleExceptionContext. Не оборачивать все exceptions в generic exception — иначе теряется original type. Использовать previous exception.

143. Module API boundaries

Public API Engine должен быть минимальным. Рекомендуемый набор: ModuleRegistry, ResourceRegistry, CapabilityRegistry, ModuleResolver, BotModuleManager, ModuleConfiguration, ModuleDiagnostics.

144. Всё остальное — internal. Не делать public: internal caches, storage implementations, compiled registry format, Laravel adapters. Это позволит менять реализацию без BC break.

145. Versioning

Public contracts должны иметь semantic versioning. Breaking change (например изменение Definition contract) → major. Добавление optional capability → minor. Исправление validation → patch.

146. Module package должен зависеть от telegram-module-engine с compatible constraint. Engine не должен зависеть от конкретных skill modules.

147. Dependency direction

Правильно:

148. Telegram Bot Lib: telegram-bot-lib тоже должен оставаться независимым. Engine может иметь optional integration (Telegram runtime adapter), но core Engine не должен требовать Telegram API client. Это особенно важно для admin-only, infrastructure и background modules.

149. Поэтому package architecture лучше: telegram-module-engine — Core, Laravel, optional Telegram integration. Возможно разделение BAGArt\TelegramModuleEngine и BAGArt\TelegramModuleEngine\Laravel. Но не дробить package слишком рано. Главное — namespace boundaries.

151. Что получает конкретный skill module

Он может сказать: я — mafia. Мне нужен authorization. Я опционально использую telegram.menu. Я предоставляю mafia.game. Я регистрирую commands, handlers, menu, admin, settings, permissions. И больше ничего не должен прописывать в платформе.

152. Что получает платформа

Платформа говорит только TelegramModuleEngine — и больше не знает Mafia, Cinema, Proxy, AntiSpam, Summarizer, Basic.

153. Что получает Management

Он может автоматически построить из Registry + Resolver: Installed Modules, Available Modules, Bot Modules, Dependencies, Capabilities, Settings, Permissions, Menu contributions, Diagnostics.

154. Что получает Menu: enabled menu contributions для конкретного bot + user context.

155. Что получает runtime: active module handlers для конкретного bot.

156. Самое важное архитектурное решение

Не делать TelegramModuleEngine "системой, которая знает всё о modules". Он должен быть типизированным composition/registry layer между package modules и platform subsystems.

158. Главный инвариант зависимостей

Module должен зависеть прежде всего от capability contract, а не от конкретной реализации. DependencyResolver строит effective dependency graph с учётом version constraints, scope, policy, configuration и provider health; выбирает допустимые providers и формирует deterministic ResolutionResult. Module получает typed capability interface/handle, а конкретный provider и его transport остаются implementation detail. Планировщик активации использует готовый dependency plan, но graph resolution остаётся ответственностью DependencyResolver.

160. Итоговая цепочка

Итоговая архитектура должна обеспечивать цепочку: Consumer → Capability Contract → DependencyResolver → Eligible Provider → Capability Adapter, при этом конкретные provider implementations, SDK, HTTP/CLI transport и внешние процессы остаются за пределами module domain. Graph resolution, provider selection и policy evaluation являются отдельными ответственностями; результатом dependency subsystem является versioned, deterministic и observable ResolutionResult, который используется для безопасной активации runtime.
