33 — Вклады и ресурсы модулей: типизированный каталог, scope-модель, жизненный цикл, реестр

Часть 1. Назначение и главные принципы

1.1. Проблема

До сих пор у нас есть:

ModuleDefinition
Module Registry Capability Registry Bot Module Binding Configuration Resolver Effective Configuration

Следующий архитектурный разрыв — ресурсы module.

Именно здесь сейчас возникает хаос:

foreach (config('telegram.modules_seeders', []))

плюс аналогичные:

foreach (config('telegram.modules_migrations', []) ...) foreach (config('telegram.modules_providers', []) ...) foreach (config('telegram.modules_routes', []) ...) foreach (config('telegram.modules_commands', []) ...)

явные ServiceProvider отдельные migration paths ручные frontend resources ручные menu registrations ручные permission registrations отдельные bootstrap calls.

Нужно полностью убрать эту модель.

1.2. Главный принцип

Module объявляет:

какие ресурсы он предоставляет платформе.

Engine (TelegramModuleEngine) определяет:

где эти ресурсы находятся когда они доступны к какому scope относятся какие lifecycle requirements имеют как их зарегистрировать и в каком порядке.

Laravel integration выполняет:

конкретное framework action.

Platform потребляет:

registry.

Module не должен знать, где и как платформа запускает его resources. Platform не должна знать:

какие seeders есть у Mafia какие migrations есть у Summarizer какой route provider нужен Cinema какие frontend resources нужны Menu какие permissions нужны Proxy Operations.

Вместо ручных списков:

Module Definition
↓
Resource Registry
↓
Laravel integration
↓
соответствующий framework mechanism

1.3. Resource — это декларация

Resource — это не обязательно файл.

Resource — это декларативно зарегистрированный элемент интеграции module с host platform.

Важное разделение:

Definition declares. Engine executes.

Platform просто:

discovers
validates
registers
executes.

1.4. Resource ≠ Runtime Activation

Это принципиально.

Resource registration и bot activation — разные lifecycle.

Например, module Mafia может быть:

установлен
platform-enabled
bot-disabled

но его:

migrations
routes
service provider

могут существовать в application.

Почему routes существуют при disabled module:

Laravel route table — application-level infrastructure. Она не должна пересобираться для каждого bot.

Runtime доступность:

Route handler уже проверяет module effective state относительно текущего bot/context.

Аналогично commands:

Laravel command зарегистрирована один раз. Команда при выполнении получает bot/context, если она bot-scoped.

1.5. Engine не заменяет Laravel

Самое важное архитектурное решение:

TelegramModuleEngine не должен пытаться заменить Laravel.

Он не создаёт собственные:

router; migration engine; scheduler; event dispatcher; container; frontend bundler.

Он создаёт единый module resource registry и adapters, через которые существующая Laravel infrastructure получает declarative resources modules.

Это сохраняет Laravel естественным, но полностью убирает module topology из платформенного business/application code.

Дополнительные жёсткие границы Engine:

Registry stays a catalog: он говорит WHAT should exist; специализированные менеджеры (dispatcher, router, scheduler, queue) говорят HOW it runs. Registry никогда сам не отправляет Telegram messages, не выполняет HTTP requests и не запускает jobs. Engine вообще не делает Telegram transport calls — обмен с Telegram выполняется вне Engine; в ресурсных контрактах используется только типизированный словарь ключей (BindingKey vocabulary). Routing table диспетчера строится на control path и хранится в PostgreSQL; Engine — «dumb dispatcher proxy» поверх неё, никакой K8s-подобной reconciliation machinery (desired/observed loops, fencing tokens, drain policies, tombstones) в Engine нет — эта механика была решена OUT. Permission system — внешняя subsystem; Engine только регистрирует permission definitions, но не хранит и не вычисляет grants.

2.2. Нет гигантского DTO — есть typed descriptors

Не делать один giant TelegramModuleResource с 50–100 nullable полями.

Лучше иметь typed resource descriptors:

TelegramModuleMigrationResource
TelegramModuleSeederResource
TelegramModuleRouteResource
TelegramModuleCommandResource
TelegramModuleFrontendResource
TelegramModuleMenuResource
TelegramModulePermissionResource
TelegramModuleAdminResource
...

Все они реализуют общий marker contract: TelegramModuleResource.

Общая metadata (минимальный contract):

id
type
moduleId
metadata
плюс: phase, scope, priority.

Конкретный resource descriptor содержит только необходимые ему свойства.

Это сохраняет:

strong typing IDE support static analysis отсутствие magic arrays.

Descriptor — data. Executor — behavior.

Resource descriptor не должен сам:

register() execute() save()

Это соответствует общей философии проекта:

Configuration DTO = data Definition = metadata Application services = behavior.

Resource descriptors immutable, как и остальные Engine DTO.

2.3. ResourceIdentity и BindingKey

Два различных идентификатора у ресурса:

ResourceIdentity — уникальный внутренний идентификатор ресурса:

формат `{moduleId}.{resourceType}.{localId}` или `{moduleId}.{localId}` например: bagart.mafia.command.play, mafia.migrations, mafia.routes, mafia.admin, mafia.frontend stable, никогда не random UUID как единственная identity не зависит от: абсолютного path vendor path PHP class hash array index.

Это лучше class-name identity. Примеры stable IDs:

mafia.routes.admin
mafia.commands.stats
mafia.menu.main
mafia.admin.settings
summarizer.migrations.create_tables

Это важно для:

diagnostics
ordering
deduplication
audit
upgrades.

BindingKey — внешний dispatch namespace:

например `telegram.command:/start`, `http.route:GET /modules/{module}/...`

Два module могут легитимно объявить ресурсы с коллидирующими BindingKeys (оба претендуют на `/start`).

Это не duplicate resource ID — это duplicate dispatch-key conflict, и он детектируется отдельно.

Default policy: ambiguous binding = explicit error; никогда «last registered wins».

Dispatch policy (priority / conditions / exclusive / fallback) может быть введена позже, но ambiguity должна быть opt-in, не silent.

Route path НЕ является identity (paths могут меняться); resource_id остаётся.

2.4. Владение (ownership) ресурсов

Module resource принадлежит module.

Каждая migration, route, listener, job принадлежит moduleId (ownerModuleId).

Registry хранит:

moduleId
resourceId
type.

Ownership enforcement:

Engine должен запрещать module A регистрировать ресурс в namespace module B (например `mafia.permissions.play`, когда owner — `mafia`). Resource IDs namespaced by moduleId (`{moduleId}.{localId}`) и валидируются (`resourceId startsWith moduleId + '.'`). Platform-owned shared resources — explicit exception.

Это позволит:

diagnostics
admin UI
uninstall
testing
conflict detection.

Reverse lookup: можно спросить

какие resources принадлежат module? кому принадлежит resource X?

Пример diagnostics-вывода:

Mafia
migrations: 4 seeders: 2 routes: 3 frontend: 5.

2.5. Per-type contracts (сохранённая суть)

telegram.command:
command, handler, scope, filters, priority, permissions. Handler никогда не саморегистрируется в dispatcher; регистрацию выполняет resource handler через Engine.

telegram.callback:
explicit, validated, bounded pattern (никаких catch-all `.*` без explicit authorization), decoder contract, handler authorization.

http.route:
method, path, handler, middleware metadata, stable route name, scope. Route path не identity.

http.middleware:
global middleware — привилегированный тип ресурса, требующий explicit capability/permission. Module не должен иметь возможности молча менять глобальный Telegram/HTTP/queue middleware pipeline. То же для глобальных exception handlers.

telegram.menu_item:
stable id, label (translation key), visibility, ordering, permissions, scope; ACTIVE/INACTIVE.

webhook.endpoint:
endpoint, method, handler, authentication mode, replay protection, request/body limits, timeout.

capability.binding:
связывает module с capability/provider/scope; required/optional/preferred; никогда не содержит секретных credentials.

2.6. Валидация схем и версионирование контрактов

Schema validation before registration:

каждый ResourceDefinition валидируется (required fields, types, ranges, enums, formats, cross-field constraints) до того, как попадёт в runtime.
invalid definition → INVALID_DEFINITION, никогда не silent default.

Resource type contracts несут schema version; handlers декларируют поддерживаемые версии; unsupported → INCOMPATIBLE.

2.7. Lazy handler loading с preflight

Registry хранит class references; handlers инстанцируются в dispatch time.

Но preflight обязан проверить:

class exists implements contract dependencies resolvable.

Lazy loading никогда не означает «no validation».

Не передавать closure в descriptor — лучше registrar class из-за serializability/testability.

2.8. Quotas

Resource types могут нести quotas per module/type (max routes, max consumers).
Violation → QUOTA_EXCEEDED.
Platform security limits не могут быть переопределены modules.

2.9. Tags

Resource registry поддерживает tags:

admin
frontend
telegram
database
runtime
security.

Tags не заменяют typed resource. Они нужны для:

filtering
diagnostics
tooling.

2.10. Serialization whitelist

Resource metadata, доступные frontend/admin API, должны проходить serialization whitelist.

Не сериализовать descriptor напрямую: PHP DTO ->jsonSerialize() может случайно раскрыть:

class names filesystem paths internal services.

Для API использовать отдельные presenters/transformers.

Internal descriptor: trusted. Public API: sanitized projection.

Это особенно важно для third-party plugins.

Часть 3. Модель регистрации и активации (scope model)

3.1. Discovery / Registration / Activation

Engine provider не должен автоматически boot everything.

Нужно разделить:

Discovery: какие modules существуют? Registration: какие resources они предоставляют? Activation: какие resources реально включить?

Это предотвращает ситуацию, когда disabled module внезапно регистрирует runtime handlers.

Registration is application-level. Activation is runtime-scoped.

Это должно стать одним из основных правил Engine.

3.2. registrationScope и activationScope

Resource Descriptor должен явно содержать:

registrationScope
activationScope.

Возможные scopes:

PLATFORM
BOT
TENANT
CHAT
USER (для activation-измерения UI; см. ограничение по admin scopes ниже).

Но registration обычно только PLATFORM.

Runtime activation может быть BOT.

Примеры:

RouteResource(
registrationScope: PLATFORM, activationScope: BOT
)

Migration:
registrationScope: PLATFORM activationScope: PLATFORM.

Permission:
registrationScope: PLATFORM activationScope: BOT.

Menu item: registrationScope: PLATFORM activationScope: BOT/CHAT.

Это предотвращает ошибку: «module enabled only for Bot A, поэтому зарегистрируем его PHP routes только для Bot A». Так делать не надо.

Laravel application остаётся единой runtime environment. Module Engine управляет availability.

Не нужно динамически добавлять Laravel routes при каждом включении module для bot — это архитектурно неправильно для Laravel application.

Аналогично commands: command зарегистрирован globally, но handler проверяет module available for current bot.

Menu: menu definition зарегистрирована globally, но effective menu computed per bot.

Permissions: permission definition глобальна. Grants — per bot/tenant/chat/user.

Capabilities: definition глобальна. Effective capabilities — per bot.

Это единое правило для всех типов.

3.3. Activation policy

Resource должен иметь activation policy. Например:

ALWAYS
PLATFORM
BOT
ACTIVE_MODULE
ADMIN_ONLY.

Это более гибко, чем `if enabled`.

Примеры:

обычно disabled module не должен принимать commands; но admin diagnostic command может быть доступен (ADMIN_ONLY); health checks могут быть always registered для diagnostics, потому что Admin должен узнать, why module unavailable.

3.4. Состояние ресурсов и lifecycle-фазы

Resource state нужно различать:

DECLARED
REGISTERED
AVAILABLE
ACTIVE
FAILED
BLOCKED.

Не все resources активируются одинаково:

Migration: declared → discovered → available to Laravel.
Bot command: registered globally, но runtime-active только если module enabled for bot.

У каждого resource есть diagnostic lifecycle (не обязательно хранить state):

discovered
validated
registered
executable.

Каждый resource имеет две независимые фазы:

DECLARE — Module говорит: «У меня есть этот resource». REGISTER — Engine говорит: «Я подключаю этот resource к Laravel». EXECUTE — Application говорит: «Сейчас этот resource можно выполнить».

Разделение declaration/execution phase:

Declaration phase не должна иметь side effects: discovery — local, deterministic, side-effect free. Execution phase: Laravel/application subsystem выполняет declared resources. Migration execution уже может работать с DB; Seeder может использовать DB; runtime resources могут использовать внешние services.

3.5. Global Registry vs Bot Effective Registry

Global Resource Registry и Bot Effective Resource Registry различаются:

Первый: module resources. Второй: resources available for Bot A.

Это аналогично Discovery Registry и Active Runtime Registry.

Architecture:

ModuleDefinition
↓
GlobalResourceRegistry
↓
BotResourceResolver
↓
EffectiveBotResources

Это позволяет:

Admin UI получать modules/resources без hardcoded lists; runtime не загружает всё.

Это ключевой механизм динамической модульности.

Bot binding changes не rebuild global resource registry — они меняют effective bot resource view.

Tenant-isolated cache keys:

global registry cache: `module-registry:{registryVersion}` per-bot effective snapshot: `effective-modules:{botId}:{configurationVersion}:{registryVersion}`.

Никогда не кэшировать effectiveResources(moduleId) без bot/tenant identity — предотвращает «Bot A видит modules Bot B».

Runtime bot enable/disable:

не требует Laravel restart; не требует dynamic route registration; не требует dynamic migration registration; не требует dynamic PHP provider registration.

Effective bot behavior вычисляется поверх глобального resource registry.

3.6. Registry immutability и compilation

Resource registry immutable после bootstrap/compile.

Runtime не должен добавлять arbitrary resources. Это security boundary.

Exception: controlled dynamic registrations через explicit runtime APIs — отдельный механизм.

Compiled/cached registry snapshots разрешены (faster boot, early validation), но cache — derived artifact, не source of truth.

REGISTRY_STALE в production — fail fast; dev mode может auto-rebuild.

Module registry version и resource registry version учитываются при compile/cache; изменение module registry инвалидирует соответствующий plan.

Snapshot может быть cached; cache invalidation — deployment / module discovery change / configuration policy change, только там, где необходимо.

Snapshot читают:

Runtime
Admin
Diagnostics.

User config никогда не может создать resource.

Bot Admin не может добавить route, provider, seeder, migration, capability. Он может только activate/deactivate, configure. User configuration не может менять handler/provider.

Module package — trusted code. Configuration — untrusted data. Resource registry работает только с trusted definitions. Это должно быть явно задокументировано, особенно учитывая, что modules устанавливаются через plugins.

3.7. Resolved module layers

Resolved module layers:

ModuleDefinition
→ ModuleConfig
→ ResolvedModule (internal Engine object: definition + effective configuration + platform state + capabilities + resources)
→ RuntimeModule.

Не передавать config() через приложение; использовать ModuleManager::module('mafia') / registries.

Immutable definition:

после discovery ModuleDefinition никогда не меняется. config/tg_modules.php содержит overrides/enabled state только, никогда replacement definition. Один registration entry point: ModuleRegistrar::register(ModuleDefinition).

Config DTO constraints (для config:cache compatibility):

никаких service container dependencies; только scalars/arrays/enums/DTOs/class strings; constructor держит defaults, types, простые invariants (timeout > 0); сложная валидация — в ModuleConfigValidator, не в DTO.

Configuration changes resource behavior (label, visibility, limits), никогда resource identity/owner. Menu resource ID остаётся `mafia.play` независимо от enabled state.

3.8. Provider policy при disabled module

Module disabled platform-wide:

Resources:
migrations → available
provider → registered according to policy
frontend → built
routes → registered

Runtime: unavailable.

Два варианта provider policy:

A. Provider зарегистрирован для всех installed modules. B. Provider только для platform-enabled modules.

Recommendation: «configured modules only» — module, отсутствующий в tg_modules.php, вообще не входит в platform runtime.

Для enabled=false:

Если enabled=false означает «module intentionally disabled at platform level», лучше не активировать его application wiring, кроме необходимого infrastructure discovery.

Но migrations должны оставаться доступны для уже установленного module.

Поэтому разделить:

Discovery
Infrastructure
Runtime Provider

Migration discovery может работать независимо от runtime provider. Это позволяет: module disabled, но migration rollback/status остаются возможными. Это архитектурно чище.

Bootstrap vs runtime resources:

часть ресурсов регистрируется на application boot (providers, migrations, routes, commands); другие резолвятся per bot/tenant в runtime (menu, permission visibility, admin navigation, bot capabilities).

Никогда не регистрировать Laravel ServiceProvider per bot — provider регистрируется один раз per process, bot activation — runtime.

3.9. Направление зависимостей (hard invariant)

Нужно определить mandatory platform modules и optional skill modules:

TelegramModuleEngine — mandatory. Menu — optional/strongly recommended. Management — optional (несмотря на операционную важность). Basic — optional. Mafia — optional skill.

Dependency direction — жёстко зафиксировать:

Engine не зависит от Menu, Management, Basic. Menu может зависеть от Engine. Management может зависеть от Engine. Basic может зависеть от TelegramBotLib и/или Engine. Telegram Bot Lib не знает Engine и не является его зависимостью.

Иначе получится снова circular architecture.

Resource registration учитывает optional modules:

Если Menu не установлен, Mafia menu contribution может быть unavailable. Но Mafia сам по себе может продолжать работать через commands, capabilities, API.

Поэтому resource dependency: menu contribution requires menu. Но module dependency может не требовать Menu.

Это ещё одна причина разделять module dependency и resource dependency.

3.10. Resource adapters

Resource adapters:

LaravelModuleResourceAdapter
FrontendResourceAdapter
TelegramResourceAdapter.

Engine знает modules, resources, scopes, lifecycle, dependencies, topology — не React, не DB implementations, не детали Telegram Bot API.

MenuResource обрабатывается Menu module; permission declarations — permission subsystem; admin surfaces — Management module.

Engine = orchestration, not god module.


Часть 4. Правила жизненного цикла по типам ресурсов

4.1. Service Provider

Module может объявить provider: MafiaServiceProvider::class.

Provider lifecycle:

регистрируется один раз на application.

Provider НЕ per bot. Никогда:

foreach ($bots as $bot) { registerProvider(...); }

Это архитектурно неверный уровень.

Provider responsibilities — может:

bind services register events register commands register policies register routes

но не должен содержать module activation logic.

Provider существует, если module установлен/configured согласно platform policy.

ServiceProvider rule (зафиксировано):

«ServiceProvider registration is infrastructure registration, not module activation». Provider может быть зарегистрирован, даже если module disabled для всех bots (он несёт bindings, definitions, resource declarations). Но provider boot никогда не делает bot activation, seeding, DB writes, external calls. Никаких `boot(): foreach bots`.

Service Provider не должен быть главным механизмом discovery.

Сейчас Laravel часто работает так:

provider → register() → foreach(...) → resources.

Это и создаёт размазанность.

Новый flow:

config/tg_modules.php
↓
Module Registry
↓
Module Definition
↓
Resource Registry
↓
Laravel integration adapters.

Service Provider остаётся техническим bridge, но не source of truth.

Например TelegramModuleEngineServiceProvider делает:

register module registry register resource registry register lifecycle manager register configuration resolver.

Далее Engine сам подключает resources.

Service provider caveat:

Laravel ServiceProvider сам имеет register()/boot(), и boot потенциально side-effectful. Поэтому module provider должен оставаться thin.

Provider не должен:

выполнять migrations; seed DB; обращаться к external APIs; искать bots; менять module activation.

Provider должен только wiring.

4.2. Migration

Module предоставляет migration resources.

Migration ownership: каждая migration принадлежит moduleId. Например:

migration 2026_01_create_games — owner: mafia.

Migration discovery:

Engine предоставляет Laravel migration integration (MigrationResourceProvider). Module объявляет MigrationResource(path: ...); Engine передаёт path Laravel migration infrastructure. Platform больше не пишет $this->loadMigrationsFrom(...) вручную по модулям.

Migration ordering:

Сначала Engine migrations, затем module migrations. Если Mafia requires Statistics — migration order может учитывать dependency graph.

Но migration dependency не должна автоматически создавать runtime dependency:

«A migration depends on B schema» не означает «A requires B enabled for bot».

Это разные graph types:

Infrastructure dependency graph Runtime module dependency graph

Не смешивать.

Migration scope — explicit:

возможные scopes: PLATFORM, TENANT, BOT, CHAT. Но migration не должна автоматически создавать bot configuration. Database migrations лучше не превращать в arbitrary dependency graph — Laravel уже обеспечивает chronological ordering.

Duplicate migration: Engine должен обнаруживать duplicate migration identifier.

Migration paths: module может предоставлять database/migrations, но Engine должен нормализовать path.

Migration runner:

Laravel migration system сам управляет applied migrations. Engine не должен иметь собственную migration history без специальной причины.
Для migrations Laravel migrations table — source of truth; Engine только отображает migration path → module identity.
Не менять Laravel migration mechanism, не писать собственный migration runner.

4.3. Seeder

Seeders разделяются по назначению.

Platform Seeder используется для:

глобальных справочников default permissions module metadata system configuration.

Bot Provisioning — не seeder: используется BotModuleProvisioner. Аналогично GroupModuleProvisioner, если потребуется.

Почему это важно:

Seeder запускается deployment/admin operation. Provisioner запускается lifecycle конкретной сущности.

Seeder lifecycle-типы — разделить:

INSTALL
DEFAULT (default/data)
DEMO
REPAIR.

Не все seeders должны запускаться автоматически.

Module resource descriptor должен иметь execution policy:

automatic
explicit
disabled.

Migration — почти всегда automatic. Demo seeder — explicit. Repair seeder — explicit/admin.

Это избавляет от ситуации: «подключили module — и внезапно он засеял production данными».

Seeder identity:

stable per-seeder identity (например `mafia.defaults.v1`), а не только PHP class name (classes get renamed). Optional таблица module_resource_runs (provisioning tracking) — только если tracking semantics реально нужны.

Seeder contract:

module может предоставить PlatformSeeder::class.

Engine command:

php artisan tg:modules:seed — Engine собирает platform seeders.

Вместо:

foreach ((array) config('telegram.modules_seeders', []) as $seeder) { $this->call($seeder); }

получается ModuleEngineSeeder, который спрашивает Registry: enabled/installable module seeders.

Принципиально лучше: Laravel DatabaseSeeder не знает ничего о modules.

Не использовать Laravel DatabaseSeeder для module discovery. DatabaseSeeder делегирует Engine:

$this->call(TelegramModuleSeeder::class);

В application остаётся максимум TelegramModuleSeeder, а не список modules.

Seeder scope — explicit: PLATFORM, TENANT, BOT, CHAT. Это решает старую проблему «foreach module seeders».

Engine может выполнить:

$moduleEngine->resources()->seeders()->forScope(...)

SeederExecutionPlan строится заранее:

resources
dependencies
ordering
scope

затем executor. Это позволяет dry-run: modules:seed --dry-run. CLI не должен знать individual seeders.

Idempotency:

Seeders должны быть idempotent, где это возможно. Engine не должен повторно выполнять seeders без необходимости.

Разделение трёх слоёв — не смешивать:

Migration создаёт database structure. Seeder создаёт initial data. Resource Definition описывает platform metadata.

Permissions и seeders:

Permission definitions — registry resources, поэтому seeders не должны вручную создавать permission definitions. Seeder нужен только для default role grants. Например: module declares mafia.play permission; permission system knows it; seeder grants mafia.play to default member role.

4.4. Routes

Module может объявить:

WebRoutes
ApiRoutes
AdminRoutes
TelegramWebhookRoutes
user routes internal routes.

Не смешивать route types: каждый descriptor должен иметь scope/type.

Route scopes:

PLATFORM_ADMIN
BOT_ADMIN
USER
WEBHOOK
INTERNAL.

Это особенно важно для multi-tenant architecture: admin route не означает global admin. Module может иметь platform admin и bot admin. Engine должен знать required scope.

Route ownership: каждый route имеет ownerModuleId.

Name prefix: module routes должны иметь namespace/prefix, например tg.modules.mafia.*. Это предотвращает collisions.

URL prefix: можно рекомендовать /modules/{module}, но не навязывать всем modules.

Bot routes: bot-specific route /bots/{bot}/modules/{module} может быть частью Management architecture. Не создавать route per bot: один route /bots/{bot}/modules/{module} и authorization/context layer.

Route handler при выполнении проверяет module effective state относительно текущего bot/context.

Registration — через Laravel Router: Engine только предоставляет descriptors, не пишет собственный router.

4.5. Commands (Artisan)

Module может объявить MafiaCommand::class.

Command registration — один раз.

Command execution, если команда bot-scoped:

resolve bot
↓
module state
↓
permission
↓
execute

CLI-only module: module может вообще не использовать Telegram. Engine не должен предполагать, что every module has Telegram handlers.

CommandResource описывает:

command name
handler
capability
visibility.

Например /play → mafia.play.

Command resource не должен содержать authorization logic. Authorization идёт через capability/permission pipeline.

Command activation policy:

Engine регистрирует их только если module active или command scope допускает disabled state. Обычно disabled module не должен принимать commands. Но admin diagnostic command может быть доступен.

Registration — через Artisan: Engine только предоставляет descriptors.

4.6. Telegram commands и callbacks

telegram.command / telegram.callback — типизированные ресурсы каталога (см. 2.5).

Dispatch идёт по BindingKey (например `telegram.command:/start`); коллизии BindingKey детектируются отдельно от ResourceIdentity (см. 2.3, 5.3).

Handler никогда не саморегистрируется в dispatcher; Engine/adapter выполняет регистрацию. Routing table диспетчера строится на control path и хранится в PostgreSQL; Engine — dumb dispatcher proxy.

4.7. Event subscribers / listeners

Module может объявить subscribers. Registration — один раз.

Event listeners должны быть module-owned. Laravel auto-discovery лучше не использовать как primary source: Engine должен знать, что listener belongs to module. Это позволит:

diagnostics
disable checks collision checks
observability.

Subscriber runtime: если событие bot-scoped — subscriber получает BotContext и проверяет module state.

Если module disabled globally, его runtime event handlers не должны выполняться. Поэтому listener resource должен иметь module lifecycle guard.

Однако нельзя unregister Laravel event listener per bot. Listener зарегистрирован globally, а event processing проверяет relevant context.

Это снова: registration ≠ activation.

Не отключать Laravel subscriber динамически — unnecessary complexity: один subscriber может обслуживать 100 bots с разными states.

Event filtering: можно использовать ModuleRuntimeGuard. Но guard должен быть единообразным: не каждый module должен писать собственную копию `if (!$bot->moduleEnabled(...))`.

Registration — через Laravel Event Dispatcher.

4.8. Policies и permissions

Module может объявлять policies.

Однако authorization system остаётся внешней subsystem.

Engine только регистрирует:

capability
permission definitions policy metadata.

Permissions resources должны быть зарегистрированы глобально.

Permission tree строится динамически, например:

mafia
├── play
├── manage
└── statistics

Но grants не принадлежат module resources:

Module объявляет permission definitions. Permission system хранит role grants.

Admin UI получает permission definitions через Engine. Это позволит автоматически строить Bot → Permissions → Mafia → Manage.

Capability definitions — resources/registry entries, глобальны; effective capabilities вычисляются per bot. Permission grants вычисляются per bot/tenant/chat/user.

Command / route / menu / admin resources могут ссылаться на capabilities.

4.9. Translations

Module может иметь lang/.

Translation registration: Laravel integration добавляет namespace moduleId.

Не смешивать module translations в global resources/lang.

4.10. Frontend resources

Каждый module может предоставлять:

JS/TS
CSS
icons
pages
components.

Module должен объявлять:

entrypoint
route/base path
assets
chunk name
dependencies
visibility.

Platform не должна иметь resources/js/modules/mafia.js в общем hardcoded manifest.

Frontend build должен получать module registry.

Разделить:

build-time discovery runtime bot availability.

Все frontend chunks могут быть собраны глобально (все installed modules могут попасть в общий build). Bot-specific filtering происходит после build.

Не надо перестраивать Vite при каждом включении module у bot — это ключевой принцип.

Frontend Resource может содержать:

id
entry
chunk
routes
permissions
menu bindings.

Admin UI получает module metadata через API, затем lazy-load module frontend chunk.

Это позволяет: platform with 100 modules, но Bot A загружает только 7 relevant chunks. Поэтому frontend resources должны поддерживать lazy loading.

Module frontend manifest: Engine генерирует descriptor:

moduleId
chunks
entrypoints
capabilities.

Admin frontend: Management получает только allowed module resources.

Security:

Frontend hiding не является security boundary. Backend authorization остаётся обязательной. Frontend не должен доверять title из module config — лучше translation key (например modules.summarizer.admin.title). Это защищает от untrusted dynamic HTML/text. Frontend получает structured resource descriptor, не arbitrary HTML. Plugin — potentially untrusted code; registry не должен разрешать arbitrary JS injection. Frontend asset должен быть declared module asset (например manifest reference). Engine не должен принимать raw `<script>`; frontend загружает known asset entrypoint.

Build-time — Resource Registry; runtime — module snapshot. Frontend integration использует существующий Vite/build system; Engine генерирует manifest (ModuleFrontendManifest).

4.11. Menu resources

Menu module должен получать contributions от Engine.

Module contribution, например Mafia: menu.main.

Contribution descriptor (MenuContribution) содержит:

contributionId
moduleId
location
label
icon
route/action
ordering
requiredPermission
плюс: translation key для label, visibility, permissions, scope; ACTIVE/INACTIVE.

Разделение ответственности:

Engine отвечает за: discovery, filtering, contribution ownership. Menu module отвечает за: tree, navigation, rendering, Telegram WebApp UI. Engine не должен рендерить menu.

Mafia не должен напрямую импортировать TelegramBotMenu implementation. Лучше MenuResource / MenuContribution: Engine знает, что module provides menu contribution. Menu module может зависеть от TelegramModuleEngine.

Menu registry не должен получать список modules через config('telegram.modules') — вместо этого ModuleMenuRegistry. Каждый active module может предоставить menu contribution; menu engine решает, показывать или нет.

Решение учитывает:

platform policy bot binding
permissions
configuration
capability
context.

Menu не должен просто показывать все installed modules:

Для Bot A: summarizer visible. Для Bot B: summarizer hidden. Для пользователя X: summarizer hidden из-за permissions. Для пользователя Y: visible.

То есть Module Discovery ≠ Menu Visibility.

Menu filtering pipeline:

installed
↓
platform enabled
↓
bot effective enabled
↓
permission
↓
visible

Registration — Resource Registry; runtime filter — BotModuleSnapshot. Menu definition зарегистрирована globally; effective menu computed per bot.

Если Menu не установлен, contribution может быть unavailable, но module продолжает работать (см. 3.9).

4.12. Admin resources

Management module получает module-provided admin resources.

Module Admin descriptor, например:

settings page dashboard widget bot settings
diagnostics
dashboard page diagnostics page.

Не делать hardcoded `if ($module === 'mafia')` в Management.

Dynamic admin: Management получает ModuleRegistry и строит UI metadata. Admin UI не должен иметь hardcoded SummarizerController — вместо этого AdminResourceRegistry.

Admin routes строятся динамически из module definitions (Admin Module Registry → surfaces → routes/navigation); никаких `Route::get('/admin/mafia')` в platform core.

URL metadata (userUrl/adminUrl) отделена от фактической route registration; user-set URLs — configuration overrides; defaults живут в module config DTO.

Admin resource описывает:

route
title key icon key
permission
scope
ordering
settingsSchema.

Admin resource scope — минимально:

PLATFORM
BOT

Например Mafia:

PLATFORM: global statistics BOT: game settings

Позже можно добавить GROUP.

USER admin scope не рекомендуется включать в Engine resource scopes: user management принадлежит authorization/user subsystem.

Platform Admin: /admin/modules. Bot Admin: /admin/bots/{bot}/modules.

Admin UI не доверяет title из module config — translation keys (см. 4.10); получает structured descriptors, не HTML.

Admin contributions проходят Resource Registry; runtime filter — Platform/Bot state. Admin integration использует Management API (TelegramModuleManagement API).

4.13. Scheduled tasks, jobs, queues

Module может объявить scheduled tasks, jobs, queue names, consumers.

Scheduler registration — application-level.

Task execution, если task относится к bot:

load bot
↓
resolve module
↓
check effective state
↓
execute

Не создавать scheduler entry для каждого bot. Scheduler должен запускать generic dispatcher.

Пример: вместо

every minute: bot 1 mafia cleanup bot 2 mafia cleanup bot 3 mafia cleanup

можно:

every minute:
ModuleScheduledTaskDispatcher

который выбирает active bots.

Но это зависит от объёма: для тяжёлых jobs лучше queue.

Jobs — module-owned resources.

Scheduler не должен запускать disabled module jobs; или job должен проверять effective module state. Предпочтительно: disabled module не имеет active schedule registration — это уменьшает unnecessary load.

Queue worker:

Worker не должен постоянно держать module enabled state в памяти. Worker получает актуальный snapshot/context.

Registration — Resource Registry; execution — runtime state.

4.14. Webhooks

Если module предоставляет webhook: route exists globally.

Incoming webhook flow:

HTTP
↓
identify bot
↓
resolve module
↓
verify effective state
↓
dispatch

Disabled module webhook: не обрабатывать бизнес logic.

Security: webhook authentication выполняется раньше module logic.

webhook.endpoint — typed contract (см. 2.5): endpoint, method, handler, authentication mode, replay protection, request/body limits, timeout.

4.15. Health checks

Health checks могут быть always registered для diagnostics (activation policy ALWAYS/ADMIN_ONLY), потому что Admin должен узнать, why module unavailable. Health checks — module-owned resources.

4.16. Middleware

http.middleware — привилегированный тип ресурса: global middleware требует explicit capability/permission; module не может молча менять глобальный Telegram/HTTP/queue middleware pipeline. То же для глобальных exception handlers (см. 2.5).

Часть 5. Реестр: ordering, коллизии, владение, безопасность

5.1. Discovery

Не использовать filesystem scan, если module сам может объявить resources.

Почему filesystem scan плох:

медленнее; сложнее deterministic order; хуже тестируется; скрывает ownership; сложнее валидировать.

Preferred discovery: Composer package DefinitionProvider регистрирует module definition.

Definition содержит resources или ссылки на typed resource descriptors.

Не создавать отдельный config.php для каждого resource, если resources статичны.

Dynamic resources: если resource зависит от environment — не вычислять его в Laravel config. Использовать ResourceProvider. Но dynamic resource generation должен оставаться deterministic. Resource provider может получить PlatformContext и вернуть descriptors.

Не разрешать resource provider делать HTTP/DB запросы при bootstrap — это критично.

Bootstrap must be cheap: discovery — local, deterministic, side-effect free.

Plugin installation должна приводить к:

package discovery
↓
ModuleDefinition validation
↓
Resource Registry compile

Не: plugin writes arbitrary config arrays.

Plugin package должен предоставить module definition. config/tg_modules.php может включать этот module, но не должен вручную перечислять все resources.

Таким образом config остаётся platform policy/configuration, а package definition — module metadata + resources.

Рекомендуемая структура module package (концептуально):

src/
Module/
MafiaModuleDefinition.php
MafiaModuleConfig.php
Resources/
...
Capabilities/
...
Permissions/
...
Providers/
...
database/
migrations/
seeders/
resources/
js/
views/
lang/

Но paths не должны автоматически считаться resources. Они должны быть явно declared.

Это обеспечивает:

predictable packaging
validation
security
diagnostics.

5.2. Deterministic ordering

Resource registration должна быть deterministic: при одинаковом module registry и config результат одинаков. Никаких foreach random discovery order.

Registry сортирует resources. Порядок:

dependencies
↓
priority
↓
stable module ID
↓
stable resource ID

Таким образом ordering deterministic.

Но:

arbitrary numeric priority не должен стать основной системой. Лучше dependency edges; priority — только tie-breaker. `after:` constraints — только per concrete resource type; никакого глобального priority integer для всего. Module dependency graph топологически сортируется и хранится отдельно от resource ordering.

Resource dependencies:

Resource dependency может быть нужна, например menu resource depends on capability resource; module migration может зависеть от another module migration; route requires permission/service.

Но:

Не разрешать arbitrary resource-to-resource dependency в первой версии — это быстро превращается в dependency hell. Использовать module dependencies. Database migrations лучше не превращать в arbitrary dependency graph. Engine должен иметь минимум module dependency graph; resource-level dependencies добавлять только там, где реально необходимо. Не строить универсальный DAG для всего подряд без причины. Resource dependencies должны использовать existing Module Dependency Graph, где возможно. Второй независимый dependency graph не создаётся без необходимости.

5.3. Collision detection

Resource collision detection обязательна.

Два modules не должны зарегистрировать:

одинаковый command name одинаковый route name одинаковый permission ID одинаковый capability ID одинаковый frontend entry ID одинаковый menu item ID duplicate resource ID.

Registry должен обнаруживать конфликт на bootstrap/compile stage.

Fail fast. Нельзя silently overwrite (особенно routes, commands, permissions). Никакого «last registration wins» — это опасная hidden behavior.

Два измерения коллизий:

Duplicate ResourceIdentity — installation/configuration error → fail fast.
Duplicate BindingKey — dispatch conflict → fail fast by default (см. 2.3).

Пример: mafia.play объявлен Mafia; другой module пытается объявить mafia.play → RESOURCE_ID_COLLISION.

Startup diagnostics: ошибка MODULE_RESOURCE_CONFLICT с:

moduleA
moduleB
resourceType
resourceId

Exception: framework может разрешать intentional override. Тогда override должен быть explicit, documented, deterministic.

Namespace: resource IDs должны быть module-owned, формат {moduleId}.{localId} (см. 2.3–2.4). Ownership enforcement — см. 2.4.

5.4. Query API и Registration Plan

Resource registry должен иметь API:

all() byModule() byType() find() has() dependencies() validate() registrationPlan() resourcesForModule() resourcesByType() resourcesByScope() resource() owners()

Conceptual resource API:

$engine->resources()->migrations() $engine->resources()->platformSeeders() $engine->resources()->routes() $engine->resources()->commands() $engine->resources()->eventSubscribers() $engine->resources()->menuContributions() $engine->resources()->adminResources() $engine->resources()->frontendAssets()

Public API должен возвращать typed collections, не array<mixed>.

Resource collection: например MigrationResourceCollection. Не обязательно создавать отдельный класс для каждой коллекции: можно начать с iterable<MigrationResource> и перейти к collection objects только при необходимости.

registrationPlan() особенно полезен: создаёт deterministic plan (providers, migrations, commands, routes, events, frontend, etc.).

Plan можно:

inspect
test
cache
execute
валидировать до выполнения.

Например ModuleBootstrapPlan содержит:

module registry version resource registry version ordered resources skipped resources blocked resources.

Bootstrap исполняет plan. Если ошибка: PLAN_EXECUTION_FAILED. Диагностика показывает: module, resource, stage, exception. Это резко упрощает debugging.

Это значительно лучше, чем непосредственный foreach в bootstrap.

5.5. Безопасность реестра

Third-party modules:

Engine должен позволять Composer-installed plugin, но plugin code считается trusted application code. Plugin data не считается trusted.

Third-party module с invalid resource → startup diagnostic.

Plugin cannot самостоятельно:

modify another module overwrite registry disable another module

через public API.

Registry mutation — только bootstrap phase.

Ownership and security:

Только owner module (или privileged Engine operation) может unregister/modify ресурс; module A не может трогать ресурсы module B. Resource IDs из user-controllable input валидируются. Sensitive fields в definitions помечаются и redacted в logs/serialization; секреты никогда не попадают в resource identity или IDs.

Resource registration должна быть observable (см. 6.3).

Часть 6. Валидация, CLI, диагностика и восстановление

6.1. Resource validation

tg:modules:validate / module:validate проверяет:

duplicate IDs missing classes invalid paths invalid dependency unsupported resource
conflicts
invalid scope invalid providers missing dependencies incompatible versions invalid routes malformed DTOs.

Diagnostic codes:

RESOURCE_CLASS_NOT_FOUND
RESOURCE_PATH_NOT_FOUND
RESOURCE_ID_DUPLICATE
RESOURCE_CONFLICT
RESOURCE_INVALID_SCOPE
INVALID_DEFINITION
INCOMPATIBLE
QUOTA_EXCEEDED
REGISTRY_STALE
PLAN_EXECUTION_FAILED
MODULE_RESOURCE_REGISTRATION_FAILED
MODULE_RESOURCE_CONFLICT.

CLI должен работать без Telegram API, bot tokens и external services; module:validate обязателен в CI.

Deployment flow:

composer install
→ module:validate
→ migrate
→ module:provision
→ cache/build
→ worker reload

6.2. Failure policy

Startup failure: critical resource error → fail fast.

Например missing migration class → deployment failure.

Non-critical UI metadata можно degraded mode, но только если явно разрешено.

Recommendation:

Infrastructure errors: fail closed. UI metadata errors: log + omit, если безопасность не нарушается.

Critical collision at boot fails the application или помечает module INVALID; никогда не молча игнорируется.

6.3. Observability

Resource registration должна быть observable.

Startup diagnostics, например:

Telegram Module Engine

Modules:
14 installed 11 enabled 3 disabled

Resources:
42 providers 18 commands 21 routes 37 permissions 12 frontend entries.

Это должно быть доступно CLI: tg:modules:list и tg:modules:diagnose.

Не обязательно делать CLI в первой реализации, но Engine API должен это позволять.

Resource errors не должны превращаться в generic Laravel exception без context.

Ошибка должна знать:

moduleId
resourceId
resourceType
phase.

Это единая Failure Taxonomy для Engine.

6.4. CLI как guaranteed recovery path

При отключённом Management команды module:list, module:validate, module:enable/disable/diagnose должны оставаться доступны (bootstrap paradox fallback).

Дополнительно module:resources печатает per-module resource tree (permissions, menu, admin, commands, migrations).

6.5. Platform integration adapters

В Laravel platform остаются небольшие adapter classes:

TelegramModuleMigrationRegistrar
TelegramModuleSeeder
TelegramModuleRouteRegistrar
TelegramModuleCommandRegistrar
TelegramModuleFrontendManifestGenerator

Они не знают конкретные modules.

Seeder example:

DatabaseSeeder → TelegramModuleSeeder → Engine → platformSeeders() → call().

Ключевое отличие:

Плохое: foreach(config('telegram.modules_seeders')) Хорошее: foreach($moduleEngine->platformSeeders())

Почему: в первом случае application владеет module topology; во втором Engine владеет module topology. Это именно та абстракция, которую мы хотим получить.

Даже если внутри Engine есть foreach ($resources as $resource) — это не проблема.

Integration mapping:

Laravel migration infrastructure знает только TelegramModuleMigrationRegistrar. Admin знает только TelegramModuleManagement API. Menu знает только TelegramModuleMenuContribution API. Frontend знает только ModuleFrontendManifest.

Engine остаётся orchestration layer.

Что исчезает из платформы:

telegram.modules_seeders
telegram.modules_migrations
telegram.modules_providers
telegram.modules_routes
telegram.modules_commands
telegram.modules_permissions
telegram.modules_menu
telegram.modules_admin
telegram.modules_frontend

и любые ручные:

foreach ($modules as ...) foreach (config('...modules...'))
ModuleA::class
ModuleB::class
ModuleC::class

в platform application code.

Что остаётся: платформа знает только TelegramModuleEngine и его adapters.

Host application после миграции не должен содержать hardcoded:

список module routes список module frontend entries список module permissions список module menu items список module commands module-specific provider lists.

Все эти сведения приходят из Module Engine.

Acceptance Criteria (сводный, дедуплицированный)

Общие принципы
- Module сам объявляет свои resources; platform не перечисляет их вручную; TelegramModuleEngine — единый Resource Registry и единственный владелец module topology.
- Host Laravel application не знает внутреннюю структуру module resources; размазанные module-specific foreach/bootstrap lists полностью устранены.
- Новый module добавляется без изменения host-кода, кроме единственной записи/политики в config/tg_modules.php, и автоматически виден Module Registry, Resource Registry и динамической Admin UI; новый skill module автоматически участвует в lifecycle Engine.
- Архитектура сохраняет один application и множество bots с различными наборами skills.

Каталог и контракты
- Существует TelegramModuleResource base contract; resource types typed, каталог типов явный, произвольные типы запрещены; нет giant universal resource DTO.
- Resource type описывает lifecycle semantics, не бизнес-категории; descriptors — immutable DTO, не выполняют DB/HTTP/business logic; execution — в Engine/adapters.
- Core contracts framework-neutral; Laravel/Telegram specifics — в adapter layer; registry — catalog: сам не отправляет Telegram messages, не делает HTTP requests, не запускает jobs.
- Engine не делает Telegram transport calls (только типизированный словарь BindingKey); routing table строится на control path и хранится в PostgreSQL, Engine — dumb dispatcher proxy; никакой K8s reconciliation machinery (desired/observed loops, fencing, drain policies, tombstones) нет.
- Permission system внешняя; Engine не хранит и не вычисляет grants.
- Schema validation до runtime: invalid definition → INVALID_DEFINITION, не silent default; schema version в контрактах, unsupported → INCOMPATIBLE.
- Lazy handler loading с preflight (class exists, contract, dependencies).

Идентичность и владение
- Stable resource ID, независимый от filesystem/vendor path, class hash, array index; resource принадлежит module; Engine определяет owner любого resource.
- IDs namespaced по moduleId и валидируются; Engine запрещает module A регистрировать ресурс в namespace module B; platform-owned shared resources — explicit exception.
- ResourceIdentity и BindingKey — разные идентификаторы; BindingKey collision детектируется отдельно от ResourceIdentity collision.
- Sensitive fields redacted; секреты не входят в resource identity/IDs.

Коллизии
- Duplicate resource/permission/capability IDs и route names обнаруживаются на bootstrap/compile; fail fast; silent overwrite и «last registration wins» запрещены.
- Ambiguous BindingKey по умолчанию — explicit error; dispatch policy — только opt-in позже; intentional override — только explicit, documented, deterministic.

Scope-модель
- Registration is application-level; activation is runtime-scoped — отделены; descriptor содержит registrationScope и activationScope.
- Scopes: PLATFORM, BOT, TENANT, CHAT (USER — только UI-измерение, не admin scope Engine); registration обычно PLATFORM.
- Migration — platform-level, scope explicit; migration/seeder не создают bot binding без explicit contract; route scopes explicit (PLATFORM_ADMIN, BOT_ADMIN, USER, WEBHOOK, INTERNAL).
- Global routes/commands/listeners не регистрируются per bot; bot activation — runtime guard/context; global resources не удаляются при отключении module у одного bot; disable у одного bot не влияет на другой.
- Activation policy per resource (ALWAYS/PLATFORM/BOT/ACTIVE_MODULE/ADMIN_ONLY).
- Resource registration ≠ capability availability ≠ permission authorization; resource metadata ≠ business domain configuration; resource state ≠ module state.

Lifecycle по типам
- ServiceProvider — integration bridge, не discovery/activation; provider boot не делает bot activation, seeding, DB writes, external calls; никаких `boot(): foreach bots`.
- Migrations: Laravel migrations table — source of truth, собственный runner/history у Engine нет; ordering Engine-затем-module, infra graph отделена от runtime graph; duplicate migration identifiers обнаруживаются.
- Seeders: execution policy (automatic/explicit/disabled); install/default/demo/repair различаются; demo/repair не запускаются автоматически; idempotent где возможно; stable identity; DatabaseSeeder без module foreach; plan с dry-run; seeders не создают permission definitions — только default role grants.
- Поддерживаются ресурсы: Route, Command, EventListener, Middleware, Permission, Menu, Admin, UserPage, FrontendAsset, ConfigSchema, Job, Schedule, HealthCheck.
- Command resources без authorization logic, ссылаются на capabilities; disabled module не выполняет runtime event handling, при этом Laravel listener registration не пересобирается per bot; фильтрация через единообразный ModuleRuntimeGuard.
- Global middleware/exception handlers — привилегированные ресурсы с explicit capability/permission; Telegram command/callback handlers не саморегистрируются; callback patterns bounded и validated.
- Scheduled jobs module-owned; disabled schedules inactive без explicit policy; нет scheduler entry per bot; queue worker получает актуальный snapshot/context.
- Health checks доступны diagnostics и у disabled modules; webhook authentication раньше module logic; disabled module webhook не обрабатывает бизнес-логику.

Меню, админка, frontend
- Menu contributions declarative; menu registry не перечисляет installed modules; visibility вычисляется отдельно с учётом bot binding, permissions, configuration, capability, context.
- Skill module не обязан зависеть от Menu implementation; menu contribution может быть unavailable без Menu.
- Admin UI использует AdminResourceRegistry; routes строятся динамически из module definitions; без hardcoded controllers; translation keys вместо module-provided text/HTML.
- Admin scopes: PLATFORM, BOT (GROUP позже); USER admin scope не входит в Engine scopes.
- Frontend declarative со stable IDs; build не зависит от bot activation; Vite не перестраивается при bot enable/disable; chunks lazy-load.
- Никакого arbitrary HTML/JS injection; assets — declared (manifest reference); frontend hiding не security boundary, backend authorization обязательна; API-метаданные через serialization whitelist/presenters.

Реестр, ordering, dependencies
- Global registry строится после discovery; discovery ≠ registration ≠ activation; disabled module не активирует обычные runtime resources.
- Deterministic registration; plan ordering: dependencies → priority (tie-breaker) → stable module/resource ID; module dependency graph сортируется отдельно; resource dependencies — только где необходимо, без универсального DAG и второго dependency graph.
- Tags для filtering/diagnostics/tooling, не замена typed resource.
- Registry immutable после bootstrap/compile; runtime не добавляет arbitrary resources; user config не создаёт ресурсы и не меняет handler/provider; Bot Admin — только activate/deactivate/configure.
- Plugin code trusted, plugin data untrusted; module A не трогает ресурсы module B и не disable другой модуль через public API; registry mutation — только bootstrap.
- Plugin installation → discovery → validation → registry compile; не произвольные config arrays; config/tg_modules.php — platform configuration, не resource inventory и не replacement definition.
- Immutable definition; один entry point ModuleRegistrar::register(ModuleDefinition); Config DTO совместим с config:cache; сложная валидация в ModuleConfigValidator; configuration меняет behavior, не identity/owner.

Планы и кэш
- Deterministic Registration Plan: валидация, диагностика, кэширование; module/resource registry versions учитываются и инвалидируют plan.
- Compiled snapshot — derived artifact; REGISTRY_STALE в production — fail fast; dev может auto-rebuild.
- Cache keys: `module-registry:{registryVersion}` и `effective-modules:{botId}:{configurationVersion}:{registryVersion}`; никогда не кэшировать effectiveResources без bot/tenant identity.
- Bot binding changes не rebuild global registry; bot enable/disable не требует Laravel restart и dynamic route/migration/provider registration; effective behavior вычисляется поверх глобального registry.
- Runtime не перечисляет Composer packages и не читает tg_modules.php напрямую; Laravel integration через Engine ServiceProvider — единственный canonical integration point.

Ошибки и диагностика
- Registration errors содержат module ID, resource ID, resource type, phase; единая Engine failure taxonomy.
- Infrastructure errors fail closed; UI metadata errors — log + omit; critical collision at boot fails application или помечает module INVALID.
- Registration observable; startup diagnostics; immutable snapshot доступен Admin/diagnostics/runtime; Admin видит disabled resources (включая health checks).
- Ownership доступен diagnostics; reverse lookup by module и by resource; quotas → QUOTA_EXCEEDED, platform security limits не переопределяются.
- CLI/diagnostics выводят полный resource inventory; module:validate работает в CI без Telegram API/tokens/external services.
- CLI — guaranteed recovery path: module:list / validate / enable / disable / diagnose / resources доступны при отключённом Management.

Dependency direction
- Menu/Management/Basic зависят от Engine; Engine от них — нет (hard invariant); Management optional; Telegram Bot Lib не знает Engine.
- Menu → Engine; Management → Engine; Basic → TelegramBotLib и/или Engine.

Host platform
- Host не содержит arrays telegram.modules_{seeders,migrations,providers,routes,commands,permissions,menu,admin,frontend} и hardcoded списки module routes/frontend entries/permissions/menu items/commands/providers.
- Все сведения приходят из Module Engine; Admin UI и Bot Admin получают metadata/effective availability динамически.
