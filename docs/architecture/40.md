40 — Module Lifecycle, Dependencies & State Machine

## 1. Назначение

Этот документ — единый документ о lifecycle модуля в TelegramModuleEngine: словарь состояний, state machine, операции (install / connect / enable / disable / disconnect / configure / upgrade / repair / uninstall / purge), зависимости, миграции и provisioning, orphan policy, optimistic locking и granular lifecycle permissions.

Главная задача — исключить смешивание измерений: installed, discovered, available, allowed, configured, connected, enabled, running, degraded, disabled, disconnected, uninstalled. Нельзя свести lifecycle к одному `module.status` или к одному boolean `enabled = true/false`.

## 2. Измерения lifecycle (многомерная модель)

Lifecycle многомерен. Минимально разделяются:

- InstallationState — существует ли module в platform.
- DiscoveryState — обнаружен ли module и валидно ли его definition.
- AvailabilityState — может ли module быть активирован.
- PolicyState — разрешено ли module использовать (platform / tenant).
- BindingState — подключён ли module к конкретному Bot.
- ConfigurationState — UNCONFIGURED / PARTIALLY_CONFIGURED / CONFIGURED / INVALID.
- DesiredState — что хочет администратор: ENABLED / DISABLED.
- RuntimeState (Operational) — что происходит прямо сейчас: STOPPED / STARTING / RUNNING / DEGRADED / FAILED / STOPPING.
- Effective State — что вычисляет Engine как реально используемое.

Никогда не сворачивать их в одну колонку `status`. Тройка «desired = ENABLED, effective = BLOCKED_BY_DEPENDENCY, operational = STOPPED» читается точно как «модуль подключён, но сейчас не может работать».

## 3. Platform Module Lifecycle

Module package проходит lifecycle:

    NOT_INSTALLED
    ↓
    INSTALLED
    ↓
    REGISTERED
    ↓
    AVAILABLE
    ↓
    DEGRADED / BLOCKED
    ↓
    DEPRECATED
    ↓
    REMOVED

Дополнительные состояния:

- NOT_INSTALLED — package отсутствует в application, Engine не имеет его definition.
- INSTALLED — Composer/package code присутствует, definition ещё не прошёл регистрацию.
- REGISTERED — Engine обнаружил ModuleDefinition.
- AVAILABLE — definition валиден, dependencies удовлетворены, module infrastructure совместима.
- INCOMPATIBLE — неподдерживаемая engine/API/PHP/platform version.
- BROKEN — definition provider failed, resource registration failed или required dependency unavailable.
- QUARANTINED — invalid/incompatible definition помещается в карантин, а не частично регистрируется; он никогда не станет Active, но остаётся видимым в Admin UI с причиной. Компиляция registry атомарна — никакого «half-registered» module.
- UNINSTALLING — явное переходное состояние перед REMOVED (см. раздел Uninstall).
- DEGRADED — module может работать, но часть возможностей недоступна (например LLM module без optional provider).
- BLOCKED — module существует, но использовать его нельзя. Причины: missing dependency, incompatible version, invalid configuration, unavailable capability, infrastructure failure, explicit platform block.
- DEPRECATED — module ещё работает, но новые подключения запрещены либо предупреждаются. Может сосуществовать с ACTIVE (warning / migration period). Deprecation — метаданные module, не configuration: deprecationSince, removalAfter, replacementModule.
- REMOVED — module package больше не зарегистрирован.

Installed не означает usable, allowed, connected. Discovery отдельна от installation: package может быть найден, но unavailable (например incompatible PHP version). Module criticality (CORE / REQUIRED / OPTIONAL) отдельна от dependencies: invalid optional skill quarantineится, invalid core engine роняет boot.

## 4. Bot Module Lifecycle

Для конкретного bot состояние другое. BindingState:

    NOT_CONNECTED (DISCONNECTED)
    ↓
    CONNECTED
    ↓
    ENABLED / DISABLED

- NOT_CONNECTED — у bot нет binding.
- CONNECTED — binding существует, но CONNECTED не означает enabled: валидно состояние connected + disabled (admin подключил, настроил, но временно выключил).
- ENABLED — binding существует, `enabled = true` (desired).
- DISABLED — binding существует, `enabled = false`. Configuration сохраняется.

Effective status вычисляется: AVAILABLE, BLOCKED, DEGRADED, MISCONFIGURED, FAILED, ORPHANED.

RuntimeState не является desired state: desired = ENABLED при runtime = FAILED означает «module включён, но runtime сломан». Нельзя превращать runtime failure в automatic disconnect — иначе теряется intent администратора. Enabled + failed runtime — валидное диагностическое состояние.

Effective state не должен физически храниться как единственный boolean. Он вычисляется централизованно (PostgreSQL хранит только факты: bindings, desired state, configuration):

    installed ∧ available ∧ allowed ∧ connected ∧ configuration valid ∧ desired enabled
    → ACTIVE (runtime may run)

Примеры:

- desired = ENABLED, platform = AVAILABLE, dependencies = OK, configuration = VALID → ACTIVE.
- desired = ENABLED, dependencies = BROKEN → BLOCKED (BLOCKED_BY_DEPENDENCY).
- desired = ENABLED, policy denied → BLOCKED (BLOCKED_BY_PLATFORM).
- desired = ENABLED, configuration invalid → MISCONFIGURED.
- desired = ENABLED, definition = missing → ORPHANED.
- desired = DISABLED → DISABLED.
- runtime crashed → FAILED (operational).

Ограниченный transition graph: не каждое состояние переходит в каждое (например PURGED → ENABLED требует reconnect/reinstall; DISABLED → ENABLED разрешён). Несколько малых ортогональных измерений лучше одной комбинаторно взрывающейся state machine (CONNECTED_ENABLED_RUNNING).

## 5. Resolver и Manager

State machine должна быть централизована. Модулю запрещено самому придумывать lifecycle вида `if ($enabled && ...)`.

- `ModuleStateResolver` — только вычисляет effective state, без side effects.
- `ModuleLifecycleManager` — выполняет lifecycle mutations: проверяет dependencies, configuration validity, bot eligibility, lifecycle policy.

Lifecycle operations command-driven: InstallModule, UninstallModule, ConnectModule, DisconnectModule, EnableModule, DisableModule, ConfigureModule, ReconfigureModule, UpgradeModule, RepairModule. Не `$module->status = ...`.

Каждая операция: authorization, validation, preconditions, transaction, side effects, audit, postcondition, operation ID. Manager не зависит от Telegram HTTP request и не выполняет Telegram transport calls; он может использоваться из CLI, Admin UI, API и Mini App и не зависит от конкретного skill.

## 6. Операции: connect / enable / disable / disconnect / purge

**Connect** — создать/активировать BotModuleBinding. Не должен автоматически enable. **Enable** — изменить desired state; не должен молча connect. UI может предложить composite «Connect & Enable», но backend понимает две разные операции.

**Enable** (полная операция): resolve module → resolve dependencies → validate configuration → validate bot eligibility → persist binding → emit event.

**Disable**: validate policy → persist desired state → emit event. Disable не удаляет: configuration, permissions, menu metadata, historical state. Runtime availability становится DISABLED.

**Disconnect** — убрать bot binding. Не должен автоматически purge data. Disconnect ≠ Delete. Disable ≠ Disconnect: disable означает «временно не использовать», disconnect — «убрать binding». Даже disconnect не обязан удалять historical configuration.

**Purge** — отдельная privileged и опасная операция (PurgeModuleData): может удалить configuration, module state, bot-specific data. Требует explicit confirmation/policy. Некоторые modules могут запретить автоматический purge (например persistent user data).

Итого: **disable, disconnect, purge — три разные операции**. Re-enable должен сохранить configuration, binding, permissions, user intent. Configuration может существовать у disabled и даже disconnected module.

## 7. Dependencies

Dependencies — first-class metadata. Module может зависеть от required/optional: modules, capabilities, platform services, infrastructure. Типы:

REQUIRED_MODULE, OPTIONAL_MODULE, REQUIRED_CAPABILITY, OPTIONAL_CAPABILITY, REQUIRED_INFRASTRUCTURE, OPTIONAL_INFRASTRUCTURE.

Правила:

- Dependency имеет stable identity (например `module:menu`), не PHP class name, не Composer package name.
- Поддерживается version constraint (например `menu >= 2.0 < 3.0`) — особенно важно при composer updates.
- Package dependency graph строится централизованно, обнаруживает cycles (прямые A→B→A и косвенные A→B→C→A); cycle — explicit configuration error.
- Graph — immutable snapshot, кешируется на application lifecycle; не перестраивается на каждый Telegram update. Пересобирается при package update, config cache rebuild, deployment.
- Bot-level dependencies отдельны: package graph (Cinema → Menu) и bot effective graph (Cinema ENABLED, Menu DISABLED → broken) — разные вещи, не смешивать. Dependency resolution учитывает bot bindings: один и тот же module может быть ACTIVE у одного bot и BLOCKED у другого.
- Required module/capability absence → BLOCKED. Optional module → DEGRADED / feature unavailable. Optional capability → reduced functionality. Optional dependency loss не блокирует uninstall автоматически.
- Module объявляет capabilities; runtime проверяет required capabilities через capability resolution — это лучше hardcoded `class_exists` checks.
- Dependency errors machine-readable: MISSING_MODULE, MODULE_DISABLED, VERSION_INCOMPATIBLE, CAPABILITY_UNAVAILABLE, CYCLE_DETECTED.

## 8. Dependency enable/disable policy

- Dependency auto-enable не является default: enable Cinema не включает Menu автоматически. Причина: автоматическое включение может неожиданно изменить bot composition. Вместо этого — «dependency missing».
- Возможен explicit «Enable with dependencies»: явное действие пользователя с подтверждением («Также будет подключён Menu.»).
- Disable dependency проверяет dependents: попытка disable Menu при Cinema requires Menu даёт «Cannot disable Menu. Dependents: Cinema.» Вариант «Disable Menu and affected modules» — тоже explicit operation. Cascade disable по умолчанию запрещён: иначе один click может выключить половину bot. Cascade operation показывает affected modules и требует подтверждения.
- Dependency нельзя silently disable при активных required dependents.

## 9. Upgrade

Upgrade ≠ uninstall + install. Upgrade имеет fromVersion и toVersion.

Порядок: compatibility check → migration plan → resource update → configuration migration → проверка runtime, по возможности zero/minimal downtime.

- Upgrade transactional на уровне metadata. Внешние side effects не всегда transactional — поэтому нужна compensation strategy (например DB migration succeeded, worker restart failed → module остаётся installed, runtime degraded/failed; никаких fake rollback «всего мира»).
- Upgrade должен иметь UpgradePlan (preview для admin): dependencies, migrations, config migrations, resource changes, restart requirements, possible downtime.
- После upgrade — health verification. Failure → runtime FAILED/DEGRADED, но desired state сохраняется (ENABLED) — это позволяет automatic repair/retry. Upgrade failure не уничтожает persisted intent.
- Package update не меняет binding desired state автоматически и не удаляет bot configuration; проходит compatibility validation. Incompatible package → BLOCKED; compatible → может восстановить ACTIVE; rollback package может восстановить прежний state.

## 10. Repair

Repair — отдельная операция (например RepairModuleRuntime): reload provider, reconnect workers, rebuild resource snapshot, retry initialization. Repair не должен silently modify configuration.

## 11. Uninstall

Module removal особенно опасна. Нельзя `composer remove package` → `DELETE FROM bot_module_bindings`.

- UNINSTALLING: перед uninstall строится preflight report — active bots, disabled bots, reverse dependencies, stored configuration, data, cleanup requirements.
- Default policy: отказ в uninstall, пока есть active bindings или hard dependents. Force uninstall требует explicit confirmation, impact report, authorization и audit.
- Uninstall имеет dependency check: если module используется — blocked. Admin видит dependent bots, dependent modules, owned data, active bindings. Для массовых операций — impact preview («This module is connected to 47 bots» → disconnect 47 bindings, preserve configuration, runtime shutdown).
- Нельзя автоматически отключать сотни bots без явного confirmation.
- После uninstall module code absent, data может оставаться. Uninstall ≠ purge. Uninstall не удаляет bot bindings и configuration.

## 12. Orphan policy

- Удаление package создаёт ORPHANED bindings. Admin UI: «Module package is not installed.», configuration сохраняется.
- ORPHANED bindings никогда не auto-deleted: package removal — не data deletion (rollback, временное удаление, reinstallation — ожидаемы).
- Engine обнаруживает orphans; Management показывает «Orphaned module configuration», cleanup — только явное действие оператора (purge / detach / reinstall package).
- Orphaned module не исполняется: нельзя вызвать через command, route, Mini App или queue.
- Если package reinstall: definition появляется, Engine повторно вычисляет state. Compatible → binding возвращается ACTIVE; incompatible → BLOCKED. Reinstall не должен автоматически менять desired state и не создаёт duplicate binding. Это позволяет безопасный rollback deployment.

## 13. Desired state — это intent, а не команда

Persisted desired state (BotModuleBinding.desired_state) — intent, не безусловная команда. Runtime восстанавливается только если policy still allows, config still valid, dependencies available. Модель сходимости (convergence):

- Desired state — цель; runtime сходится к ней. Это критично для long-lived Telegram workers / queue daemons.
- Если runtime не может hot-disable (worker reload failed), desired disable НЕ откатывается. Engine честно сообщает: desired disabled, operational still running, restart pending. Никогда не врать пользователю, что module disabled, пока stale worker обрабатывает updates.
- Симметрично: desired enabled при missing dependency или invalid configuration остаётся ENABLED при effective blocked/misconfigured; устранение причины автоматически делает module READY (self-healing admin) — без повторного ввода configuration.
- Автоматические retries имеют лимиты: retry policy, backoff, max attempts; operational failures не создают бесконечных retry loops.
- Долгоживущие workers не держат состояние вечно: проверяют revision, обновляются между jobs/updates, реагируют на invalidation events; activation state никогда не является worker-global mutable state (защита от cross-bot leakage).
- Активация runtime resources idempotent: повторный запуск не создаёт duplicate listeners, schedules, workers, webhook handlers. Resource Registry (desired → effective → runtime): enabled module → activate resources; disabled → deactivate; connected but disabled → binding exists, resources inactive; configuration invalid или policy denied → binding может remain, runtime blocked. Это позволяет admin исправить policy/config без повторного подключения.

## 14. События и audit

- Lifecycle events существуют для значимых transitions: BotModuleEnabled, BotModuleDisabled, BotModuleBlocked, BotModuleRecovered, ModuleInstalled, ModuleConnected, ModuleDisconnected, ModuleUpgraded, ModuleUninstalled, ModuleRuntimeFailed, ModuleRuntimeRecovered.
- Events содержат moduleId, tenantId (где применимо), botId (для bot events), actor (при наличии), operationId.
- Source of truth — PostgreSQL (binding): events — notification / cache invalidation / projection, не source of truth. Event listeners не должны произвольно менять lifecycle state. Menu может инвалидировать cached menu, permission subsystem — пересобрать projection, Admin UI — получить realtime update. Но «event → DB mutation» не является обязательным lifecycle mechanism — это снижает сложность recovery.
- Publish только после DB commit (outbox для надёжности): commit first, invalidate/publish second.
- Audit обязателен для: connect, disconnect, enable, disable, configure, upgrade, uninstall, purge. Runtime failures — тоже audit/diagnostic event. Module lifecycle observable.

## 15. Optimistic locking, idempotency, constraints

- Каждый binding несёт revision; операции принимают expectedRevision. Mismatch → CONCURRENT_MODIFICATION / MODULE_STATE_CONFLICT, никогда silent last-write-wins; UI предлагает refresh вместо перезаписи.
- На configuration edits UI отправляет expectedVersion; изменённая версия даёт CONFLICT вместо молчаливой перезаписи чужих изменений.
- Settings и activation разделяют одну revision sequence.
- Enable / disable / enable-with-dependencies — transactional.
- Каждый lifecycle operation несёт operation ID (ULID/UUID): idempotency (queue retry не дублирует активацию — Engine сначала проверяет состояние операции), tracing, audit correlation, retries.
- Connect под race защищён DB unique constraint: два одновременных Connect дают один binding; проигравший получает «already connected» / «operation in progress».
- Все lifecycle operations idempotent: enable дважды, disable дважды, disconnect дважды — безопасны.
- `tg_bot_modules` хранит module_id как stable logical string (не PHP class name, не Composer package name). Нет SQL FK на installed-modules table (Composer state, не DB state); FK на bot_id обязателен. UNIQUE(bot_id, module_id) обязателен.

## 16. Migrations, provisioning, seed, purge

Migration vs Provisioning vs Seed vs Purge — четыре разных понятия:

- **Migration** = schema, deployment lifecycle. Laravel migrations регистрируются через Engine, но выполняются стандартным Laravel/deployment lifecycle — никогда per module enable, никогда на каждом bootstrap. Schema соответствует установленному ПО независимо от enabled state; migrations не создают bot-specific rows (это provisioning).
- **Provisioning** = application data/state в module lifecycle (Platform Seeder — global data через `module:provision`; Bot Provisioner — bot-specific данные через `bot:module:provision`, idempotent).
- **Seed** = initial/default data. Seeders типизированы и никогда не запускаются автоматически на boot; Demo Seeder — никогда в production без explicit policy.
- **Purge** = explicit destructive removal module-owned data с declarative ownership (никаких догадок по table prefix).

Configuration migrations:

- Migration — часть module lifecycle, но не module enable operation: enable module не запускает произвольную DB migration.
- Хранится module configuration version (`config_version = 3`) против текущей definition (`config_version = 4`) → migration required; runtime BLOCKED или DEGRADED в зависимости от policy. Старую configuration нельзя silently интерпретировать при несовместимой schema.
- Configuration migrations deterministic: 1→2, 2→3, 3→4; не 1→latest без необходимости. Migration history audit-able. Admin UI может показывать «Configuration migration required».
- Provisioning version (и settings/config version) отслеживается отдельно от Composer version; upgrade сравнивает applied vs declared version и является controlled, deterministic, idempotent операцией — не boot side effect.
- Package version ≠ bot configuration version. Четыре разных понятия: module package version, module API version, module configuration version, binding revision (например 3.4.1 / 3 / 7 / 42).

## 17. Permissions (granular, external)

- Permission system — внешний. Engine только хранит permission NAMES, источником которых является ModuleDefinition; Engine лишь агрегирует их. Core application не хардкодит module permission names, и никакие произвольные permission names не генерируются из URL.
- Не один `module.manage`: как минимум module.view, module.use, module.configure, module.connect, module.disconnect, module.enable, module.disable, module.upgrade, module.uninstall, module.purge.
- Configure может быть более привилегирован, чем use: configuration может содержать внешние credentials, webhook URLs, integrations.
- Authorization — цепочка: Actor → canManageBot (bot ownership) → canPerformModuleAction (lifecycle permission) → operation. Module permissions never заменяют bot-level authorization — это предотвращает permission escalation.
- Permissions исключены из effective state: EffectiveModuleState отвечает «can the module run for this bot?», authorization — «may this actor use this capability/action?». Независимые слои, никогда не смешивать. Permission denial (например нет mafia.play) не должен представлять module как disabled: state остаётся enabled, действие запрещено. UI может скрыть menu contribution, но Engine state не меняется.
- Permission проверяется на каждую lifecycle operation. Tenant admin может allow/deny modules в рамках platform policy; bot admin — connect / disconnect / enable / disable / configure только разрешённые операции.

## 18. Snapshot и наблюдаемость

- Runtime никогда не ре-анализирует Composer/config per update: он потребляет compiled Module Registry плюс кешированный immutable per-bot BotModuleSnapshot (botId, revision, module states, capabilities, dependencies, contributions), построенный из одной revision — никогда из смешанных.
- Snapshot invalidation после DB commit; revision/event-based invalidation — первична, TTL — только safety net. Fallback при недоступном кеше — DB; если DB недоступна — fail closed.
- Admin UI видит все измерения (Installed / Available / Allowed / Connected / Configured / Enabled / Running), не один status badge, но UX не обязан показывать все технические состояния одновременно (например «Connected · Enabled · Degraded»).
- Per bot: available / connected / disabled / blocked / misconfigured modules. Общая admin — installed modules, compatibility, dependencies, platform policy. Bot admin — modules бота, configuration, permissions, runtime health. Module UI динамическая; module-specific lifecycle UI не hardcoded в platform.
- Dependency chain отображается (Cinema → Search → Proxy → Proxy provider), но без внутренних технических деталей обычному bot owner: owner видит «Требуется подключить X» + действие ([Enable Menu]) при наличии permission; platform administrator видит полный diagnostic и причину BLOCKED, а не просто «Не работает».

## 19. Изоляция ботов

- Один module package может иметь bindings у множества bots. Enable Bot A не меняет Bot B; disable Bot A не меняет Bot B; configuration Bot A не меняет configuration Bot B.
- Dependency state Bot A может отличаться от Bot B (Menu enabled у A, disabled у B): один и тот же module ACTIVE у одного и BLOCKED у другого. Effective state рассчитывается per bot; при наличии chat activation — per chat.
- Package lifecycle не зависит от bot count. Composer/package lifecycle, platform module lifecycle и per-bot binding lifecycle независимы; TelegramModuleEngine — единственное место, где вычисляется их пересечение в детерминированный EffectiveModuleState.

## Главный инвариант

Installation module на Platform, разрешение module Tenant, подключение module к Bot, desired enabled state, configuration и фактическое runtime состояние — независимые измерения. Disconnect не удаляет данные, Disable не удаляет binding, Uninstall не равен Purge, а runtime failure не уничтожает административное намерение enabled. TelegramModuleEngine централизованно вычисляет их пересечение в детерминированный EffectiveModuleState, не допуская скрытых cascade-операций, потери bot configuration или влияния lifecycle одного bot на другой; включение/отключение skill одного bot никогда физически не устанавливает, не удаляет и не изменяет module package для остальных bots.

## Acceptance Criteria

- Module lifecycle не сводится к одному boolean / status.
- InstallationState, DiscoveryState, AvailabilityState, PolicyState, BindingState, ConfigurationState, DesiredState, RuntimeState существуют и разделены.
- Platform lifecycle: NOT_INSTALLED, INSTALLED, INSTALLING, FAILED, REGISTERED, AVAILABLE, INCOMPATIBLE, BROKEN, QUARANTINED, DEGRADED, BLOCKED, DEPRECATED, UNINSTALLING, REMOVED поддержаны.
- Bot binding: NOT_CONNECTED, CONNECTED, ENABLED, DISABLED поддержаны.
- Effective state поддерживает ACTIVE, BLOCKED, DEGRADED, MISCONFIGURED, FAILED, ORPHANED; вычисляется централизованно (ModuleStateResolver), не хранится как единственный persistent boolean.
- Connected + disabled — валидное состояние; enabled + failed runtime — валидное диагностическое состояние.
- Installed ≠ Available ≠ Allowed ≠ Connected; Connected ≠ Enabled; Enabled ≠ Running; Running ≠ Healthy.
- Runtime failure не меняет desired state автоматически.
- Policy DENY, invalid configuration, missing dependency блокируют effective activation; resource collision блокирует installation.
- QUARANTINED definition не может стать Active; registry compilation atomic, без half-registered module.
- DEPRECATED может сосуществовать с ACTIVE; deprecation — метаданные module.
- Module criticality (CORE/REQUIRED/OPTIONAL) отделена от dependencies.
- Существуют ModuleStateResolver (без side effects) и ModuleLifecycleManager (mutations, проверяет dependencies/configuration/eligibility/policy).
- Install, Connect, Enable, Disable, Disconnect, Upgrade, Uninstall, Purge, Repair — explicit operations, каждая с authorization, validation, preconditions, transaction, side effects, audit, postcondition, operation ID.
- Connect не включает module автоматически; Enable не подключает автоматически.
- Disable не disconnects; Disconnect не purges; Uninstall не означает purge.
- Disable не удаляет configuration, permissions, menu metadata, historical state.
- Re-enable сохраняет configuration, binding, permissions, user intent.
- Configuration может существовать у disabled и disconnected module.
- Disconnect не уничтожает persistent module data автоматически; purge — явно опасная операция с explicit confirmation/policy.
- Module может объявлять lifecycle policy; persistent data имеет retention policy.
- Lifecycle operations idempotent (enable/disable/disconnect дважды безопасны) и используют optimistic concurrency (expectedRevision/expectedVersion → CONCURRENT_MODIFICATION / CONFLICT, никогда silent last-write-wins).
- Каждый operation имеет operation ID; idempotency, tracing, audit correlation, retries.
- Connect под race защищён DB unique constraint; UNIQUE(bot_id, module_id) обязателен; module_id — stable logical string, без FK на installed-modules, FK на bot_id обязателен.
- Enable/disable/enable-with-dependencies transactional; events публикуются только после commit (outbox).
- Lifecycle manager не зависит от Telegram HTTP request и не выполняет Telegram transport calls; работает из CLI, Admin UI, API, Mini App; не зависит от конкретного skill.
- Dependencies first-class; identity stable (не PHP class name); version constraints поддерживаются; типы REQUIRED/OPTIONAL × MODULE/CAPABILITY/INFRASTRUCTURE.
- Dependency graph централизован, обнаруживает прямые и косвенные cycles, cycle — explicit configuration error; graph кешируется как immutable snapshot; package graph и bot graph не смешиваются.
- Required module/capability блокирует dependent; optional module → DEGRADED; optional capability → reduced functionality; required infrastructure может блокировать; optional infrastructure не блокирует.
- Dependency types и errors machine-readable (MISSING_MODULE, MODULE_DISABLED, VERSION_INCOMPATIBLE, CAPABILITY_UNAVAILABLE, CYCLE_DETECTED).
- Dependency auto-enable не default; explicit «enable with dependencies» с подтверждением; cascade disable не default, показывает affected modules, требует confirmation; dependency нельзя silently disable при активных required dependents.
- Admin UI показывает причину BLOCKED и dependency chain; bot owner получает понятное описание, platform admin — полный diagnostic.
- Upgrade: fromVersion/toVersion, compatibility check, migration plan, configuration migration plan, resource change plan, restart requirements, health verification, metadata transactional, UpgradePlan preview для admin.
- External side effects имеют compensation strategy; upgrade failure не уничтожает persisted intent и не делает fake rollback.
- Package update не меняет desired state и не удаляет configuration автоматически; проходит compatibility validation; incompatible → BLOCKED; rollback может восстановить прежний state.
- Repair — отдельная операция, не меняет configuration silently.
- Uninstall: preflight report, dependency check, refusal при active bindings/hard dependents, force — с confirmation, impact report, authorization, audit; mass operations имеют impact preview; affected bots/dependent modules/owned data показываются.
- Uninstall не удаляет bot bindings и configuration; ORPHANED bindings не auto-deleted; orphaned module не исполняется через command/route/Mini App/queue; cleanup — только explicit operator action.
- Reinstall восстанавливает без duplicate binding и без авто-смены desired state; повторно вычисляет effective state; compatible → ACTIVE, incompatible → BLOCKED.
- Persisted desired state — intent, а не unconditional command; runtime восстанавливается только при allowed policy, valid config, available dependencies.
- Convergence model: desired — цель, runtime сходится; failed hot-disable не откатывает desired; честный отчёт «restart pending»; self-healing после устранения причины; retry limits (backoff, max attempts), без бесконечных loops.
- Активация runtime resources idempotent: без duplicate listeners/schedules/workers/webhook handlers; workers не держат activation state как worker-global mutable state; snapshot invalidation после commit, TTL — safety net, недоступны кеш и DB — fail closed.
- Events: BotModuleEnabled/Disabled/Blocked/Recovered и module-level lifecycle events; содержат moduleId, tenantId, botId, actor, operationId; events не source of truth; listeners не меняют lifecycle state произвольно; могут инвалиждировать caches и обновлять projections.
- Audit для connect, disconnect, enable, disable, configure, upgrade, uninstall, purge; runtime failures — audit/diagnostic events.
- Migrations отделены от enable; platform migrations — deployment process; migrations не создают bot-specific rows; seeders не запускаются на boot; migration vs provisioning vs seed vs purge различны; provisioning version отслеживается отдельно от Composer version.
- Module configuration versionирована; config migration required — explicit state; старая configuration не интерпретируется silently; migrations deterministic, history audit-able.
- Package version, API version, configuration version, binding revision — четыре разных понятия.
- Permission system внешний: Engine хранит только permission NAMES из ModuleDefinition, агрегирует их; core не хардкодит names, нет names из URL.
- Permissions granular: module.view/use/configure/connect/disconnect/enable/disable/upgrade/uninstall/purge; configure может быть привилегированнее use; authorization chain Actor → canManageBot → canPerformModuleAction → operation; escalation невозможна.
- Permission denial не изменяет Engine state модуля; authorization и effective state — независимые слои.
- Admin видит все измерения состояния; UI per bot / per tenant; module UI динамическая.
- Один package — bindings многих bots; операции одного bot не влияют на других; effective state per bot (и per chat при chat activation); package lifecycle не зависит от bot count.
- PostgreSQL — single source of truth для bindings, desired state и configuration; runtime/computed state не является source of truth.
