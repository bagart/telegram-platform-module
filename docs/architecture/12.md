12 — Module Registry, Resolver API & Runtime Contracts
1. Назначение

Этот документ формализует API BAGArt\TelegramModuleEngine.

Главная задача — чтобы после внедрения Engine остальные части платформы вообще не знали, как modules:

обнаруживаются;
регистрируются;
подключаются;
хранятся в config;
включаются для bot;
валидируются;
разрешают зависимости;
получают settings;
предоставляют migrations;
seeders;
routes;
menu;
admin resources;
frontend assets.

Все эти операции должны проходить через публичные contracts Engine.

2. Основной принцип

Внутри приложения должно быть:

Composer
↓
Module Discovery
↓
Module Registry
↓
Platform Policy
↓
Bot Module Resolver
↓
Runtime Snapshot
↓
Module consumers

Consumer не должен знать implementation details module registration.

3. Главные API

Engine должен предоставить следующие основные contracts:

TelegramModuleRegistry
TelegramModuleResolver
TelegramBotModuleResolver
TelegramModuleSettingsResolver
TelegramModuleResourceRegistry

и value objects:

TelegramModuleId

TelegramBotModuleSnapshot
4. Registry

TelegramModuleRegistry отвечает за:

"Какие modules существуют в этой installation?"

Он работает на уровне всей Laravel application.

5. Registry НЕ отвечает

Registry не должен решать:

включён ли module у bot;
имеет ли user permission;
можно ли выполнить конкретное действие.
6. Registry scope

Registry — application/platform scoped.

Не:

per bot
per user
per group
7. Registry API

Минимально:

get(string|TelegramModuleId $id): TelegramModuleDefinition

has(string|TelegramModuleId $id): bool

all(): iterable<TelegramModuleDefinition>
8. find

Можно дополнительно:

find(...): ?TelegramModuleDefinition

если отсутствие module является нормальным сценарием.

9. get

get() должен бросать domain exception:

ModuleNotFound

если module отсутствует.

10. Не возвращать null повсюду

Для обязательной зависимости:

get()

лучше, чем:

find() === null
11. Registry immutable

После bootstrap application registry не должен изменяться произвольно.

12. Почему

Иначе один service provider может:

register module A

а другой:

unregister module A

во время runtime.

Это создаёт недетерминированное поведение.

13. Registration phase

Registry строится:

application bootstrap

после discovery и platform configuration.

14. Runtime phase

После завершения bootstrap:

registry = readonly logical snapshot.

29. Snapshot immutable

30. Почему snapshot

Все consumers одного operation получают одинаковое состояние.

31. Пример
    $snapshot = $resolver->resolve($botId);

$snapshot->isEnabled('menu');

$snapshot->isEnabled('mafia');
32. Не делать
    $resolver->isEnabled($bot, 'menu');
    $resolver->isEnabled($bot, 'mafia');
    $resolver->isEnabled($bot, 'cinema');

если каждый вызов способен обращаться в DB.

33. Допустимый shortcut

Можно иметь:

isEnabled()

как facade поверх cached snapshot.

Но внутри должен использоваться один snapshot/context.

157. Security

Module definitions — trusted application code.

Bot settings — untrusted runtime data.

External module metadata — не считать trusted автоматически, если discovery допускает third-party packages.

158. Package trust

Installed Composer package фактически обладает application-level privileges.

Поэтому:

module installation является code deployment operation.

Engine не должен пытаться "sandbox" PHP module.

159. Но runtime data

Должна валидироваться независимо.

160. External data

Например module получает HTML/API content.

Такой data flow должен проходить собственный sanitization/security layer.

207. Ключевой результат

После этого документа у нас появляется чёткая граница:

Module package отвечает за то, что он умеет.

config/tg_modules.php отвечает за то, что разрешено этой установке платформы.

DB bot-module binding отвечает за то, что подключено конкретному боту.

Resolver отвечает за то, что реально доступно сейчас.

Permission system отвечает за то, кому разрешено пользоваться.

Menu отвечает за то, как это показать пользователю.

Management отвечает за то, как этим управлять.

TelegramModuleEngine связывает всё это, но не забирает на себя ответственность самих подсистем.

Именно эта граница позволит дальше без переделки ядра добавлять новые plugin skills, новые bot-specific настройки и новые интерфейсы управления.
