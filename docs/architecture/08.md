08 — Laravel Bootstrap & Resource Registration
1. Назначение

TelegramModuleEngine должен стать единственной точкой управления жизненным циклом подключаемых Telegram-модулей на уровне Laravel-приложения.

Цель:

убрать размазанные foreach;
убрать ручные регистрации module ServiceProvider;
убрать отдельные списки migrations/seeders/routes/commands;
убрать знание платформы о конкретных module packages;
обеспечить одинаковый module registry в HTTP, CLI, queue workers и long-running processes;
не загружать ресурсы отключённых модулей без необходимости;
сохранить возможность Laravel package discovery;
сделать bootstrap детерминированным.

Главный принцип:

Laravel знает только TelegramModuleEngine. TelegramModuleEngine знает registry модулей. Платформа и другие subsystem не перечисляют модули вручную.

   Laravel
   ↓
   TelegramModuleEngineServiceProvider

   Module Discovery

3. Engine ServiceProvider

Основная интеграция:

TelegramModuleEngineServiceProvider

Он является инфраструктурным ServiceProvider самого Engine.

Именно он:

загружает Engine config;
создаёт registry;
запускает discovery;
разрешает platform configuration;
регистрирует module infrastructure;
предоставляет Engine contracts в container.
4. Platform Core

Основная платформа должна иметь только одну явную зависимость:

BAGArt\TelegramModuleEngine

и зарегистрировать:

TelegramModuleEngineServiceProvider

Но даже это желательно сделать стандартным Composer/Laravel package discovery.

5. Composer Discovery

telegram-module-engine должен быть обычным Composer package.

В его Composer metadata:

extra.laravel.providers

указывается:

TelegramModuleEngineServiceProvider

Это единственный ServiceProvider, который платформа обязана знать напрямую.

6. Module ServiceProvider

Для конкретного module:

MafiaServiceProvider

не должен быть перечислен:

в platform composer.json;
в platform bootstrap;
в platform config/app.php.

Он принадлежит самому module package.

7. Важное исключение

Если Laravel package discovery автоматически зарегистрирует:

MafiaServiceProvider

то он будет загружен даже при:

mafia = disabled

Это нежелательно.

Поэтому skill-модули не должны использовать обычный Laravel auto-discovery ServiceProvider как механизм runtime activation.

8. Правильная схема

Composer package:

Mafia
↓
manifest/discovery metadata
↓
TelegramModuleEngine
↓
if platform-enabled
↓
register MafiaServiceProvider
9. Module package

Каждый module package предоставляет Engine manifest/definition.

Например концептуально:

MafiaModuleProvider

но этот provider не должен регистрироваться Laravel напрямую.

Он регистрируется Engine после resolution.

10. Два разных lifecycle

Нужно строго разделить:

package discovery

и:

module activation.

Package discovery отвечает:

Какие modules вообще существуют?

Activation отвечает:

Какие modules должны работать?

11. Discovery

Discovery может использовать Composer metadata.

Например:

bagart.telegram-module

или другой dedicated Composer extra namespace.

Рекомендуется не переиспользовать произвольные Laravel fields для Engine semantics.

12. Composer Manifest

Каждый module package публикует metadata примерно следующего уровня:

package
module_id
definition/provider
engine compatibility

Не нужно дублировать всю Definition в JSON.

13. PHP Definition

Основная Definition остаётся PHP-классом:

TelegramModuleDefinition

Почему:

типы;
IDE;
refactoring;
constants;
value objects;
compile-time visibility;
отсутствие stringly-typed metadata.
14. Composer metadata vs Definition

Composer metadata отвечает:

"где находится module?"

Definition отвечает:

"что представляет собой module?"
15. Не хранить Definition целиком в composer.json

Не нужно превращать composer.json в второй config system.

16. Discovery Contract

Engine должен иметь:

ModuleDiscovery

с responsibility:

discover(): iterable<ModuleDescriptor>
17. ModuleDescriptor

Descriptor на discovery этапе может содержать:

moduleId
packageName
definitionClass
providerClass
packageVersion

Но это ещё не runtime Definition.

18. Definition resolution

После discovery:

ModuleDescriptor
↓
DefinitionFactory
↓
TelegramModuleDefinition
19. Не создавать module instance

Engine не должен создавать:

MafiaModule

CinemaModule

ProxyModule

как runtime objects только ради registry.

Definition должен быть DTO.

20. ServiceProvider registration

После resolution Engine может зарегистрировать provider module:

MafiaServiceProvider

только если module:

platform enabled

и prerequisites выполнены.

21. Provider registration stages

Нужно разделить:

register()

и:

boot()

Laravel сам разделяет эти lifecycle phases.

Engine должен уважать это.

22. Register phase

На register():

bindings;
contracts;
configuration;
infrastructure services.
23. Boot phase

На boot():

routes;
translations;
views;
migrations;
commands;
menu/admin contributions;
other Laravel registrations.

Но конкретные resources должны быть зарегистрированы в правильной фазе Laravel lifecycle.

24. Почему нельзя всё делать в Engine boot

Потому что некоторые Laravel facilities уже используют boot ordering.

Нужно минимально вмешиваться в Laravel lifecycle.

25. Module Resource Registrar

Рекомендуется отдельный contract:

TelegramModuleResourceRegistrar

Но не один giant method.

26. Resource categories

Engine должен поддерживать:

Config
Migrations
Seeders
Routes
Commands

Frontend metadata
27. Config

Module config должен быть module-owned.

Например:

config/tg_modules.php

содержит:

activation policy

а не весь internal config Mafia.

28. Module config

Можно иметь:

config/mafia.php

но загрузка должна происходить только если module active, если это действительно нужно.

29. Не объединять config

Не делать:

config('telegram.modules.*')

для каждой subsystem.

Engine должен иметь собственную canonical config:

tg_modules.php
30. tg_modules.php

Это platform policy.

Например:

mafia => TelegramModuleConfig(...)
31. Config semantics

Config отвечает:

platform-level configuration

Database отвечает:

bot-level runtime configuration
32. Config cache

Laravel:

php artisan config:cache

должен корректно работать.

tg_modules.php должен содержать только cache-safe values.

33. Не использовать closures

В tg_modules.php запрещены:

Closure

потому что config cache.

34. DTO в config

Readonly DTO допустимы только если Laravel config cache корректно сериализует их в текущем поддерживаемом runtime.

Но для максимальной надёжности рекомендуется:

config file
↓
plain arrays/scalars
↓
Engine parser
↓
typed DTO
35. Важное архитектурное уточнение

Изначальная идея:

'mafia' => new TelegramModuleConfig(...)

красивая с точки зрения типов, но делает Laravel config runtime зависимым от concrete PHP classes.

Лучше:

'mafia' => [
'enabled' => true,
'provider' => ...,
...
]

и:

TelegramModuleConfigFactory

преобразует это в immutable DTO.

36. Но пользовательский config должен быть typed

После bootstrap:

ConfigRepository
↓
TelegramModuleConfig

внутри Engine не должно существовать произвольных arrays.

37. Почему

Это даёт:

config syntax = Laravel-friendly

runtime = strongly typed
38. Migration registration

Одна из главных целей Engine:

Убрать:

foreach (config('telegram.modules_migrations', []))
39. Module migration descriptor

Module definition/resource manifest указывает:

migrations path

Например:

database/migrations
40. Laravel migration mechanism

Engine вызывает стандартный:

loadMigrationsFrom(...)

для active modules.

41. Disabled module migrations

Здесь важный вопрос.

Не следует связывать:

runtime module enabled

с:

database schema existence.
42. Migration policy

Migrations относятся к installed/configured module, а не к bot activation.

Если Mafia выключен для Bot A, таблицы Mafia всё равно могут существовать.

43. Platform disabled

Даже если module platform-disabled, его уже установленная database schema не должна автоматически исчезать.

44. Should migrations load for disabled module?

Да, если module установлен и platform policy знает его.

Причина:

Laravel migration system отвечает за состояние schema, а не runtime activation.

45. Important distinction
    Resource registration
    ≠
    Runtime activation
46. Migration lifecycle

При установке package:

Composer
↓
Engine discovery
↓
migrations registered
↓
php artisan migrate
47. Bot activation

При этом:

Bot A → Mafia disabled

не влияет на migrations.

48. Seeders

Seeders сложнее.

Не все seeders должны выполняться автоматически.

49. Seeder categories

Нужно различать:

Platform Seeder
Reference/Data Seeder
Default Configuration Seeder
Demo Seeder
50. Platform Seeder

Например:

permission definitions
system resources
default roles

может быть idempotent.

51. Bot Seeder

Не должен автоматически запускаться для каждого bot просто потому, что module package установлен.

52. Seeder ownership

Engine только агрегирует seeders.

Seeder semantics принадлежат module.

53. Seeder Registry

Engine предоставляет:

ModuleSeederRegistry

и Laravel command:

module:seed

может запускать нужные seeders.

54. Не вызывать все seeders при каждом migrate

Запрещается архитектурно:

migrate
↓
all module seeders
55. Default platform seeding

Можно иметь:

db:seed

который вызывает Engine:

PlatformSeederCoordinator

а тот запускает только declared platform seeders.

56. Seeder idempotency

Все module platform seeders должны быть:

idempotent

или явно обозначены как:

one-shot
57. Seeder dependency order

Если:

Mafia seeder

requires:

Menu resource

Engine должен иметь dependency graph.

58. Seeder dependency

Не использовать порядок:

foreach modules

и надеяться, что Composer order правильный.

59. Topological ordering

Dependencies должны определять порядок:

Menu
↓
Mafia
60. Circular dependency

Если:

A → B
B → A

Engine должен обнаружить:

MODULE_DEPENDENCY_CYCLE

до запуска resources/seeders.

61. Routes

Routes принадлежат module package.

Engine регистрирует routes только согласно resource policy.

62. Bot routes

Например:

/bot/{bot}/mafia

Route registration может существовать на platform level даже если Mafia disabled for every bot.

Но handler должен использовать effective module state.

63. Alternative

Можно регистрировать routes только если module platform-enabled.

Это уменьшает route table.

Рекомендуется:

platform disabled
→ routes not registered

bot disabled
→ route exists, runtime returns module unavailable
64. Почему

Bot activation динамический.

Перерегистрировать Laravel routes при каждом enable/disable невозможно.

Поэтому:

platform-level registration
+ bot-level runtime gating.
65. Commands

Laravel Artisan commands module-level.

Если module platform-enabled:

register commands.

Если bot-specific disabled:

command всё равно может существовать.
66. Commands need scope

Например:

module:mafia:stats

может работать только если:

target bot has Mafia enabled.
67. CLI без bot context

Если command не требует bot:

module:mafia:repair

может быть platform admin operation.

Это должно быть explicit в command descriptor.

68. Command collisions

Engine должен обнаруживать:

same signature

между modules.

69. Translation

Translations можно регистрировать для installed module независимо от bot activation.

Это дешёвый static resource.

70. Views

Views аналогично:

loadViewsFrom

на platform/module level.

71. Disabled module views

Сам факт наличия view не означает доступность feature.

Runtime authorization всё равно применяется.

72. Frontend

Frontend resources требуют особого отношения.

Нельзя строить frontend bundle динамически при каждом bot activation.

73. Frontend principle

Frontend build определяется:

installed modules

а runtime UI определяется:

BotModuleSnapshot
74. Example

Bundle содержит:

Mafia UI
Cinema UI
Proxy UI

Но Bot A может показывать только:

Mafia
Cinema
75. Dynamic chunk loading

Можно использовать lazy chunks:

/assets/modules/mafia.js

Menu/Management загружает chunk только при необходимости.

76. Frontend Registry

Engine может экспортировать:

frontend module manifest

например:

module_id
chunk
entrypoint
permissions
routes
77. Не смешивать backend/frontend registry

Backend:

ModuleRegistry

Frontend:

FrontendModuleManifest

Связь через stable module ID.

78. Asset publication

Не делать:

publish everything for every module

если это не нужно.

Но package resources могут быть published на install/deploy level.

79. vendor:publish

Это deployment concern.

Engine не должен автоматически выполнять:

vendor:publish

при каждом request.

80. Storage

Module storage directories должны быть namespaced:

storage/app/modules/{moduleId}
81. Cache

Module cache:

cache/modules/{moduleId}

или Redis namespace.

82. Route caching

route:cache должен видеть одинаковый module set.

Поэтому:

config/tg_modules.php

должен быть стабильным между deploys.

83. Bot activation не влияет route cache

Это принципиально.

Нельзя делать:

route cache per bot.
84. Config cache

Platform module configuration:

config/tg_modules.php

попадает в Laravel config cache.

Bot activation:

DB/cache

и не должен попадать в config cache.

85. Queue workers

Queue worker запускается с тем же:

ModuleRegistry

что и HTTP.

86. Job serialization

Job не должен сериализовать:

ModuleDefinition object

если можно передать:

moduleId

и разрешить Definition из registry.

87. Long-running worker

При обновлении package:

worker restart required

если изменились PHP classes/Definition.

88. Runtime activation changes

При:

enable/disable bot module

worker должен получить:

BotModuleStateChanged

и обновить snapshot.

89. ServiceProvider registration and bot activation

Ключевой принцип:

ServiceProvider регистрируется один раз на application boot, а module activation проверяется на runtime.

Иначе невозможно эффективно поддерживать динамический набор modules per bot.

90. Поэтому два уровня
    Application lifecycle
    ↓
    Module resource registration

и:

Bot runtime lifecycle
↓
Module activation

Их нельзя объединять.

95. Resource registration modes

Нужно иметь три категории:

STATIC

Регистрируется при application boot:

99. Почему это важно

Если пытаться зарегистрировать:

Bot A Mafia

как Laravel ServiceProvider отдельно от:

Bot B Mafia

архитектура сломается.

Laravel application имеет один container.

100. Один application

Платформа запускает много bots внутри одного Laravel application.

Следовательно:

ServiceProvider ≠ Bot Module Activation.
101. Это должно быть зафиксировано

Laravel ServiceProvider представляет installed/platform module infrastructure, а не activation module для конкретного bot.

102. Module Resource Registrar

Рекомендуемый pipeline:

103. ResourceResolver

Проверяет:

104. ResourceRegistrar

Регистрирует только нужные application resources.

105. Failure policy

Если один module invalid:

не падать молча.

В зависимости от criticality:

platform bootstrap failure

или:

module disabled + diagnostic.
106. Critical module

Например:

Menu

может быть platform-critical, если вся платформа без него не функционирует.

Но Engine сам не должен считать Menu критическим.

Это policy платформы.

107. Engine independence

TelegramModuleEngine не должен знать:

Menu is mandatory

Платформа может определить это через dependency policy.

108. Module compatibility

Definition должен объявлять:

engineVersion requirement

или package Composer должен требовать совместимую версию Engine.

Предпочтительно Composer constraints.

109. Laravel compatibility

Также package Composer:

require:
laravel/framework

с подходящим constraint.

Engine не должен вручную проверять Laravel version без необходимости.

Проверить:

должна повторно проверить state.

143. Engine package

Engine должен быть пригоден для использования без конкретной platform.

То есть:

pure Laravel package

с минимальной Telegram-specific coupling.

144. Telegram-specific layer

Поскольку это именно:

TelegramModuleEngine

допустимы Telegram-specific concepts:

bot
group
Telegram permissions
Mini App

Но generic Laravel module machinery не следует дублировать.

145. No magic scanning

Не сканировать:

app/Modules/*
misc/*

по файловой системе.

Discovery должен быть explicit через Composer package metadata.

146. Почему

Filesystem scanning:

недетерминирован;
плохо работает с package boundaries;
ломается в production builds;
усложняет caching;
скрывает dependency graph.
147. Discovery is explicit

Каждый module package сам заявляет:

I am a Telegram module.

Engine собирает их.

148. Configuration is explicit

Platform config:

I allow/use this module.
149. Activation is explicit

Bot DB:

I enable this module for this bot.
150. Runtime is explicit

Snapshot:

This is the effective module state for this bot.

152. Итоговые архитектурные правила
     Rule 1

Laravel знает только Engine provider.

Rule 2

Module packages не регистрируют свои ServiceProvider напрямую через Laravel auto-discovery.

Rule 3

Composer discovery определяет installed modules.

Rule 4

config/tg_modules.php определяет platform policy.

Rule 5

Database определяет bot activation.

Rule 6

Laravel ServiceProvider никогда не является bot activation mechanism.

Rule 7

Migrations принадлежат установленному module, а не bot activation.

Rule 8

Routes/commands регистрируются на application/platform уровне и проверяют bot module state во время выполнения.

Rule 9

Menu/Admin/Permissions используют Engine registries и runtime snapshots.

Rule 10

Один Laravel application имеет один ModuleRegistry, но много BotModuleSnapshot.

Rule 11

Config cache не содержит bot state.

Rule 12

Route cache не зависит от конкретных bot activation states.

Rule 13

Любая runtime activation change проходит через application use case.

Rule 14

Engine не знает concrete feature modules.

Rule 15

Никаких foreach(config(...modules...)) в платформе вне самого Engine.

153. Главный результат

После реализации этой архитектуры старый код вида:

foreach ((array) config('telegram.modules_seeders', []) as $seeder) {
$this->call($seeder);
}

исчезает из платформы.

Вместо него:

PlatformSeeder
↓
TelegramModuleEngine
↓
ModuleSeederRegistry
↓
dependency-aware seeding

Аналогично для:

migrations
providers
commands
routes
menu
admin
permissions
frontend

Платформа перестаёт знать как именно подключаются модули.

Она знает только:

TelegramModuleEngine.

И это, на мой взгляд, уже правильная граница ответственности для твоей архитектуры: Engine является control plane модулей, а не просто очередным helper для foreach по конфигу.
