32 — Module Configuration Model: глобальная конфигурация, bot-specific настройки и typed DTO
1. Назначение

После разделения:

installed module
platform policy
bot module binding
effective capabilities

нужно окончательно определить, где и как живёт конфигурация module.

Главная цель:

не допустить, чтобы configuration снова размазалась по Laravel config, .env, Eloquent models, controllers, service providers и Admin UI.

Конфигурация должна иметь чёткие уровни владения.

2. Главный принцип

Нужно разделить:

Module Definition
↓
Platform Configuration
↓
Bot Configuration
↓
Runtime Effective Configuration.

Это четыре разных вещи.

3. Module Definition

Принадлежит самому module package.

Определяет:

module id
name
description
version
dependencies
capabilities
resources
default configuration
configuration schema
activation policy.

Это не пользовательская конфигурация.

4. Platform Configuration

Находится:

config/tg_modules.php

и задаётся владельцем Laravel application.

Например:

enabled
serviceProvider
platformConfig
menu configuration
admin configuration
seeders
migrations
frontend resources
platform-wide defaults.
5. Platform configuration

не должна содержать:

bot_id
chat_id
user_id
tenant_id.
6. Это принципиально.

config/tg_modules.php описывает:

как module встроен в платформу.

А не:

как module работает у конкретного bot.
7. Bot Configuration

Хранится runtime persistence.

Например:

bot_module_bindings

и связанная configuration data.

Определяет:

включён ли module
bot-specific settings
module overrides.
8. Например Mafia:

Platform defaults:

max_players = 16
night_timeout = 60

Bot A:

max_players = 10

Bot B:

max_players = 20.
9. При этом ModuleDefinition

остаётся одинаковым.

10. Effective Configuration

Runtime получает уже собранную конфигурацию:

ModuleDefinition defaults
↓
Platform configuration
↓
Bot overrides
↓
Runtime effective config.
11. Необходимо явно определить precedence.

Рекомендуется:

Module defaults
<
Platform defaults
<
Bot overrides.
12. Но не все параметры разрешено переопределять.

Это критично.

13. Например:
    serviceProvider

никогда не может быть overridden bot configuration.

14. То же касается:
    handler
    routes
    migrations
    seeders
    resource registration
    permission definitions
    capability definitions.
15. Bot configuration

может менять только:

module-declared configurable values.
16. Следовательно, configuration должна иметь категории.

Например:

PLATFORM
BOT
RUNTIME.
17. PLATFORM-only

Например:

queue connection
storage driver
external service endpoint
resource registration.
18. BOT-configurable

Например:

language
limits
feature switches
moderation settings
UI preferences.
19. RUNTIME-only

Например:

cached capability snapshot
health state
compiled configuration.

Это вообще не user configuration.

20. Не позволять Admin UI

самостоятельно решать:

какие поля можно редактировать.
21. Module должен предоставить:
    ConfigurationDescriptor.
22. Descriptor описывает:
    key
    type
    default
    scope
    editable
    validation
    secret
    visibility
    label
    description.
23. Но business defaults

должны находиться в typed config DTO,

24. Например:
    TelegramBotSummarizerConfig(
    enabled: true,
    maxTokens: 2000,
    temperature: 0.2
    )
25. Конструктор является источником:
    types
    defaults
    requiredness.
26. Это соответствует выбранному принципу:

DTO максимально простые, immutable и без business methods.

27. DTO не должен делать:
    validation logic
    DB calls
    environment reads
    HTTP requests
    dependency resolution.
28. Validation

должна находиться отдельно.

Например:

ModuleConfigurationValidator.

Чтобы один и тот же config можно было проверить:

CLI
Web Admin
tests
bootstrap
runtime.
30. Не:
    if ($value < 0) ...

в Controller.

31. Configuration hydration

должна быть централизована.

32. Например:
    ModuleConfigFactory

или:

ModuleConfigurationResolver.
33. Flow:
    raw stored configuration
    ↓
    schema/DTO hydration
    ↓
    validation
    ↓
    effective typed configuration.
34. Ни один module consumer

не должен напрямую читать:

config(...)
JSONB
Eloquent attribute.

получает:

    $config = $moduleContext->config(
    SummarizerConfig::class

если module получает свой config напрямую через dependency injection.

40. Тогда domain code

вообще не знает:

DB
JSON.
41. Configuration resolution

делается на boundary.

42. Для long-running workers

это особенно важно.

Config нельзя читать:

из DB

при каждом вызове.

43. Worker получает:
    immutable effective configuration snapshot.
44. Если config изменился,

создаётся новая version.

45. Например:
    Bot A
    summarizer config
    version = 17.

После изменения:

    bot:{id}:module:{module}:config:{version}.
47. Config version

должен быть частью:

48. Тогда runtime знает:
    какой configuration использовался.
49. Это очень полезно для audit/debugging.

Например:

Message processed with:

50. Configuration changes

должны быть atomic.

51. Нельзя получить:
    enabled = true
    config = old

при одной части транзакции

и:

config = new

при другой.

52. Activation + configuration

должны быть согласованы.

53. При включении module

можно использовать:

default configuration.
54. Если default configuration invalid:
    activation fails.
55. Нельзя включить module

с заведомо невалидным config.

56. При изменении config:
    validate
    ↓
    authorize
    ↓
    transaction
    ↓
    version++
    ↓
    event/outbox.
57. Configuration schema

должна быть versioned.

58. Например:
    configSchemaVersion = 3.
59. Это необходимо потому что:
    Module v1
    ↓
    Module v2

может изменить структуру config.

60. DB configuration

не должна навсегда зависеть

от текущего PHP DTO.

61. Нужна migration mechanism.
62. Например:
    Config v1
    ↓
    migration
    ↓
    Config v2
    ↓
    DTO v2.
63. Migration должна принадлежать module.
64. Engine предоставляет infrastructure,

но не знает:

как `maxUsers`

переименовать в:

`maxParticipants`.
65. Это responsibility module.
66. Нельзя делать:
    generic recursive JSON magic

как универсальную migration систему.

67. Для каждой version:
    explicit migration.
68. Например:
    SummarizerConfigV1ToV2.
69. Migration должна быть:
    deterministic
    testable
    idempotent where possible.
70. Не выполнять migration

в обычном runtime request.

71. Migration выполняется:
    deploy
    module upgrade
    explicit configuration upgrade.
72. Runtime

может только обнаружить:

CONFIG_VERSION_UNSUPPORTED.
73. Это безопаснее.
74. Secrets

нужно рассмотреть отдельно.

75. В module configuration

может быть поле:

apiKey.

Но нельзя хранить его как обычный JSON value.

76. Лучше:
    SecretReference.
77. Например:
    secret('openai.summarizer.key').
78. DTO получает:
    SecretReference

или resolved secret

на boundary.

79. Но Admin UI

не должен получать secret обратно.

80. API response:
    hasValue = true

вместо:

apiKey = "....".
81. Secret update:
    set
    replace
    clear.
82. Никогда:
    GET configuration → return secret.
83. Это должно быть частью generic Engine contract.
84. Configuration fields

могут быть:

PUBLIC
SENSITIVE
SECRET.
85. PUBLIC

можно показывать.

86. SENSITIVE

можно показывать ограниченно.

87. SECRET

никогда не возвращается в plain form.

88. Но Engine

не должен превращаться в полноценный secret manager.

89. Лучше abstraction:
    SecretStore.
90. Реализация может использовать:
    environment
    encrypted DB
    external secret manager.
91. Module только знает:
    SecretReference.
92. Configuration ownership

тоже нужно явно определить.

93. Каждое поле принадлежит:
    module
    platform
    bot.

определяет semantic meaning.

допустимы ли bot overrides.

    maxPlayers

## Merged from earlier revisions (04, 10, 15, 19, 22, 27, 46)

### Strict / deny-by-default mode

Engine config supports `engine.strict` (recommended true in production):

- Unknown module entry in config/tg_modules.php (package not discovered) → explicit `MODULE_NOT_DISCOVERED` error, never silently ignored. A typo like `summariser` must not look like a disabled module.
- A discovered module absent from config has state `DISCOVERED / NOT_CONFIGURED`, never enabled. Installing a Composer package must not automatically activate handlers, webhooks, admin endpoints, commands, permissions or jobs — this is the deny-by-default security principle.
- Normalized internal platform states: `NOT_CONFIGURED`, `DISABLED`, `ENABLED`, `INVALID` (plus `BLOCKED_BY_PLATFORM_POLICY` when platform disables a module whose bot bindings still say enabled=true).

### Policy modes: DISCOVER_ALL vs EXPLICIT_ALLOWLIST

Engine should support a `modulesMode`:

- `DISCOVER_ALL`: discovered modules are platform-available by default (unless explicitly disabled).
- `EXPLICIT_ALLOWLIST`: only modules explicitly listed in config are allowed; preferred for security-sensitive deployments.
- In both modes "installed" ≠ "allowed" — Admin must show both dimensions.

### Config as security boundary

config/tg_modules.php cannot swap PHP implementation. Config must not change: module ID, package, provider class, handlers, migrations, commands, capabilities, dependency graph. If a provider override is ever allowed, it must be validated against the discovered Definition — provider mismatch between config and package is a boot error, never silent. Module Definition is the canonical owner of provider identity.

Class names may come only from trusted module Definitions, never from user-controlled settings or Admin UI input (Admin may send `model = "foo"`, never `provider = "Some\Evil\Class"`). Never `new $class(...$request)` from HTTP input.

No `unserialize()` of stored settings (PHP object injection). Bot settings are stored as structured JSON, read back through validate → typed DTO. Config payloads must not contain PHP code, instantiation instructions, closures, or arbitrary service references; config must stay plain static PHP data compatible with `php artisan config:cache`.

### Secrets — additional rules

- Secrets (API keys, tokens, passwords) never live in tg_modules.php, Definition, or bot settings JSON — the file is version-controlled and must be Git-safe.
- Secrets are never exported/imported, never copied on bot clone, never included in templates.
- Empty string must not be interpreted as "delete secret"; clearing requires an explicit clear operation (common admin mistake).
- `env()` is allowed only in the configuration layer; module business code must never read `env('MODULE_X_ENABLED')`.
- Avoid dumping arbitrary config DTOs to logs; use redacted serialization for diagnostics.

### Validation rules (unique additions)

- Two validation levels: structural (types, required, enum, ranges, formats — offline, deterministic) vs semantic (dependency/resource/external-service availability — may require runtime). `tg:modules:validate` runs structural offline; keep the levels separate.
- Engine CLI: `tg:modules:validate` (config, discovery, definitions, dependencies, resources, schemas; non-zero exit on error) and `tg:modules:list` / `tg:bot:modules {bot}` diagnostics. Production deployment must run validate before queue workers, web workers and scheduler.
- Stable diagnostic codes: `CONFIG_INVALID`, `MODULE_NOT_DISCOVERED`, `MODULE_NOT_CONFIGURED`, `MODULE_DISABLED`, `DEPENDENCY_MISSING`, `DEPENDENCY_DISABLED`, `MODULE_ORPHANED`, `TG_MODULE_CONFIG_DUPLICATE`, `TG_MODULE_CONFIG_TYPE_ERROR`. Error codes, not exception messages, are the contract for CLI/Admin/logs/tests.
- Fail-fast vs degraded: fatal platform errors (e.g. duplicate module ID) fail bootstrap; a broken optional module becomes disabled/unavailable while the platform keeps running. Never silently fall back to defaults on invalid config.
- Deprecated config fields may be temporarily supported with a warning and removal documentation; unknown fields are always errors. No module aliases: module ID is persistent identity and must not change when the Composer package is renamed; rename requires explicit migration.
- URL overrides: distinguish internal paths from external URLs as separate types; validate URLs; prevent open redirects; nullable typed fields instead of empty-string sentinels.
- Backend validation is authoritative; frontend validation is UX only.

### Config file as versioned contract

tg_modules.php is a public platform configuration API, not arbitrary Laravel config: schema changes require migration/documentation; a top-level `version => 1` may be added when real breaking changes are expected (not before). Only Engine reads it; application code never calls `config('tg_modules...')`.

Platform disable (allowed=false) preserves existing bindings, permissions and data (effective state becomes blocked); re-enable restores eligibility but never auto-connects bots. Mass enable/disable is an explicit, auditable command/migration, never a side effect of deployment.
